## 一、「旧记忆归谁」是一道选择题，不由助手代定

主人明确要求「给用户自己选择的机会」。所以这里**不写默认值**、不替使用者拍板：
旧记忆里没有任何人格标记，分给谁都是猜；猜错的表现很隐蔽（换人格后她突然
不记得某件事，面板上还看不出为什么）。

### 三个候选（面板上让使用者自己选，随时可改）

| 选项 | 含义 | 代价 |
|---|---|---|
| **A 共享** | 旧记忆对所有人格可见；开启隔离后只有**新**记忆各写各的 | 零迁移、最安全；但老人格的事新人格也知道 |
| **B 归某一个人格** | 旧记忆整体归指定人格，其他人格从空白开始 | 要选「哪个人格」；选错了要能一键改回来（不删数据，只改归属标记） |
| **C 逐会话 / 逐条指定** | 面板列出旧记忆的键（沿用账号迁移页那套 `scan()`），使用者逐个指给人格 | 最灵活、工作量最大；适合记忆多且确实想分开的人 |

三者都必须满足：**只写归属标记，不搬动旧数据**；改主意时改标记即可，不需要 rekey。
这样才不会重演账号迁移那次「删了旧 openid，整段记忆看起来全没了」的坑。

### 共用的技术底子（三个选项都用得上）

1. 项目已经有一套为账号迁移做的 `aliases` 备用键机制（`memory.list / journal.recent /
   graph.nowEdges` 全都吃 `aliases` 参数）——人格隔离复用它，不新造读取路径。
2. 归属标记单独存一份（`persona-ownership.json`），不塞进 `memory.json`。
   理由：改归属不该碰记忆正文，也不该被「一键改写 / 备份回退」连带覆盖。
3. 默认**关闭隔离**（`isolate=false`），升级前后行为逐字一致；开启时才问上面的选项。
   面板必须让使用者自己选，不能由代码替他选 A。

## 二、落地方案（三层，每层可独立开关、可回退）

统一一个纯函数：`scopeKey(chatId, personaId, enabled)`。
`enabled=false` 时原样返回 `chatId`（**升级前后行为逐字一致**）；
开启时返回 `chatId::<personaId>` 作为**写入键**。

### 第 1 层：记忆（事实 / 日记 / 关系）

- 写入：新事实、新日记、新关系边写到 `scopeKey(...)`。
- 读取：主键 = 专属键，`aliases` = `[原 chatId, ...账号别名]`。
  于是专属记忆 + 共享旧记忆一起读得到（复用现成的别名合并，不改各模块内部）。
- 旧数据一个字节不动。关掉开关即回到「一锅记忆」，专属键的内容仍在盘上，不丢。

**风险点**：`apply-markers.js` 的「忘掉 / 清空」也吃 `aliases`，隔离时删除会跨到共享键——
这正是「同一个写操作摆两个地方」的老问题。开启隔离后，删除要只删当前人格的键，
共享键里的条目要**明确提示**「这条是共享记忆，删了所有人格都看不到」。

### 第 2 层：会话

- `sessions.json` 的 key 用 `scopeKey(...)`，每个人格独立 DSH 会话（上下文不串味）。
- 旧 key 保留不动；关闭开关后回到原会话。
- 注意 `chatId` 同时是 QQ 出站 target：**只有 DSH 会话键能被 scope**，
  发消息用的 target 必须仍是原始 openid。这是整条链最容易写错的地方——
  一旦把 `chatId::<persona>` 发给 QQ，消息直接发不出去且不报错。

### 第 3 层：流水

- `usage.json` / `delivery.json` / `awake.json` 按 `scopeKey` 分行记账。
- 总量不受影响，只是每个人格各看各的。

## 三、实施时怎么绕开这三条风险

上面的担心是真实的，所以实现没有采用「在入口替换 chatId」或「搬动存量数据」：

1. **零迁移、可回退**：物理键只在 store 层生成（`chatId::p:<人格>`），
   旧键原封不动；归属标记单独存 `persona-ownership.json`，改主意只改标记。
   关掉开关即回到原来的一锅记忆，专属键数据仍在盘上、不删不搬，
   因此不需要 rekey 工具，也没有不可逆后果。
2. **不动 host 各调用点**：`chat.chatId` 全程保持原始 openid——它同时是
   QQ 出站 target，改了消息会发不出去且不报错。改的是四个 store 的
   **入参**：规则表（`PLAN`）按「chatId 位置 + aliases 位置」声明，
   由通用函数提取/替换/注入，覆盖全部吃 chatId 的对外方法。
3. **两轮独立对抗性测试**：第一轮抓出 4 条 P0（`journal.insert` 方法名
   写错、PLAN 大面积漏网、`recentTimeline`/`top` 参数位置错、日记
   写共享键读物理键导致分裂），全部修复；第二轮 P0 清零。
   最后又按主人要求做了一次覆盖全部改动的统一对抗测试。

实现落在 `src/persona-scope.js`、`src/host.js`、`src/config.js`、
`src/account.js`、`src/rewrite.js`、`client/client.js`（人格页选择卡），
测试在 `test/persona-scope.test.js`（17 条）与 `test/client-render.test.js`。

## 四、验收口径（已逐条跑过）

- `enabled=false` 时：所有键、所有读取结果、所有路由返回与升级前**逐字一致**
  （42 个包装方法参数逐字透传，有对照测试）。✅
- 开启后：A 人格记住的事，B 人格读不到；A 共享下旧记忆两边都读得到。✅
- 删除：只删当前人格的键，不跨共享键（`remove`/`clearChat`/`forget`
  都是 write 模式，不追加共享别名）。✅
- 出站：`msg.send` 的 target 永远是原始 openid，不含 `::p:`
  （出站链五个文件零命中物理键记号，真调验证）。✅
- 关掉开关：回到共享库，专属键数据仍在盘上、不丢不删。✅
- 账号迁移的 `aliasesOf` 与人格的 `scopeKey` 叠加时不能互相覆盖
  （账号别名原样保留，归属允许的旧键追加在后面）。✅
- 没选策略不许开：`/persona/scope/save` 拦 400，`state()` 还有第二道闸。✅
- 并发两轮不串味：人格按 chatId 存 `personaByChat`，不是全局单值。✅
