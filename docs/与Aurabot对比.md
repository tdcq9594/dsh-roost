# 和 Aurabot 的功能对比

> 对照对象：[dsh-aurabot-qq](https://github.com/accomplish07zrh-eng/dsh-aurabot-qq)（MIT）
> 对照时间：2026-10-26，我们 = dsh-roost 0.3.5 + ai-chat 3.1.0

---

## 一、一句话结论

**传输层我们更好，对话体验它更成熟。**

它是「hook 本机 QQ 客户端的机器人」，能拿到 OneBot 的全部事件（打字状态、戳一戳、QQ 空间）；
我们是「官方接口的机器人」，拿不到那些，但**不用扫码登录、不会被风控、官方支持**。

差距集中在**「怎么把一段话变成一轮对话」**这件事上——它做了很多打磨，我们只做了最直白的版本。

---

## 二、真该补的（按性价比排）

### ① 消息合并 —— 差距最大的一条

**它的做法**（`hub.js` 866-890）：

```
对方还在打字 → 先别急着回，等他停下来
群聊里大家你一句我一句 → 多等一会儿，把一段话攒齐再回
它正在回上一段时 → 新消息先攒着，等说完一起交过去
```

四个参数：`waitSec`（私聊停顿多久算说完）、`maxSec`（最多等多久）、
`groupWaitSec`、`groupMaxSec`（群里同理）。

**我们现在的做法**：来一条处理一条。群里三个人连着说三句，它就回三条——
或者更糟，第一条还没回完，后面两条被 busy 锁直接丢掉。

**为什么必须补**：这不是锦上添花，是「像不像人」的分水岭。
真人不会在你打字打到一半时插话，也不会对同一段话回三次。

**怎么做**：在 ai-chat 的 `handle()` 前面加一个**收集窗口**——
收到消息先入缓冲，等 `waitSec` 没新消息（或到 `maxSec`）再一次性交给模型。
群里如果上一轮还在跑，把新消息攒进下一轮，而不是丢掉。

**代价**：回复会晚 1-3 秒。对聊天来说是值得的。

---

### ② 图片理解 —— 现在模型「看不见」图

**它的做法**：把图下载下来转 base64，作为 **image 内容块**喂给模型（多模态）。

**我们的做法**：`inbound.js` 里把图变成一句「（发了一张图：https://…）」——
**模型只看到一行字，根本看不见图**。有人发张截图问「这报错怎么修」，它只能干瞪眼。

**怎么做**：payload 里带上 `url`（已经有了），dsh-roost 侧把图片 URL 转成
DSH 的 image 内容块；或者 ai-chat 直接下载转 base64 塞进 payload。

**代价**：一张图几百到几千 token。要限张数（它限 4 张）和大小（它限 8MB）。

---

### ③ 人格库 —— 现在只有一段文本

**它的做法**：多个 persona，各有名字/标签/正文，可以按会话切换，面板里能编辑。

**我们的做法**：一段全局 `persona.text` + 按会话的 `<<persona:>>` 覆盖。
够用，但**不能在面板里预置几套换着用**。

**怎么做**：`personas: [{id, name, tags, text}]` + `persona.current`，按群覆盖。

**优先级**：中。现在能用，只是不方便。

---

### ④ 表情包库 —— 能发，但没有「库」

**它的做法**：一个 `stickers` 模块，能收集群里的表情、按情绪 `match(query)` 挑一张发。

**我们的做法**：能发图（`<<image: 路径>>`），但**没有库**——
模型得自己知道某个路径下有张合适的图。

**怎么做**：一个目录 + 一个索引（`[{file, tags, mood}]`），
给模型一个工具/约定：`<<image: 表情:开心>>` 由插件去库里挑。

**优先级**：中。接上 DSH 的生图工具后，其实「现画一张」比「翻库存」更灵活。

---

### ⑤ 主动搭话 —— 完全没有

**它的做法**：定时/随机主动找主人说话，群里也会偶尔插一句。

**我们没有**：只被动应答。

**注意**：官方接口的主动消息有硬限制——**单关系 20 条/分钟、每群 1000 条/天**，
而且群里主动说话容易被当成骚扰。要做也得做成「只对主人、每天一两次」。

**优先级**：低。风险大于收益，除非你明确想要。

---

### ⑥ TTS 语音 —— 只能发现成音频

**它的做法**：接了 TTS，AI 说的话可以变成语音发出来。

**我们的做法**：`<<voice: 路径>>` 能发音频文件，但**没有把文字变成声音的能力**。

**怎么做**：接一个 TTS 服务（本地或云端），拿到音频文件再走 `replyVoice`。

**优先级**：中低。跟「翻唱」共用同一套 TTS 基建。

## 三、我们已经更强的地方

| 项 | 它 | 我们 |
|---|---|---|
| **权限** | 三档，群里所有人同一档 | 四档，**逐条消息判定**，认不出身份只给聊天 |
| **调试** | 日志页 | 日志 + **概览** + **一键自测**（不经过 QQ 直接跑一轮） |
| **接入** | 向导，但要装 SnowLuma、扫码 | **一键**装 Roost + 插件 + 配适配器 |
| **给别的程序调** | 本地 HTTP 接口 | `roost-mcp`（标准 MCP，Claude/Cursor 直接接） |
| **传输** | hook 本机 QQ 客户端 | **官方接口**，不用扫码、不会被风控 |
| **多机器人** | 单机器人 | Roost 本身支持多机器人 |

---

## 四、不该做的（附理由）

| 功能 | 为什么不做 |
|---|---|
| **连接管理**（装 SnowLuma、扫码登录） | 我们走官方接口，不需要 hook 客户端。这是**架构差异**，不是缺功能 |
| **QQ 空间日记** | 官方 Bot API 没有空间接口。要做只能 hook，等于换掉整个传输层 |
| **打字中提示** | OneBot 特有事件，官方接口没有 |
| **扩展 / 模块系统** | DSH 本身就是扩展点。再套一层等于重复造轮子 |
| **B 站解析** | 要外部 API + 解析逻辑，价值低。真需要的话让 AI 用 `web` 工具查 |

---

## 五、做不了 / 代价太大

**翻唱**：要 TTS + 歌唱模型（它自己集成了整条 pipeline）。
这不是「加个开关」，是另一个项目的体量。真要做，单独开一个插件。

---

## 六、建议顺序

如果只做两件，做 **① 消息合并** 和 **② 图片理解**——

这两件直接决定「像不像个正常人」：
- 不合并：你打字打到一半它就插嘴
- 不看图：发张截图问它，它只会说「我看到你发了一张图」

剩下的（人格库、表情库、TTS、主动搭话）是加分项，按需再加。
