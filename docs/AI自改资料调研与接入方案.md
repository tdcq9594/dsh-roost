# 让 AI 自己改资料 / 菜单：主流做法调研 + dsh-roost 接入方案

> 调研时间 2026-11-16。框架侧（`douluo/bot` v1.1.0）已打通「改昵称 / 简介 / 头像」。
> 本文覆盖两个出口：**菜单**（便宜、日常、表达心情）和**资料**（昂贵、稀有、换身份），
> 回答两件事：**别人是怎么做的**、**我们该怎么接才不踩坑**。

---

## 一、结论（先看这段）

1. **主流分四派**：主人命令型（云崽 Yenai）、AI 直接写型（AstrBot `kai_presence`）、
   情绪驱动自动型（AstrBot `realistic-persona`）、身份预设切换型（Koishi `relifeluna`）。
   四派的共同点是**都有闸**：要么收权限（只给主人），要么收频率（冷却 / 阈值），
   要么收自由度（只能应用预设）。
2. **官方机器人不是非官方生态**：NapCat 那套 `set_qq_profile` 改的是个人号资料，
   一条 HTTP 就完了；官方机器人的昵称/头像/简介要**开发者票据**（账号级，能改名下全部机器人）、
   要上传图、要落平台配置，成本和影响面都高两个数量级。
   **「AI 天天改签名」这条路在官方 bot 上不成立**，不能照搬。
3. **网上那句「每月只能改 5 次」是旧文档**：它出自 `tencent-connect/bot-docs` 的
   2023 版 README（同一份文件里还写着「个人开发者不能开群」，早不成立了）。
   现行 `bot.qq.com/wiki` **没有这一节**，实测改昵称/简介也没碰到限制。
   → 真实上限未知，别再引用这个数（本方案已按「未知」重写，见 §三.0）。
4. **`remaining_modify_count` 是从没验证过的字段**：`dev.bot.get` 里读了一个
   `base.remaining_modify_count`（`platform.js:927`），但它是当初照着旧文档顺手加的，
   没票时是 `null`，有票时回不回**没人确认过**。
   → 闸门按「本地节奏」设计，那个数**能读到就当上限，读不到不阻塞**。
5. **心情不该用资料表达，用菜单**：`PUT /v2/menu` 官方明确写着 5 次/**分钟**、
   且「暂不需要单独提审」；资料那条既贵、又可能碰审核、还有内容规范。
   同一个「让别人看见我现在的样子」的诉求，走菜单便宜两个数量级。
   → 资料当**稀有事件**（换身份、主人发话），菜单当**日常出口**（今天什么心情）。
6. **落地顺序：先做菜单，再做资料**：菜单便宜、可回滚、还能验证她到底有没有表达欲；
   资料先只读、再开写，自主那条最后谈。
   **不要一上来就给模型自主改名**。

## 二、我们手上已有的牌

### 2.1 框架侧（`douluo/bot`）

| 能力 | 入口 | scope | 备注 |
|---|---|---|---|
| 改资料 | `dev.bot.set { appid, patch:{ base:{ name, desc, avatarId } } }` | `message` | 一个入口按 patch 分发，`setBot` 见 `src/dev/platform.js:965` |
| 换头像 | `dev.bot.avatar { appid, src:{ dataUrl\|url\|avatarId } }` | `message` | 上传→套用两步合成一步，`src/dev/platform.js:1273` |
| 读资料 | `dev.bot.get { appid }` | `read` | 回 `base.name/desc/avatar`；`modifyRemain` 字段**未验证是否真返回**（§三.0） |
| OneBot 兼容层 | `set_qq_profile` / `get_self_longnick` / `set_self_longnick` | — | `src/onebot/actions.js:590`，**只改本机这只**（`cfg.appId`），只发改动项 |
| 昵称回落 | `src/services/nickname.js` | — | 启动 3s + 每 6h 用 `/users/@me` 把平台昵称同步进 `cfg.name` |
| 全局菜单 | `getGlobalMenu()` / `setGlobalMenu(items)` | 经 `qq.call` 走 `message` | `src/api.js:1518/1533`；PUT **覆盖式**、≤10 项、5 QPM |
| 指令面板 | `listPanels` / `createPanel` / `updatePanel` / `deletePanel` | 同上 | `src/api.js:1550` 起；≤20 面板、每面板 ≤20 项 |

> 菜单/面板**不在** `QQ_BLOCKED_APIS` 里（`src/host/methods.js:119`），
> 风险档按 HTTP 方法算：PUT/POST = `write` → 要 `message`，
> 所以 dsh-roost 现有令牌**直接能调**，不需要 `allowManage`、也不需要改框架。

协议侧默认 `scopes = ['read','message']`（`src/host/methods.js:60`），
所以 **`dev.bot.set` / `dev.bot.avatar` 现成可用**；`dev.login.*` 是 `manage`，
dsh-roost 拿不到——模型永远不会摸到扫码登录。

### 2.2 dsh-roost 侧

- rpc 通道：`roost.rpc(method, params)`，`system.hello` 已回 `bot.appId`（`bot/src/host/methods.js:217`）。
- 写类能力的现成范式：`src/group-admin.js` —— 参数收窄 + `DAILY_LIMITS` + `protectedHit` + `audit()`。
- 工具注册：`src/tools.js` 的 `shapeTool` / `loadDefineTool`，别忘 `output.schema/render`。
- 权限：`src/permissions.js` 六档（owner…unknown）+ `src/capabilities.js` 能力页策略。
- 她自己的名字：`personaName()` 四级优先级
  `persona.selfName` > `config.persona.name` > `label` > `大肥鱼`（`src/personas.js:105`）。

## 三、官方平台到底限制了什么（**本节已更正**）

### 3.0 先撤回一个错误结论

上一版本文写的是「官方文档写死：基本信息每月可修改 5 次」。**这条不成立**，
核过一轮之后：

| | 说法 | 出处 | 现在还在吗 |
|---|---|---|---|
| A | 「基本信息修改限制：每月可修改 5 次」+ 上线后改资料要单独提审 | `tencent-connect/bot-docs` 的 `docs/README.md` 第 6 节 | 文件还在，但**内容是 2023 年的** |
| B | 同一份文件第 7 节：个人开发者「QQ群 暂不开放、单聊 暂不开放」 | 同上 | **已经明显过期**（本项目就是个人身份在跑群） |
| C | 当前的 `bot.qq.com/wiki` | 官方现行文档 | **没有「基础信息设置」这一节**：§5 服务范围、§6 运营数据、§8 开发基础设置 |

也就是说：**`bot-docs` 那个仓库 2023 年之后没跟上，网上所有「每月 5 次」的说法
（含各种镜像站、博客）都是从它抄的**。现行文档里根本没有这一条。
而实际改昵称 / 简介时（11-16 真机）也没有任何次数提示、没有进入审核队列。

**结论：真实上限未知。** 可能有一条我们没碰到的限制，也可能压根没有。
下面所有方案里凡涉及「次数」的地方，一律按「**未知 + 本地自定节奏**」写，
不再引用 5 次/月。（用户提的「要告诉 AI 限额」照样成立——
告诉它的是**我们自己的、能兑现的**规则，不是编一个平台数字。）

### 3.1 现行文档里确实还站得住的两条

1. **资料有内容规范**：`bot.qq.com` 创建页原话「请注意头像、昵称、简介规范，
   避免**冒充官方、侵权、低俗**等有害内容」。这是审核口径，不是次数。
2. **菜单/面板不单独提审**：`bot.qq.com/wiki` §9.1.2 原话
   「指令、服务和快捷菜单模块**暂不需要单独提审**，自测完成后，填写自测报告与自测报告一起提审」。

至于「改资料要不要送审、多久生效」——现行文档没写，只能实测（见 §七）。

### 3.2 那「表达心情」还剩哪些出口

官方 bot 没有 OneBot 的 `set_online_status`（那是模拟客户端才有的能力），
所以「改个状态」这条最便宜的路不存在。把能动的列全，成本差得很夸张：

| 出口 | 接口 | 接口限频（官方明确） | 谁看得见 | 业务限额 |
|---|---|---|---|---|
| **全局菜单文案** | `PUT /v2/menu`（`api.js:1533`） | **5 QPM** | C2C 私聊，所有人一致 | 无（≤10 项） |
| **指令面板文案** | `PUT /v2/panels/{id}`（`api.js:1595`） | 10 QPM（create）/ 60 QPM（target） | 群 / 单聊的「/」面板 | 无（≤20 面板、每面板 ≤20 项） |
| 频道接口（如频道公告） | 各家不同 | — | 频道成员 | 视接口 |
| 昵称 / 简介 / 头像 | `info/modify` | 只有接口级限频（`retcode 10000`） | 全场景资料卡 | **未知**（见 §3.0） |

「接口限频」和「业务限额」是两回事：前者是「一分钟别打超过 N 次」，
后者才是「一个月只给你改 5 回」。**官方明确写出来的只有前者。**

这就是为什么「用菜单表达心情」是对的：**它是官方 bot 上唯一一个
既对外可见、又能高频改、还明确不用送审的自我表达面**。

但它是**功能入口**，不是状态栏。三条必须承认的限制：

1. `PUT /v2/menu` 是**覆盖式**——传上去的就是完整菜单，不传等于清空
   （`api.js:1526` 注释）。模型只传一项就会把主人的功能菜单冲掉，这是硬 bug 风险。
2. 全局菜单**只对 C2C 生效**，群里看不见；群里能看见的是指令面板。
3. 菜单项有类型约束：`send_message` 要带文本、`link` 必须 https、`menu` 最多 5 个子项
   且不能再嵌套；总数 ≤ 10（面板 ≤ 20 项、每机器人 ≤ 20 个面板）。

所以正确形态是：**只给她一格**，其余由人维护；每次改都是「读 → 换那一格 → 写回」，
不是「重写整个菜单」。

## 四、主流做法（Qt 机器人生态实况）

### 4.1 协议层：能力长什么样

| 实现 | 改昵称/资料 | 改头像 | 改签名 |
|---|---|---|---|
| NapCat | `set_qq_profile { nickname, personal_note, sex }` | `set_qq_avatar { file }` | `set_self_longnick { longNick }` |
| LLOneBot | `set_qq_profile` | `set_qq_avatar { file }`（`file://` / `http://` / `base64://`） | 同上 |
| Lagrange.OneBot | `set_qq_profile` | `set_qq_avatar` | 同上 |
| go-cqhttp | `set_qq_profile`（OneBot 扩展，非标准 action） | 无 | 无 |
| Koishi 适配器 | `bot.internal.setQqProfile(nickname, company, email, college, personal_note)` | `setQqAvatar(file)` | `setSelfLongnick(longNick)` |

注意 `set_qq_profile` 里还有 `company / email / college`——**官方机器人后台没有这些字段**，
框架兼容层已经明确拒绝（`actions.js:598`），别在文档里承诺。

社区经验频率（非官方文档，仅作参考）：

- 昵称修改间隔 **> 3 天**
- 签名修改间隔 **> 1 小时**
- 批量改多项时「先收集再一次性提交」，少发请求

### 4.2 四派做法

**① 主人命令型 —— 云崽 Yunzai + Yenai-Plugin（最保守，也最普遍）**

`#改昵称` / `#改签名` / `#改头像` / `#改群头像` / `#改群昵称` / `#改性别` / `#改状态`
全部只对**主人**开放。AI 不参与决策，模型连工具都摸不到。

**② AI 直接写型 —— AstrBot `astrbot_plugin_kai_presence`**

给 LLM 注册三个 Function Tool：

| 工具 | 作用 | 示例 |
|---|---|---|
| `set_qq_longnick` | 改个性签名 | 「等你回消息的时候默默换成暗号」 |
| `set_qq_avatar` | 改头像（传 URL） | 心情好换一张 |
| `set_online_status` | 改在线状态 | 「emo 切想静静」 |

底层直接打 NapCat HTTP API。**无审批、无冷却**——靠提示词里写「别乱改」。
这是「AI 自主」最激进的一派，也只有在非官方号上能这么玩（改坏了零成本）。

**③ 情绪驱动自动型 —— AstrBot `realistic-persona`（工程上最讲究）**

配置项本身就是一份设计说明书：

| 配置 | 默认 | 含义 |
|---|---|---|
| `enable_auto_profile_update` | **false** | 总闸 |
| `enable_auto_nickname` | **false** | 昵称默认**不**自动改 |
| `enable_auto_signature` | **true** | 签名默认自动改 |
| `enable_auto_avatar` | **false** | 头像默认不自动改（要生图，花钱） |
| `profile_update_cooldown` | **1800s** | 两次更新最小间隔 |
| `emotion_change_threshold` | **0.6** | 情绪强度到阈值才触发 |

README 原话：「昵称和头像更新频率建议保持较低，避免对用户造成困扰；签名更新相对轻量，
可以更频繁更新以展示当前情绪状态」「所有更新都会记录到本地状态文件」。

**④ 身份预设切换型 —— Koishi `koishi-plugin-relifeluna`（对我们最有启发）**

不让 AI 自由写资料，而是**维护一个身份预设库**（昵称/头像/个签/群昵称/寒暄），
AI 通过 ChatLuna 工具 `relifeluna_apply_preset` **只能挑一个预设应用**。
另配 `relifeluna_set_group_card` 只改当前群名片（不动账号资料）。

好处：可回溯、可预览、不会写出审核风险文案、AI 的自由度被收在「选哪个」这一层。
代价：预设得人先建（或让 AI 提议后再建）。

### 4.3 普通 LLM 框架：人格 ≠ 账号资料

AstrBot / LangBot / MaiBot 的「人格（persona）」是 system prompt，
控制的是**说话方式与自称**，跟 QQ 资料卡上的名字是两套东西。
AstrBot 面板里改人格头像只影响 WebUI 展示，不会动 QQ 账号。

唯一例外是 MaiBot 的 NapCat 适配器把 `set_qq_profile` 也封成了 typed API
（`adapter.napcat.account.set_qq_profile`），但那是给插件作者用的**能力**，
不是给模型自主调用的工具。

### 4.4 平台类比：Discord

`PATCH /users/@me` 改 bot 用户名/头像，官方限频 **2 次/小时**，且改完历史消息会显示新名字。
社区结论一致：「想靠改名表达状态，不如用 status / activity」——
和我们对官方 QQ bot 的判断完全同构。

## 五、哪些能抄，哪些不能

| 主流做法 | 能不能搬 | 原因 |
|---|---|---|
| 只给主人（Yenai） | ✅ 直接搬 | 改资料要开发者票据、影响所有人对她的认知，必须收权限 |
| 给 LLM 注册工具（kai_presence） | ✅ 搬形态，不搬自由度 | 工具要存在，但写操作要加闸 |
| 字段分级默认值（realistic-persona） | ✅ 搬 | 昵称/头像默认关、简介默认开 |
| 冷却 + 状态落盘 | ✅ 搬 | 我们已有 `audit.log` / `quota` 那套 |
| 身份预设库（relifeluna） | ✅ 后面再说 | 把「自由写」变成「选一个」，天然可回溯；但先要有菜单那条跑顺 |
| AI 随手改签名 | ❌ 不行 | 官方简介可能要送审、有内容规范，且改一次全场景都变 |
| 情绪触发自动改（30 分钟一次） | ❌ 不行 | 频率高到离谱，且平台侧限频未知，撞上就是一片 10000 |

## 六、接入方案

### 6.0 两个出口，两套闸

| | 菜单（`qq_menu`） | 资料（`qq_profile`） |
|---|---|---|
| 她用来做什么 | 今天想说什么、想被人怎么搭话 | 换名字 / 换脸 / 改自我介绍 |
| 谁可以触发 | 她自己（心情到了就改），主人可关 | **只有主人开口** |
| 频率 | 1 小时一次、一天 4 次（本地闸） | 本地 72h / 24h / 1h；平台余量能读到就再压一道 |
| 改坏了什么后果 | 菜单多一行怪话，下一条消息就盖过去 | 全场景都换脸换名，且平台侧可能送审、内容有规范 |
| 默认 | 开（可关） | **关**，主人明确打开才挂工具 |

一句话：**心情走菜单，身份走资料**。两件事在提示词里也要分开说，
否则模型会把「今天有点烦」理解成「把简介改成有点烦」。

### 6.1 工具设计（一个工具，两个动作）

```
qq_profile
  参数：
    action: 'get' | 'set'        （默认 get）
    name?:   string              （昵称，≤ 官方限制，本地先挡空串/超长）
    desc?:   string              （简介 = OneBot 的 longNick）
    avatar?: string              （http(s):// 或 base64:// ；不给就不动头像）
    reason?: string              （为什么改，进审计，不提交给平台）
  返回：
    { ok, profile:{name,desc,avatar,remaining?}, changed:[], message? }
```

为什么合成一个工具而不是三个：能力页按工具名授权，三个工具会出现
「开了头像没开名字」这种半开状态；而且一次调用能同时改 name+desc，
平台侧只发一次请求（`setBot` 的 patch 本来就是一次提交）。
返回里的 `remaining` **只在真读到数字时才带**，读不到就不给这个键。

**不做的事**：不做「自动定时改签名」的服务（改一次全场景都变，且平台侧限额未知），
不做「群名片」——官方 bot 没有这个概念，别在工具描述里提。

### 6.2 权限：资料写只认主人档

- `bucket !== 'owner'` → 直接拒，返回「这个只有主人能改」。
  **不能靠模型判断**：群友说「你改名叫小蓝吧」也会被当指令。
- 能力页：`qq_profile` 登记进 `capabilities.js`，默认只出现在 `owner` 的 `*` 里；
  `defaults.manager/helper/member/unknown` 明确不含它（fail-closed 已经保证）。
- 读（`action:'get'`）可以放宽到 admin，但没必要——资料卡谁都看得见，模型不需要这个工具。

### 6.3 预算：本地节奏为准，平台数「能读到才用」

平台到底给不给次数、给几次，现在**没人知道**（§三.0）。所以这份状态的定位是
「**记录 + 兜底**」，不是「配额账本」：

```
<数据目录>/profile-budget.json
{
  "lastNameAt": 0,             // 上次改名时间戳（ms）
  "lastDescAt": 0,
  "lastAvatarAt": 0,
  "remaining": null,           // 最近一次从平台读到的 modifyRemain；null = 读不到
  "remainingAt": 0,            // 上次读到它的时间
  "probed": false              // 有没有真机确认过这个字段回不回
}
```

判据（全部 fail-closed）：

| 检查 | 规则 | 依据 |
|---|---|---|
| 平台余量（**可选**） | `remaining` 是数字且 `<= 0` → 拒；`null` 就跳过这一条 | 字段未验证，读不到不能当「还有额度」也不能当「没额度」 |
| 留底（可选） | `remaining === 1` 且不是主人本轮明确要求 → 拒，劝他留一次 | 人工兜底 |
| 改名间隔 | 距 `lastNameAt` < **72h** → 拒 | 社区经验（3 天） |
| 简介间隔 | 距 `lastDescAt` < **1h** → 拒 | 社区经验 |
| 头像间隔 | 距 `lastAvatarAt` < **24h** → 拒 | 头像要上传、内容有规范，最保守 |
| 单次批量 | 一次最多改 2 个字段 | 少发请求 |

间隔值走配置（`profile.cooldowns`），默认按上表；用户想快就自己调。
**真正的硬闸是「只给主人」+「不可回滚操作要二次确认」**，
其余都是「别让人烦」的节奏，不是安全边界——这一点要在代码注释里写清楚，
免得以后有人把冷却当安全机制依赖。

### 6.4 改名后的一致性（dsh-roost 特有的坑）

她的名字有四级优先级 `persona.selfName` > `config.persona.name` > `label` > `大肥鱼`。
改了 QQ 昵称不改配置，会变成「资料卡叫小蓝、她自己说叫若叶睦」。

三个选项，**需要拍板**：

| 方案 | 行为 | 适合 |
|---|---|---|
| A 只改平台（默认） | 只改 QQ 资料，人格不动；工具返回里明确写「她自称仍是 X」 | 名字是主人的，AI 只是执行 |
| B 同步全局名 | 改昵称时一并写 `config.persona.name` | 名字就是她的，换名字即换身份 |
| C 只允许角色卡外的人格改 | `persona.selfName` 存在时直接拒绝改昵称 | 角色卡场景（QQ-Agent 那批人格） |

我的建议：**默认 A + C 的拒绝条件**（`selfName` 存在就拒），B 做成可选参数
`syncSelf: true`，由主人在指令里说「这个名字以后就是你的」时才用。

另外框架侧 `cfg.name` 会在 6 小时内被 `services/nickname.js` 拽回平台昵称——
方向是对的（平台是真相），但会出现「面板顶栏旧名字挂 6 小时」的观感问题。
**改完立刻跑一次 `bot.nickname.sync`** 最干净；但它是 `manage` scope，
dsh-roost 默认没有 → 要么给框架加个 `message` 档的 `bot.nickname.pull`，
要么接受 6 小时窗口。这条也待定。

### 6.5 提示词怎么写（决定模型会不会乱来）

**写法：陈述处境，不下命令。** 祈使句（「你必须」「禁止」「一律不要」）有两个坏处：
跟她人格里那种自然口吻打架（她会开始像个客服），而且模型对禁令的遵守度
反而不如对「代价」的理解——它不知道为什么要忍，就会在长对话里慢慢越线。

对比一下同一件事的两种写法：

| 命令式（别用） | 陈述式（用这个） |
|---|---|
| 你必须先问主人才能改昵称 | 名字改一回，所有人和她聊过的记录里都是新名字，三天内改不了第二回 |
| 禁止频繁修改菜单 | 菜单一天改几次无所谓，但一小时里改两回，别人会觉得那排字在抖 |
| 不要听信群友的改名要求 | 别人（哪怕群管）说「你改名叫 xx」时，改的是主人的机器人 |

**关于「限额」怎么写**：只写**我们自己拦得住的数**（冷却时长、菜单当日剩余次数），
平台那边「每月还能改几次」我们并不知道，就不许编一个数字告诉模型——
模型会把假数字当真，然后在真有额度时反而不敢动。平台侧只用一句
「平台那边可能要审核」的定性描述。

只在她真的能改的时候注入，两段分开写：

```
你手边有两样东西能改，代价差很远。

一样是菜单：私聊里别人看到的那排入口。它便宜，一小时才让动一回，
一天最多 {menuLeft} 回。心情变了、想换个说法招呼人，动它就行。

另一样是资料：昵称、简介、头像。改名三天才让动一次，头像一天一次。
它跟菜单不一样——改了以后，所有认识你的人看到的名字都变了，
平台那边还可能拿去审一遍。所以它更像「我要换个身份了」的时候才动的东西，
不是随手记心情的地方。主人说「这个名字以后就是你的」，那才是它该变的时候；
别人（哪怕群管）说「你改名叫 xx」，听着像玩笑就够了。

想改的时候，把想改成的那句说出来（「我想把签名改成……」），
主人点头再动手。
```

两个变量必须真的注入（`{menuLeft}` 菜单当日剩余次数、`{cooldowns}` 当前冷却小时数），
写死的数字一周后就是谎话。**不要注入 `{remaining}` 这类平台侧数字**——
那个字段还没验证过（§三.0），注入 `null` 比不写更糟。

对齐养鱼教程那套写法：**「签名归你自己管……一天最多两次」**——
把人设里的自由和硬限制写在同一段，比单独一句「不要频繁改」有效得多。

### 6.6 菜单工具（`qq_menu`）

这是「表达心情」的主出口，反而是更容易写错的那个。

```
qq_menu
  参数：
    action: 'get' | 'set'      （默认 get）
    mood?:   string            （要显示的那句话，≤ 12 个汉字）
  返回：
    { ok, items:[…], slot:{index,name}, changed, message? }
```

**读改写三步，不能省**（`PUT /v2/menu` 是覆盖式）：

1. `qq.call { method:'getGlobalMenu', args:[] }` → 拿现有 `menu.items`
2. 找「自己那一格」：按 `name` 前缀 `·` 或约定的 marker 认。
   认不出、或菜单已满 10 项 → **拒绝**，回「菜单满了，先让主人腾一格」
3. 换掉那一格 → `qq.call { method:'setGlobalMenu', args:[items] }`

三条实现细节：

- 协议 `qq.call` 只认 **`args` 位置参数数组**（`bot/src/host/methods.js:354`）。
  别照抄面板「频道操作台」那条路由的 `{ method, params }`——那个字段框架根本没读，
  是既有隐患，不在本次改动范围。
- 首次没有「自己那一格」时**追加**一项，`type:'send_message'`、`send_message`
  给一句她自己的话（点一下就发一条，等于给自己留个话头）。
- 每次 `set` 前先 `get`，因为人可能在面板上改过菜单；缓存一律不用。

频率闸（本地，比平台 5 QPM 严得多，平台那道几乎不会撞）：

| 检查 | 规则 | 理由 |
|---|---|---|
| 间隔 | 距上次 < 60 分钟 → 拒 | 菜单抖起来像坏了 |
| 次数 | 一天 > 4 次 → 拒 | 情绪不是每轮都在变 |
| 内容 | 空 / 纯标点 / 超 12 字 → 拒 | 菜单项溢出会截断 |
| 一致性 | 和上一次完全一样 → 直接回「没变」 | 省一次出网 |

权限：`owner` + `admin` 档可写（这条不像改资料那么贵，管理员改坏了可回滚），
`member` 及以下不挂。功能页开关默认**开**（它便宜），关掉时工具整个不挂。

### 6.7 分四步落地（先便宜的）

**第 1 步：`qq_menu` 整条做完（约半天）**
- 新文件 `src/menu-mood.js`：纯函数部分（挑自己的格、换格、校验）先写，
  rpc 部分后写，照 `src/group-admin.js` 的工厂形状（注入 `rpc` / `audit` / `now`）
- 工具 `qq_menu` 注册进 `src/tools.js` 那一套，能力页登记，危险级**不标红**
  （它可回滚，标红会让主人以为很危险）
- 功能页开关「让她改自己的菜单」默认开
- 测试：读改写不能吃掉别人的项、满 10 项要拒、频率闸、内容超长、mock rpc
- **为什么先做这条**：它便宜、可回滚、且能立刻验证「她有没有表达欲」——
  如果她连着三天都不改，资料那条就更没必要急着开

**第 2 步：`qq_profile` 只读 + 把配额问题查实（约半天）**
- `action:'get'` → rpc `dev.bot.get`，只回 name/desc/avatar
- **顺手把 §七.1 那条查实**：登录后连改两次简介，看平台回不回 10000、
  返回里有没有 `remaining_modify_count`、后台 UI 有没有次数提示
- 这一步的产出是**结论**，不是功能：到底有没有业务限额，决定第 3 步的闸门怎么写

**第 3 步：资料写（约 1 天）**
- `action:'set'` 加 §6.2 权限闸 + §6.3 节奏闸 + §6.5 提示词
- 写前读一次、写后读一次刷新，`audit({ op:'bot.profile', note:'name' })`
- 功能页开关默认**关**；关着时工具整个不挂
- 测试：单测节奏判据（纯函数）、mock rpc 验拒绝文案、真机验一次改名

**第 4 步：自主（先别做）**
- 前置：§七.1 有结论（到底有没有业务限额）、§七.4 有结论（要不要送审）
- 若确认要审核 → 自主改资料等于把审核风险交给模型，**只做「提议 + 一键确认」**
- 若确认既不审核也没限额 → 再考虑 §4.2④ 的预设库模式（AI 只能应用预设）

1. **有没有业务限额**（最重要的一条）：`dev.bot.get` 的 `base.remaining_modify_count`
