## 0. 先回答「AI 能知道自己回了什么吗」

**日记里能，账本里不能。**

| 层 | 出站（AI 自己说的话） | 入站（别人说的） |
|---|---|---|
| 事件账本 `events.db` | **没有**。`bot.js:830` 的 `ledger.append(msg)` 是全仓唯一调用点（插件拿到的是 `readOnlyLedger`，`plugin/context.js:21`），`outbound.js` 零接入 | 全量，含没触发 AI 的 |
| 日记 `journal.sqlite` | **有**。`journal-bridge.js` 每轮写两条：`role='user'` 和 `role='bot'` | 只记触发过回复的 |

而且日记**已经能被读**：`memory_search`（`tools.js:159`）读的就是它，
`scope:'global'` 还早就支持跨会话（`canCrossGroup()`，owner/admin 可用）。
所以这次要做的不是「把日记接上」，是补两个它给不了的东西：

1. **时间线视图**。`memory_search` 是关键词检索（给几个词，命中几条摘要），
   回答不了「这个群刚才在聊什么」——后者要的是「按时间倒序取最近 N 条」。
2. **会话清单**。模型手里没有 chatId，得先能列出「有哪几个群、分别叫什么」。

实测（2026-11-05 真机库）：

| 会话 | 账本入站 | 日记 `role='user'` | 日记 `role='bot'` | 日记 `role='digest'` |
|---|---|---|---|---|
| `55597677`（机器人测试） | 97 | 147 | 147 | 5 |
| `F1F759AD`（roost交流群） | 329 | 63 | 59 | 3 |
| `CBF1E6B3`（私聊） | 21 | 21 | 21 | 3 |

`role='digest'` 是巩固写的摘要行（`consolidate.js:288`），`kind` 也是 `'digest'`，
和对话行分开算——`recent` 视图要把它排掉或单独标出来。

两个方向都有差，原因不同，都直接影响工具怎么用：

- **账本 > 日记**（群 329 vs 63）：账本记的是「发生过的事实」，**每一条入站都记**；
  日记只记「被转发到宿主、真的跑了一轮」的那些。想回答「群里刚才谁在聊什么」，只能查账本。
  **进日记的判据不是「有没有 @ 她」**（这点容易想当然，实测不成立）——
  默认 `decide: 'ai'` 时非 @ 消息也会被转发，日记里大量是普通闲聊
  （例：「哈哈哈哈哈，感觉糊糊的」「搓了一个识图+视频抽帧的插件」）。
  真正决定进不进的是 ai-chat 的几道闸门（`ai-chat/index.js:1075` 起）：

  | 闸门 | 位置 | 挡掉什么 |
  |---|---|---|
  | `shouldConsider` | `decide.js:86` | 空消息、`ignoreWords` 前缀（像是别的插件指令）、`decide:'mention'` 模式、每分钟回复数用满（默认 3） |
  | 情绪闸门 | `index.js:1088` | 社交意愿 `sociability < 0.4` 时**只接 @ / 回复**（`gate.force`） |
  | 合并窗口 | `merge.js:16` | 1.5 秒内连发合成一轮（多条消息 → 一条日记） |
  | ai-chat 自己的忙态 | `index.js:1144` | `paceSt.busy` 时**直接 return，静默丢弃**，不排队也不提示 |

  实测比例：群 `F1F759AD` 在 11-02 有 184 条入站，日记只有 24 轮（13%）；
  按人看也不是白名单（`倦飞之鸟` 103 → 16，`π` 19 → 0）。
  差额的确切归因还没定论——已排除合并窗口（相邻 <1.5s 的只有 6 对）、
  每分钟配额（24 轮/天远低于 3 条/分）、当前情绪（0.519 > 0.4）。
  最可能是 `paceSt.busy` 的静默丢弃，但这需要另开一次排查，不影响本方案的结论。

- **日记 > 账本**（`55597677` 的 147 vs 97）：**账本按 7 天滚动删除，日记不删行**。
  `ledger.js:330` 的 cutoff 是精确毫秒（`Date.now() - retentionDays*86400000`），
  但 `prune()` 由每小时一次的 `setInterval` 触发（`ledger.js:161`），所以边界最多滞后 1 小时。
  日记只把 `normal`/`important` 的 `digest` 压缩掉，`text` 永不改写、行也不删。
  实测按天（口径：`55597677` 单会话）：10-28 日记 34 / 账本 0，10-29 日记 58 / 账本 21（11:2x 时点，随 prune 漂）。

所以两份数据不是重复，是**互补**：

| 想知道 | 该查 |
|---|---|
| 群里刚才谁在聊什么（含没叫她的） | 账本 |
| 她和某人的对话来回（含她自己说的） | 日记 |
| 她主动搭话说过的（上下文早压缩掉了） | 日记 `role='bot'` |
| 原文（日记会压缩成 digest） | 账本 / 日记 `text`（`text` 永不改写） |

Part A 补的正是账本缺的那一半出站，让账本也变成完整往返。

## 1. 为什么是工具，不是注入

注入（每轮把群聊近况塞进提示词）的问题：① 每轮都花 token，哪怕九成轮次用不上；② 塞多少都是拍脑袋；③ 主人私聊注入群聊 = 强制串场，普通用户没得选。

工具是「要用才查」：模型自己判断「他说的那个群的事我不清楚」→ 调一次 → 拿到摘要。九成轮次零开销。DSH 已有 `memory_search` 的同款先例（检索式而非注入式），行为模式模型已经会了。

`roost_skill`（能力页方案 P5）也能承载这件事，但还没实现，不搭这趟车；等它落地后这个工具可以平移成技能，不冲突。

## 2. 数据怎么拿到

### 2.1 三个源，各有各的用

| 源 | 位置 | 打开方式 | 用途 |
|---|---|---|---|
| 日记 `journal.sqlite` | `~/.dsh/dsh-roost/journal.sqlite`（`DSH_ROOST_DATA` 可覆盖） | `DatabaseSync(file, {readOnly:true})` | 可选源（`source:'journal'`）：对话流、人话、含 bot、**长期不删** |
| 会话映射 `sessions.json` | 同目录 | 已有 `sessions.entry(chatId)`（同步） | 补群名、判 kind |
| 账本 `events.db` | `join(roostDir, 'data', 'bots', botId, 'events.db')` | 同上 | **默认源**：原文、全量事实（含没触发 AI 的） |

- 真机实测：`readOnly` 打开 WAL 库正常（两个库都试过，WAL 有未 checkpoint 的数据也能读到）。
- 日记没有 sqlite 时（Node 22.0~22.4）会回落 JSONL（`journal.js` 头部注释），
  那种情况下**不注册工具**，面板上看不到它，不报错不吵。
- 账本同理：找不到库 / 打不开 → 该源不可用，`source:'ledger'` 时明确回一句「账本没开」。

**目录别用 `dataDir()`**：`config.js:15` 的 `dataDir()` 里有 `mkdirSync`，
一个只读工具不该顺手建目录。用 `process.env.DSH_ROOST_DATA || join(homedir(), '.dsh', 'dsh-roost')` 直接拼。

**两个库不在同一个目录下**（初稿含糊带过，容易写错）：

| 库 | 位置 | 来源 |
|---|---|---|
| `journal.sqlite` | `dataDir()/journal.sqlite`，默认 `~/.dsh/dsh-roost/` | `host.js:1050` |
| `events.db` | `<roost 安装目录>/data/bots/<botId>/events.db` | `bot/src/paths.js:148` |

真机印证：`Desktop/工具/qq-bot-roost/data/bots/main/` 里只有 `events.db / stats.db / groups.json`，
`journal.sqlite` 在 `~/.dsh/dsh-roost/`。**别想着「一个目录取两个库」**。

**`resolveRoostDir()` 不可导入**：它是 `setup.js:324` 里 `createSetup` 的**内部闭包**。
`setup.detect()`（`setup.js:393`）能拿到 `{ dir, bots }`，但它内部会 `isRunning()` 打一次
1.5 秒超时的 HTTP（`setup.js:404` → `:384`），**不适合放进工具热路径**。

最省事的写法：直接读 `cfg.setup.roostDir`（真机已配 `C:\Users\q9079\Desktop\工具\qq-bot-roost`），
为空再退 `join(dataDir(), 'roost')`。零网络、零依赖。

**不走 HTTP 的原因要换**：初稿说「面板 API 要额外配地址 + token」，这个理由是错的——
`setup.baseUrl()` + `setup.keyQuery()` 是现成的，`contextOf()`（`host.js:1265`）已经在生产里用。
真正的理由是**路由不够**：ai-chat 暴露了五条（`/r/context` 按 eventId 取邻文、`/r/send`、
`/r/reply`、`/r/delivery`、`/r/status`），其中四条是写操作或单点查询，
**没有「按会话取最近 N 条」和「列活跃会话」**。为两个只读查询新开路由、还要跟着 ai-chat 一起发版，
不如直接读库。

**schema 耦合的代价要认**：

- 日记只用 `chat_id / role / sender / text / digest / at / level / kind / event_ids`，
  `journal_chat` 索引正好是 `(chat_id, at)`，按会话取最近 N 条是索引扫描；
- 账本只用 `seq / kind / chat_id / user_name / content / at / time_basis` 七列。
  但 `events-schema.js` 里**只有 `content` 有「正文独立列」的明确承诺**，
  其余列靠 `EVENTS_SCHEMA_VERSION` 迁移——改 schema 时要人工核一遍这里，没有约定替你兜。

### 2.2 内容要洗一遍（但不是洗尖括号）

实测账本 `content` 的真实形态（447 条里）：

| 类型 | `content` 实际值 | 条数 |
|---|---|---|
| 表情 | `<faceType=1,faceId="124",ext="eyJ0ZXh0IjoiT0sifQ==">` | 39（全库唯一带尖括号的） |
| @ 某人 | 正文照旧，`<@OPENID>` 已被 `message.js:236` 的 `stripMention()` 剥掉，原文只在 `payload.content` | 63 条带 mentions，其中只有 1 条没有正文 |
| 图片 / 文件 | 有文字时保留文字，纯图时**空串**，附件在 `payload.attachments` | 49 条带附件，其中 28 条没有正文 |
| 纯文本 | 正常 | 其余 |

**全库 `content=''` 共 29 条（6.5%）**：28 条带附件、1 条带 mentions、0 条两者都无。
也就是说「空」的成因只有「纯图」和「纯 @」两种，没有第三种。
而 `[图片]` / `[表情]` 这类占位符**一条都没有**。

所以清洗规则要这么写，不能照初稿「去掉 `<...>`」了事：

1. 去 `<faceType=...>` 这类表情标记（这是唯一真实存在的尖括号形态）；
2. **别按 `<@...>` 去洗**——账本列里早就没有了，写了是空转；
3. **只有 `content` 为空时才回落**到 `payload`（有文字时别覆盖）：有 `attachments` 出「（图片）」，
   有 `mentions` 出「（@某人）」——否则时间线里会出现 29 行「`[11:20] 倦飞之鸟: `」。

日记的 `text` 已经是人话，`source:'journal'` 时不经过这一步。

## 3. 工具形状

```
chat_look
  what: 'recent' | 'chats'     默认 recent
  chatId: string               不传 = 当前会话；传了要过隐私判定
  limit: number                recent 条数，默认 20，上限 50
  cursor: string               翻页游标（上一页最后一条的不透明串）
  source: 'ledger' | 'journal' 默认 ledger；journal = 长期/摘要视图
```

**为什么 `source` 是枚举而不是 `raw: boolean`**：布尔参数只能表达「是不是原始数据」，
模型得先理解「raw 指什么」才能选；而且以后再加第三个源（比如 transcript）就要再加一个参数。
枚举是封闭的、自解释的，加源时改枚举值即可，工具签名不变。

**默认 `ledger` 的三个理由**：

1. 用户最初的需求是「私聊时知道群里**刚才**聊了什么」，只有账本记全量——
   群里没 @ 她的消息不进日记（实测群 329 条 vs 日记 63 条）；
2. Part A 落地后账本是**唯一完整往返**（入站 + 出站），日记那份出站就成了冗余副本；
3. 默认路径只跑一套 SQL、一套清洗、一种游标，日记那条是可选分支——
   两条默认路径语义不同，是最难查的一类 bug。

**日记仍然保留，因为它有一个账本永远补不上的能力：长期。**
账本 7 天滚动删除（`ledger.js:330`），日记不删行、只压 `digest`。所以：

| 想知道 | 用哪个源 |
|---|---|
| 这个群刚才在聊什么（含没叫她的） | `ledger`（默认） |
| 一周前/更早聊过什么（只要触发过她） | `journal` |
| 她以前回过什么（A 落地后） | `ledger` |
| 她以前回过什么（A 落地前） | `journal` |

- `recent`：按时间**正序**输出，格式 `[HH:MM] 名字: 内容`（内容截 200 字）。
  注意底层是 `ORDER BY … DESC` 取最近 N 条，**要 reverse 之后再输出**。
- 日记源下 `role='bot'` 显示为机器人自己的名字，就是完整往返；`role='digest'` 标成「（摘要）」
  或者直接排掉（它不是对话，是巩固写的摘要行）。
- **日记的 `role='user'` 行不是「某人说的原话」**，是「这一轮投给模型的整段输入」：
  `host.js:2986` 的 `journalAdd(payload, chat, text, 'user')` 里的 `text` 已经拼进了开场白、
  自述、记忆注入块。实测 63 行里有 9 行以「【你自己最近写下的】」开头，最长 377 字。
  更麻烦的是**主动搭话 / 觉醒的轮次也写在这里**——有几行的 `at` 在账本里根本找不到对应的入站消息。
  所以日记只能当「她的视角」，**不能当聊天记录**；`source:'journal'` 的输出要剥掉这些块，
  或者干脆只在「查她自己说过什么」时用。这也是默认走账本的原因之一。

  **这处有现成的一行修法**：`host.js:2900` 已经有 `const said = text;`（注释原话
  「用户原话的副本。发送者标签要贴在**它**前面，而不是整段正文最前面」），
  把 2986 的 `text` 换成 `said` 即可——自述和开场白就不再被当成「用户说的话」记进日记。
  不改的话，`memory_search` 会命中自述块，然后下一轮再把命中的自述注入回去，
  形成「她自己的旁白被当成聊天记录」的循环。属于记忆系统的问题，**不在本方案范围内**，
  但和 `chat_look` 的 `journal` 源直接相关，建议同批修。
- **user 行在模型调用之前就写了，所以「她没说话」的轮次也有 user 行**。
  `host.js:2986` 在 `turns.run` 之前，注释写明「即使这一轮请求失败了，'他说过这句话'这件事仍然发生过」；
  而 `bot` 行只在真正说出话之后才写（`host.js:3171` / `3196`），`<skip>` 那一支明确不写
  （`host.js:3192` 的注释：「这一支不写日记：她一个字都没说」）。
  实测群里 63 条 user 行只对应 59 条 bot 行，4 条孤儿就是「接了但没说」——
  **进不进日记跟模型的决定无关，模型只决定有没有 bot 那一行**。
- **日记源必须过滤 `text === ERASED || text === CLEARED`**（`journal.js:48-49` 的两个占位符）。
  现有的 `listChat` **不过滤**它们（只有 `digests()` / `byDay()` 过滤，`journal.js:530/1353`），
  不加这道的话，用户明确要求「忘掉」的内容会以「（已按用户要求遗忘）」重新出现在时间线里。
- **`listChat` 根本不在对外门面上**（初稿写「调 `journal.listChat`」是错的）。
  `journal.js:1249` 起的门面只有 `recent / byDay / scanChats / top / digests / search / remove / purgeChat …`，
  `listChat` 是两个**内部 store** 的方法（SQLite 在 `:542`、JSON 在 `:971`），而且**没有游标参数**。
  所以「按会话取最近 N 条 + 翻页」要**新增**：门面 1 处 + 两个后端各 1 处，共 3 处。
  现成的 `recent(chatId, n, kind, aliases)` 也没有 before/cursor，只能取「最近 N 条」，翻不了页。
- **`chatId` 为空直接拒绝**。`listChat('')` 内部会退化成全库查询（`journal.js:542` 的
  `keys.length ? … : 'SELECT * FROM journal'`）；删除类操作有 `requireChat()` 硬拦（`journal.js:1161`），
  **读类没有**。`chat_look` 站在隐私边界上，必须自己再加一道。
- `chats`：最近活跃会话列表，**带真名**：

  ```json
  [{ "chatId": "F1F759AD…", "name": "roost交流群", "kind": "group", "lastAt": "…", "count": 329, "preview": "…" }]
  ```

  初稿说「不做群名映射表，靠预览让模型认群」——这条放弃了一个现成能力。
  `sessions.entry(chatId)`（`sessions.js:54`）同步返回 `{sessionId, preset, title, kind, at}`。
  实测 `sessions.json` 的 title 是 `QQ · 机器人测试` / `QQ · roost交流群` / `QQ · 私聊 FC7BB5` /
  `QQ · 巩固` / `QQ · 私聊 lftest`——**都带 `QQ · ` 前缀**，输出前剥掉。
  （`selftest` 是 chatId 的键名，不是名字，别当示例。）

`cursor` 故意做成不透明字符串：日记按 `(at, id)` 翻页，账本按 `seq` 翻页，
两个源的游标形态不同，暴露成两种参数等于把实现细节写进工具协议。

## 4. Part A：出站入账（框架仓，`douluo/bot`）

### 4.1 接线点：四处，不是一处

初稿写「只改 outbound.js 一处 hook」。审校后确认**必须四处**，其中前两条不改就等于没做：

| 位置 | 改什么 | 不改的后果 |
|---|---|---|
| `host.js:3172 / 3193 / 3195 / 3316`（dsh-roost） | `postReply` 补 `{requestId}` | **主回话不入账**（见 4.2） |
| `bot.js:289` 附近（`this.ledger.open()` 前后） | `this.outbound.ledger = this.ledger` | **拿到 `undefined`，静默零记录**（见 4.3） |
| `outbound.js:249` | 构造函数加 `ledger = null` | 无处可写 |
| `outbound.js:358` | settle 成功后入账 | — |

### 4.2 主回话为什么进不了 settle

`postReply(payload, text, done = true, extra = {})`（`server.js`）只把 `extra.requestId` 透传进报文，
而 dsh-roost 的主回话路径全部是**三个参数**：

```js
3172: await postReply(payload, '', true);            // 空回复
3193: await postReply(payload, '<skip>', true);      // 跳过
3195: await postReply(payload, reply, true);         // ← 最常见的正常回话
3316: await postReply(payload, friendly, true);      // 出错时的兜底话术
```

`adapter/bridge.js:158` 拿到的是 `String(body.requestId ?? '')` → 空串，
`outbound.js:320` 于是 `if (!requestId || !this.delivery) return this.#sendOnce(opts)`，
**根本不进 claim / settle**。

也就是说：模型自己说的一句话（最常见的一轮）在账本里一条都不会有，
只有它主动调 `qq_send` 分段说话时才记。「账本 = 完整往返」不成立。

修法：这四处补 `extra.requestId`，用能天然幂等的派生键，例如
`` `${payload.id}:main` `` / `:err`（`:empty` / `:skip` 不需要，见下）。

`payload.id` 是 `evt_${randomUUID()}`（`adapter/bridge.js:40`），语义要说准：
**一轮之内稳定**——同一轮里多次 `postReply` 共用一个 id，所以本轮内的 HTTP 重试是幂等的；
**跨轮会变**——同一条 QQ 消息被重新处理就是新 id，所以不会误 reuse 掉新消息。
（初稿写「同一条消息重试不变」不准确，方向对但论据不对。）

**必须写死一条不变式**：`delivery.claim` 对 `SENT` / `AUDITED` **一律返回 `reuse`、不比较正文**
（`delivery.js:120`），所以——

> 一轮之内，每个派生键最多发生一次**非空** `postReply`；新增回话点必须换后缀。

违反的后果是**静默丢消息**：第二次带不同文本调用会被当成「已经发过」直接返回，不报错。
现有四处恰好互斥（`host.js:3168` 的 `if / else if / else`），一轮只有一个非空回话，
所以安全；但这是靠结构偶然成立，不是靠约定。

两个后缀是空转，不必加：空文本（`host.js:3172`）在 `bridge.js:148` 就 `if (text)` 被跳过，
`<skip>` 在 `index.js:1306` 早退，两者都到不了 `sendReply`，更不会 settle。
注意 `qq_send` 那条路已经在 `host.js:2154` 传了 `opts.requestId`（`qq-tools.js:289` 生成的 `qs-...`），
不用动。

**这条改动在 dsh-roost 仓**，不在 bot 仓。所以 Part A 实际横跨两仓，
「A 先发版、B 后做」的顺序要改成「dsh-roost 补 requestId 不晚于 bot 1.0.4 上线」（见 §8）。

### 4.3 为什么不能走构造函数传 ledger

`bot.js:193` 的 `new Outbound({...})` 里没有 ledger，而 `this.ledger = createLedger(...)`
在它**之后**才执行（账本要等 `paths.events` 就绪）。照初稿「`bot.js:193` 传 `ledger: this.ledger`」改，
拿到的是 `undefined`，`send()` 里 `if (!this.ledger) return` 直接跳过——**不报错，只是永远不记**。

同文件已有正确范式，照抄即可：

```js
278: if (this.outbound) this.outbound.delivery = this.delivery;   // ← 后置注入
```

注释写的就是「outbound 在更早的地方构造好了（它不依赖库），这里补上引用」。
ledger 走同一条路：`this.outbound.ledger = this.ledger`，放在 `createLedger` 之后。

### 4.4 字段映射

| events 列 | 取值 | 备注 |
|---|---|---|
| `kind` | `opts.kind` | group / c2c |
| `chat_id` | `opts.target` | 群 openid 或对方 openid，与入站口径一致 |
| `user_id` | 机器人自己的 openid | **`api.getMe()`（`api.js:228`）首次成功时缓存**，进程内一份；拿不到存空串 |
| `user_name` | 机器人昵称 | 同上 |
| `content` | `digestTextOf(opts.payload)` | 现成函数（`outbound.js:228`），媒体/卡片有占位 |
| `msg_id` | 响应 `r.id` | |
| `msg_idx` | 响应 `raw.ext_info.ref_idx` | `#post` 已把 `raw` 带出来（`outbound.js:547`），`send()` 也原样透传 |
| `at` | 发送时刻 | 我们自己的钟，可信 |
| `time_basis` | `'observation'` | 传 `append(msg, {timeBasis:'observation'})`；此时 `at` 取本地时刻（`ledger.js:197`） |

| `plugin` | 见 §4.4.1 | **新增列**（schema v3），谁说的 |

两处已知缺口，实现时按这个写：

- **`getMe()` 不能阻塞发送**：它是网络调用。按「账本绝不影响主链路」的原则，
  第一次入账时 `user_id` 先存空串，`getMe()` 成功后再补（或者干脆接受空串——
  出站记录的 `user_name` 只在时间线里显示，日记那边本来就显示机器人名字）。
- **`reuse` 分支拿不到 `raw`**：`outbound.js:331` 返回 `{id, reused, pending, requestId}`，没有 `raw`。
  命中重放时 `msg_idx` 会是空——可接受（重放说明这条已经发过，账本里该有那一行）。

### 4.4.1 插件归属：谁说的这句话

用户提的需求：ai-chat 读账本时，应该知道哪条回复是哪个插件发的。

**好消息：框架里早就有这个信息，只是账本没记。**

- `msg.pluginId` / `msg.pluginName` 由 `bot.js` 在**调用插件之前**设好
  （命令在 `bot.js:965`，监听器在 `bot.js:1023`）；
- `msg.reply()`（`message.js:495`）已经把它们压进 `replyBuf`，
  用来在**多插件合并回复**时加 `【插件名】` 标题（`message.js:555`）；
- 所以出站路径上拿得到 id，不用新造概念。

**但要先认一件事：一条出站消息可能属于多个插件。**

`msg.flushReplies()`（`message.js:533`）会把同一轮里多个插件的回复合并成一条发出去，
正文用 `【回声】\n…\n\n【AI 对话】\n…` 分隔。所以 `plugin` 不能是单值：

| 场景 | 值 |
|---|---|
| 只有 ai-chat 回 | `ai-chat` |
| 回声 + ai-chat 合并回 | `echo,ai-chat`（去重、逗号分隔） |
| 框架内部直发 | 空串 |
| 入站消息 | 空串（不是插件发的） |

用逗号分隔而不是 JSON 数组：能直接 `LIKE '%ai-chat%'` 过滤，SQLite 也不需要 JSON1 扩展。
（本项目已经在用 `node:sqlite`，JSON1 是有的，但一个字符串够用，别为它写解析。）

**注入点三处**：

| 位置 | 怎么拿 |
|---|---|
| `msg.flushReplies` | `items` 里每条都有 `pluginId` → `[...new Set(items.map(i => i.pluginId).filter(Boolean))].join(',')`，随 `send()` 传下去 |
| `ctx.push`（`plugin/context.js:858`） | `createContext({ meta })` 里就有插件 id → 直接 `plugin: meta.id` |
| `outbound.send` 的直接调用方 | 没有就留空，不猜 |

**读取侧**：`readOnlyLedger` 的 `recent` / `timeline` / `get` 把 `plugin` 带出来，
`recent({ plugin })` 加一个可选过滤。ai-chat 就能回答「这条是别的插件说的，不是我」。

**时序上必须并进 Part A，不要单独发一版**：
加列要 `ALTER TABLE` + 升 `EVENTS_SCHEMA_VERSION`（现在是 2 → 3），
分两次做等于两次迁移、两次发版、两次兼容测试。Part A 本来就要动 `outbound.js` 的入账，
一次做完。

**和 `trace` 列的分工**：`trace` 是「哪一次请求」的链路 id（v2 加的），
`plugin` 是「哪个插件」。两者不重叠——同一个插件可以有多条 trace，
同一条 trace 里合并回复又可能来自多个插件。

### 4.5 去重：用 `msg_id`，不用 `out:${requestId}`

初稿写 `dedupe = out:${requestId}`，**传不进去**：`append()`（`ledger.js:184`）只收 `{timeBasis}`，
`dedupe` 是它自己算的（`ledger.js:202`）：

```js
const dedupe = msgId ? `${this.botId}:${msgId}` : `${this.botId}:${msg.chatId}:${at}:${digestOf(msg)}`;
```

有 `msg_id` 就用它——出站响应本来就带 `r.id`，天然唯一，**不需要 `out:` 前缀，也不需要改 `append` 签名**。
真正保证「一个 requestId 只记一次」的是 claim 状态机：`send()` 里 `reuse` 分支
（`outbound.js:331`）直接返回、不调 settle，所以入账只会走一次。

`r.id` 为空时退化到指纹（`at` 毫秒级），同一毫秒同内容同会话才会撞——代价可接受，和入站同一条规则。

### 4.6 规则

- **失败不入账**：`settle(FAILED / UNKNOWN)` 时不记——没发出去就等于没说过，记了反而污染时间线。
- **审核中（AUDITED）记**：消息确实出去了，只是待审。
- **降级主动**（被动过期转主动）：只记最后成功那次的最终形态。
- **一个 requestId 一行；被切块的一条逻辑消息会落成多行**。
  单段超 1800 字时 ai-chat 会切成 `base#1..#4`（`ai-chat/outbound.js:484`），
  每块是**独立 requestId、独立 msg_id**，账本里就是 2–4 行。时间线里会看到碎片，这是预期。
- **滚动删除共用 7 天**：出站记录没有理由比入站活得久，同一套 `PRUNE`。
- append 失败只 `log.warn`，**绝不影响发送主链路**。

**一个要留意的坑**：`append` 失败后如果调用方重试，`delivery.claim` 命中 `reuse` 分支直接返回，
**不会再 settle**，这条消息就永久不入账了。修法二选一：
① append 失败时把 requestId 记进一个内存待补队列，下次启动/下次 settle 时补写；
② 在 `reuse` 分支做一次「账本里有没有这条」的补偿写（按 `msg_id` 查一次，没有就补）。
推荐 ②，查询是索引命中，成本可以忽略。

## 5. 隐私边界

| 谁 | 能查什么 |
|---|---|
| 任何人 | **当前会话**的记录（群成员查本群——他们本来就看得见，无新增暴露） |
| 主人的**私聊** | 当前会话 + **任意群**的记录 |
| 任何情况 | **别人的私聊一律不返回**：跨会话查询只接受 group 类 chat_id，owner 也不行 |

### 5.1 判定必须带 `kind`，不能只看 `bucket`

初稿写「bucket / kind 从 turn ctx 拿，和 `memory_search` 的 scope 判定同源」——**同源不了**：
`callerOf`（`tools.js:127`）只返回 `{bucket, chatId, aliases}`，**没有 kind**。

这不是补个字段那么简单，是隐私漏洞：`permissions.js` 的 `bucketOf()` **完全不看 chat kind**，
只读 `sender.bucket` / `sender.level`（`level<=0` 即 owner）。所以主人在群里说话，`bucket` 也是 `owner`。
只判 bucket 的话，主人在群里随口一句，模型就能把 B 群的内容拉进 A 群——
A 群的普通成员因此看到他们不该看到的对话。

所以：

1. `callerOf` 增加 `kind`（`host.js:2039`，从 `speaker.get(sid).payload.chat.kind` 取；
   `speaker.set` 在 `host.js:2790` 存的就是 `{payload, bucket, system}`，路径成立）；
2. 跨会话放开的条件是 **`kind === 'c2c' && bucket === 'owner'`**，两个都满足；
3. 传入的 `chatId` 必须被判定为 group 类：
   `sessions.entry(chatId)?.kind === 'group'`——**注意 `entry()` 可能返回 `null`**
   （`sessions.js:54` 是 `map.chats[chatId] || null`），用可选链，null 一律当不合法（fail closed）。
   不靠「openid 长得像群」这种猜测。

### 5.2 注入路径的洞比 `memory_search` 更大（本方案不修，但必须记下来）

初稿把风险定位在 `memory_search`，说它「只看 bucket，泄露面小」。审校发现前提是反的：

`journal.search` 的 `crossCritical` **默认值是 `true`**（`journal.js:1373`）：

```js
async search(query, { chatId = '', limit = 5, crossCritical = true, ... } = {})
```

而每轮的记忆注入（`host.js:3024`）**没传这个参数**：

```js
hits = await journal.search(text, { chatId, limit, entityJournalIds, aliases });
```

SQL 侧（`journal.js:625`）在 `crossCritical` 为真时是
`chat_id IN (...) OR chat_id='' OR j.level='critical'` ——
**任何档位、任何群、任何私聊**的每一轮注入，都会把别处的 `critical` 日记拉进提示词。
工具那条反而是关着的（`tools.js:190` 只在 `scope==='global' && canCrossGroup()` 时才开）。

现有库里 `level='critical'` 只有 1 条（来自 `F1F759AD`：「记住，以后不要每句话都回，提到你再回」），
所以还没造成实际泄露。但 `chat_look` 落地后，「群友只查本群」的承诺会被同一条注入路径打穿——
不是 `chat_look` 的锅，但用户会当成同一件事。

**更正（2026-11-05 当天推翻）**：这不是洞，是**有意设计**。

`crossCritical` 只放行 `level='critical'`，而这一档只收「身份事实」（名字、住处、
明确要求记住的约定），群内梗和闲聊永远进不了。两条验收锁着它：

- `memory.test.js` 「验收1」：这个群说过的身份事实，**换个群问得出来**；
- `memory.test.js` 「验收2」：A 群的内部梗，**B 群不提**。

我一度把默认值改成 `false`，被验收1 当场打红，已回滚。
真要改这条，必须同时改两条验收——那是产品决定，不是 bug 修复。

**唯一残余风险**（记录，不修）：群友说的「记住我住 XX」如果被判成 critical，
也会跨群。要不要把 critical 再细分成「关于主人的」和「关于别人的」，等有真实案例再说。

### 5.3 主动搭话 / 凌晨巩固：**不满足** owner 边界

初稿写「它们跑在 owner 私聊会话里，天然满足 owner 边界」——不成立。

`callerOf` 的 bucket 来自 `speaker.get(sidFor())`，而 `speaker.set` 全仓**只有一处**
（`host.js:2790`，在 `onInbound` 里）。主动搭话（852/1472）、巩固（1185）都不经过 `onInbound`，
`speaker` 里没有这个 sid → `cur` 为 null → `bucket: undefined` → `caller()` 归一成 `'unknown'`。

所以 `kind === 'c2c' && bucket === 'owner'` 永远不成立，文档举的场景（「觉醒时先看看群里刚才聊到哪了」）
实现出来会一直被拒。

两条路：

1. **给宿主发起的轮次显式标 bucket**：在 speakup / awake 的 `restrictTurnTools({bucket:'owner'})`
   同一处顺手把 `kind` 和 `bucket` 写进 `speaker`（或另一个 `hostTurns` Map），
   这样 `callerOf` 照常读得到；
2. **本版明确不支持**：主动轮次只能查当前会话（也就是主人私聊自己），
   把「觉醒前看群聊」留到下一版。

推荐 1（改动小，且这个场景正是用户最初提的「私聊不知道群里说了啥」的延伸）。选 2 的话，
§9 的文案要跟着改，别写「天然满足」。

## 6. 能力页与开关

### 6.1 名字为什么定 `chat_look`

工具名**会被写进用户的配置文件**——`~/.dsh/dsh-roost/capabilities.json` 的
`defaults.<bucket>.allow` 里就明写着 `memory_search` / `qq_send` 这些字符串。
所以改名不是改代码，是让**用户已经配好的名字静默失效**：旧名字留在 allow 里解析成「未知工具」，
新名字不在白名单里 → 工具在面板上消失，用户只会觉得「升级后坏了」。

这就是「哪个方便维护」的实际判据：**一次选个以后不用改的**。

| 维度 | `ledger_look` | `chat_look` |
|---|---|---|
| 与数据源是否一致 | 只对账本成立，默认读账本还行，但日记源名不副实 | 两个源都成立 |
| 以后加源（transcript / 记忆） | 必须改名，代价见上 | 不用改 |
| 与现有工具同族 | `memory_*` 是按用途命名，不是按存储 | 同族：`memory_*` / `chat_*` |
| 用户理解成本 | 「ledger」是陌生词 | 「chat」直白 |

选 `chat_look`。不是因为它好听，是因为改名有实际代价，而 `ledger_look` 的适用范围只会越来越窄。

### 6.2 权限默认值：**新工具默认只有主人能用**

这一条初稿写错了。`capabilities.js:122` 的 `newTools` 默认是 `'owner-only'`：

- `owner` 的 `allow` 是 `['*']`（`*` 会包含新工具）→ **主人自动能用**；
- 其余档位是**白名单，没写 = 不给**（`capabilities.js:116` 的注释原话是「fail-closed」）。

所以「群友查本群」不会自动生效，用户得在面板上把 `chat_look` 加进对应档位。
这是默认保守策略，不是缺陷——但文档和 README 要写清楚，否则用户会以为工具坏了。

另外两条容易混淆的：

- **`CHAT_ONLY`**（`capabilities.js:85`）只对「这个群设成只能聊天」生效，而且**对 owner 无效**
  （`capabilities.js:343` 明确排除主人）。把它当成「群友也能用」是误解。
- **`PINNED_SOFT`**（`capabilities.js:70`）只是面板上标个 🔒 建议，不参与解析。
  `chat_look` 要不要进这张表，取决于「关掉它机器人还说不说话」——答案是还说话，所以**不进**。

### 6.3 开关

- `features.js` 加 `chatTools` 开关（「功能」页，与 `features.js:66` 的 `memoryTools` 同款），
  默认**开**——和记忆工具同一信任级别。
- 不进 `PINNED_KEEP`（`capabilities.js:63`）：关了它机器人照样说话，只是不能翻记录，属于用户的选择。

## 7. 明确不做的

- **不做注入式群聊上下文**：用户已选工具路线，注入废弃。
- **不做打断 / 排队**：那是另一份方案（`排队方案.md`），两件事不塞一个版本。
- **不做 DSH 会话记录（transcript）读取**：`~/.dsh/sessions/*/session.v4.jsonl.zstd` 里确实是完整往返
  （含工具调用），但实测一个文件是 **609 个 zstd 帧 / 675,781 字节**拼的追加日志，
  Node 的 `zstdDecompressSync` 只解第一帧（228 字节，只有会话头），要读全得自己按帧魔数切。
  而且格式是 DSH 内部 v4，升级就可能全废。账本 + 日记已经覆盖「用户看得见的内容」，
  不值得为工具调用记录背这个依赖。
- **不做别人的私聊查询**：没有「合法需求」能盖过隐私风险，永远不做。
- **面板不加新页面**：能力页的工具列表自然会出现它，不加专门 UI。

## 8. 实施顺序与依赖

| 步 | 仓 | 内容 | 依赖 |
|---|---|---|---|
| 0 | dsh-roost | `postReply` 四处补 `requestId`（§4.2） | 无，但**不早于步 2、不晚于步 4** |
| 1 | dsh-roost | `chat_look` 两个源 + `chats` + 隐私判定 + `callerOf` 补 kind + 单测 | 无 |
| 2 | dsh-roost | 发版 **1.0.2 → 1.0.3**（本线先发；排队方案随后发 1.0.4） | 步 1 |
| 3 | bot | 出站入账（后置注入 ledger + hook + 去重）+ **`plugin` 列与 schema v3** + 单测 | 步 0 |
| 4 | bot | 发版 v1.0.4（现读 `package.json` 为 1.0.3） | 步 3 |
| 5 | dsh-roost | 核对出站记录形态（切块、审核中、降级），补必要清洗 | 步 4 的数据 |

**B 仍然不等 A，但要说准它能给出什么。** 步 1 落地后：

- ✅ 「这个群刚才在聊什么」——**立刻可用**（账本本来就有全量入站，这是用户最初的需求）；
- ✅ 「一周前的对话」——`source:'journal'` 可用（账本只有 7 天）；
- ❌ 「她以前回过什么」——**要等步 4**。账本的出站是 Part A 才有的；
  A 之前只有 `source:'journal'` 能看到她的回话，而且只覆盖「触发过她」的那些。

步 5 不是「打开一个新源」，是**验收入站+出站混排后的形态**：
切块的长回复会落成 2–4 行、审核中的行缺 `msg_id`、降级主动的行 `time_basis` 仍是 `observation`。

但**步 0 不能晚于步 4**：只发 bot 1.0.4 而 dsh-roost 不补 requestId，
出站入账只会记到 `qq_send` 那部分（分段说的长回复），主回话照样空白，
用户会以为「升级了但还是看不见自己说过什么」。反过来（先补 requestId、bot 还没升级）是无害的——
老框架会忽略这个字段。

## 9. 已决定（2026-11-05，按「哪个方便维护」定的）

1. **工具名 `chat_look`**。判据不是好听，是**名字会写进 `capabilities.json`**，
   改名 = 用户配好的白名单静默失效（§6.1）。
2. **默认 `source:'ledger'`**，日记作为显式可选源。理由：默认路径只跑一套 SQL / 清洗 / 游标；
   而账本是唯一能回答「群里刚才聊了什么」的源（§3）。日记保留是因为它有账本补不上的「长期」。
3. **`journal.search` 的 `crossCritical` 默认值改成 `false`**（§5.2）。默认安全比默认方便更难改回来；
   这是一行改动，顺带补一个现有洞。**行为变化**：注入时不再自动带别群的 `critical`，
   发版说明里要写一句。
4. **主动轮次补 `speaker`**（§5.3 方案 1），让觉醒/主动搭话也走同一条 `callerOf` 读路径。
   不引入第二个身份源（另建 `hostTurns` Map），否则以后两处判断必然分叉。

四条都改了的话，剩下的只是实现细节，不需要再拍板。

## 10. 参考实现（2026-11-05 调研，给 §3 的日记口径找依据）

「账本 + 日记」这种双层不是本项目自创，主流 Agent 记忆系统都这么分。
两个项目选了**相反**的路，但共享同一条铁律。

| | [Graphiti / Zep](https://github.com/getzep/graphiti) | [claude-mem-lite](https://github.com/sdsrss/claude-mem-lite) |
|---|---|---|
| 原始层 | **永久保留**，叫 episode：不可变、ground truth | **只当临时态**：`runtime/ep-*.json`，flush 后编码成 observation 就丢 |
| 派生层 | 实体 / 关系边，带双时态有效期，失效**不删除** | `observations` + `session_summaries`，FTS5 索引 |
| 溯源 | 每条派生事实都能回到 episode（原文 "full lineage"） | `related_ids` / `files_read` / `memory_session_id` / `branch` |
| 防自噬 | 派生只进图，不写回 episode | 代码级 Tier1 过滤 + Jaccard/MinHash 两层去重 + `🤖` 标记机器生成 |
| 存储 | Neo4j / FalkorDB | **单 SQLite（WAL）+ FTS5**，和本项目同构 |

两家的原文：

> Graphiti：**"Episodes (provenance): Raw data as ingested — the ground truth stream. Every derived fact traces back here"**
>
> claude-mem-lite：**"filters first with code, then sends only what matters"**；
> 唯一保存原文的地方是 `user_prompts.prompt_text`，assistant 的原始输出**不存**。

**共同铁律：原始层只收外部输入，绝不收自己生成或拼装的内容。**
Graphiti 靠「episode 只来自 ingest」；claude-mem-lite 靠「派生结果打 🤖 + 先过滤」。
违反它的后果两家都点明了：自己的输出被当输入重新摄取 → 记忆自我强化，越走越偏。

### 本项目对照

| 层 | 本项目 | 判定 |
|---|---|---|
| 原始层 | 账本 `events.db`（原文 + payload，append-only） | ✅ 对齐 Graphiti |
| 派生层 | 日记 `journal`（digest / 向量 / FTS5） | ✅ 架构对齐 claude-mem-lite |
| 溯源 | `journal.event_ids` + `evidence` 指回 events | ✅ 两家都强调的东西这里已经有了 |
| 压缩不删 | `text` 永不改写，只写 `digest` | ✅ 对齐 Graphiti 的「失效不删除」 |
| **唯一违反** | `journalAdd(..., text, 'user')` 存的是**拼装后的 prompt**（自述 + 开场白） | ❌ 正是两家都禁止的「把自己生成的东西写回原始层」 |

所以结论不是「改架构」，是**改一处口径**：存 `said`（`host.js:2900` 已有的原话副本）。

**一个容易忽略的连带收益**：账本 7 天滚动删、日记不删，所以**日记的 user 行在 7 天后就是唯一的长期原文**。
现在它存的是拼装物，等于「唯一长期原文」被污染；换成 `said` 之后它才真能当长期原文用。
这比「少存点垃圾」重要得多。

**要不要像 claude-mem-lite 那样给自产内容打标记**？本项目 `journal.role` 已经分了
`user` / `bot` / `digest`，`bot` 行天然是自产内容，**不需要额外标记**。
缺的只有一条：注入块不许进 `user` 行。

## 11. 落地校正（2026-11-05 可行性审查，开工前必读）

以下都是「照前文写会静默失效或打红测试」的点，来自逐行核对，不是推测。

### 11.1 加工具会打红两条现有测试

| 测试 | 断言 |
|---|---|
| `test/tool-schema.test.js:86` | 「能造出全部 **6** 个工具」，`deepEqual` 硬比名字数组 |
| `test/tools.test.js:147` | `registered.sort()` 必须等于 `['memory_note','memory_search']`，且 `disposed.length === 2` |

所以新工具塞进 `buildToolDefs` 的返回数组（`tools.js:293`）之后，**这两条必须同步改**。
想「不改测试」就得另开 `buildChatToolDefs` + `registerChatTools`，但那样
`tool-schema.test.js` 的 schema 校验会漏掉新工具——是**假绿**，不建议。

### 11.2 `callerOf` 加 `kind` 会被 `tools.js` 的白名单丢掉

`host.js:2039` 返回 `{ bucket, chatId, aliases }`，而 `tools.js:132-147` 会**重新组装**：

```js
const caller = () => {
  const s = callerOf?.() || {};
  return { bucket: String(s.bucket || 'unknown'), chatId: String(s.chatId || ''), aliases: ... };
};
```

未列出的键**静默消失**。所以两处都要改，且 `tools.js` 里要允许缺省
（`String(s.kind || '')`）——现有 7 处测试只传 `{bucket, chatId}`，不容缺省会全红。

顺带：`cur()`（`host.js:2080`）返回的是 `kind: chat.kind`（mount 时闭包捕获），
不是 `payload.chat.kind`；两者语义相同，用哪个都行，但别混着写。

### 11.3 工具里**不能**用 `turns.run()` 去「起一轮看一眼」

`turn.js:220` 的 `waiters` 在 `followup` **之前**就 `set` 了（`turn.js:230`），
而工具是模型在**本轮 turn 内部**调用的——此时这个 sid 正挂在 `waiters` 里。
所以工具里 `isWaiting(sid)` 恒为 `true`，任何「借 run() 起子对话」的实现都会立刻 `busy`。
`chat_look` 只能读库或走 HTTP，**这条是硬约束**。

### 11.4 出站入账：`append()` 不认 `at`，`digestOf` 还有同名不同义

`ledger.js:184-197` 的 `at` 只从 `msg.raw.timestamp` 推（`resolveTime`，`:89`），
**传 `at` 完全无效**。想固定发送时刻只有两条路：`msg.raw = { timestamp: at }`
（代价是这段假 raw 会被序列化进 `events.payload`），或者接受 `observation` + `receivedAt`（推荐后者）。

同一处两个坑：

- **`digestOf` 同名不同义**：`outbound.js:4` 从 `delivery.js` 导入的 `digestOf(text: string)`
  返回 `"正文…(12)#abcd1234"`；`ledger.js:111` 的 `digestOf(msg)` 吃**对象**、返回 16 位 hex。
  在 `outbound.js` 里再 import 会直接重名。
- **`digestOf(msg)` 读的是 `msg.chatId / userId / content`**，传一个字符串不够。

### 11.5 新工具默认只有主人能用，放开要动五处

`capabilities.js:136-139` 的档位白名单是写死的，不在名单里的名字一律进 `deny`。
`chat_look` 上线后 admin / member 都调不了，只有 `owner`（`allow:['*']`）能用。
想放开还要动：`capabilities.js:70`（PINNED_SOFT）、`:85`（CHAT_ONLY）、
`permissions.js:87`（GUEST_KEEP_TOOLS）、`client/client.js:3784/3791/3808`（面板预设）、`:4067`（SUGGESTED）。

**本版决定：不放开**。先只给主人，等真实用法出现再评估。

### 11.6 `features.js` 加开关要动 5 处

`FEATURES` 条目、`FEATURE_GROUPS`（`features.js:265`，`features.test.js:56` 会断言
「每个 feature 都在某个分组里」，漏了直接红）、`host.js` 挂载条件（照 `:2033`）、
`tools.js` 的 build/register、`config.js` 默认值。面板不用改——`features.get`
（`host.js:3794`）是把 `FEATURES` / `FEATURE_GROUPS` 直接吐给前端的。

`readFeatures` 对缺失字段默认「开」（`features.js:185`），所以新开关不写进 config 也不会把功能关掉。
