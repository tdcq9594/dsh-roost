# 端口自动切换方案

> 目标：端口被占时两边都能自动换，并且**另一边知道对方换到了哪**。

## 一、先说清楚问题的本质

现在有三个端口，各存各的地方：

| 端口 | 谁用 | 存在哪 |
|---|---|---|
| 15210 | Roost 面板 | Roost 的 `config/bot.json` → `webui.port` |
| 17321 | dsh-roost 的 `/inbound` | dsh-roost 的 `config.json` → `server.port` |
| 15210 的引用 | ai-chat 的 `dshUrl` | Roost 的 `config/bots/main/plugins/ai-chat.json` |

**问题的根不在「怎么换端口」，而在「谁说了算」。**

配置里写的是**意愿**（用户希望用 17321），
实际 bind 成功的是**现实**（可能变成 17322）。
现在代码把两者当成一个东西，所以：

- 自动改了实际端口 → 配置没改 → 重启又回到被占的那个
- 改了配置 → 另一边不知道 → ai-chat 还往旧端口推

所以第一件事是**把「意愿」和「现实」分开存**。

## 二、三个方案

### 方案 B：只让 dsh-roost 自动换（最小改动）

```
dsh-roost: 17321 被占 → 试 17322 → 成功 → 写进配置 → PUT ai-chat 的 dshUrl
Roost:     不动（端口被占就启动失败，用户自己改 config）
```

| | |
|---|---|
| 改动 | 只改 dsh-roost，Roost 一行不动 |
| 解决 | 这次的坑（DSH 重载时旧 server 占着 17321） |
| 不解决 | Roost 端口被占时还是起不来 |
| 工作量 | ~60 行 + 6 条测试 |

**够用吗？** 够覆盖 90% 的情况——因为 dsh-roost 的端口是「程序自己挑的」，
被占是因为它自己的旧实例；而 Roost 端口是「用户自己定的」，被占的概率低得多，
且用户改 config 是明确的动作，不需要自动。

### 方案 A：共享「端口租约」文件（推荐）

两边都能换，通过一个共享文件互相知道。**核心是租约文件。**

位置：`<roost 目录>/data/ports.json`

```json
{
  "roost": { "want": 15210, "actual": 15211, "pid": 12345, "at": "2026-10-27T01:40:00Z" },
  "dsh":   { "want": 17321, "actual": 17322, "pid": 9999,  "at": "2026-10-27T01:40:01Z" }
}
```

- `want` = 配置里的意愿（**永远不改**，用户写的）
- `actual` = 实际 bind 成功的（**每次启动重写**）
- `pid` = 用来判断这个租约是不是还活着（进程没了 = 过期）

**启动时序（以 dsh-roost 为例）：**

```
1. 读租约 → 拿 dsh.actual（上次用的）
2. 依次试 bind：配置的 server.port → 上次的 actual → 往后 +1 到 +20
3. 成功 → 写回租约 dsh.actual
4. 主动 PUT ai-chat 的 dshUrl 指向新端口
   （ai-chat 在 Roost 进程里，它只能被通知，不能读租约）
```

**Roost 侧同理**，只是第 4 步不需要——dsh-roost 会轮询租约。

**dsh-roost 怎么知道 Roost 换了端口：**

```
每 30 秒（以及每次点「检测」时）读一次租约的 roost.actual
→ 用 actual 覆盖 portOf() 的结果
→ 面板显示「配置写的是 15210，实际在 15211」
```

**为什么用文件而不是 HTTP 回调：**

| 方式 | 问题 |
|---|---|
| Roost 主动 POST 给 dsh-roost | Roost 不知道 dsh-roost 换到哪了，鸡生蛋 |
| dsh-roost 主动 POST 给 Roost | 反过来同样 |
| **共享文件 + 轮询** | 无方向依赖，谁先起都行，进程重启也不丢 |

**竞态怎么处理：**

- 两边同时启动抢同一段端口 → 各自 bind 失败就 +1 重试，最终会落在不同端口
- 写租约用「写临时文件 + rename」（原子），不用锁
- 读租约解析失败 → 当作没有，退回配置值（不能因为一个坏文件就起不来）
- `pid` 对不上/进程不在 → 认为 `actual` 过期，从 `want` 重新试

### 方案 C：统一端口分配服务

起一个常驻的小服务专门发端口。**不推荐**——为了两个端口引入第三个服务，
故障面反而变大。

## 三、推荐

**方案 A，但分两步落地：**

**第一步（先做）**：把方案 B 的部分做掉
- dsh-roost 自动换端口 + 自动同步 ai-chat
- 这一步立刻解决你现在的痛（重载后端口被占）

**第二步**：加租约文件，让 Roost 也能换、dsh-roost 也能知道
- 改框架 `src/web/server.js` 的 listen 部分
- dsh-roost 的 `portOf()` 改读租约优先

理由：第一步是小改动、风险低、马上见效；第二步动框架，
需要单独验证（面板端口变了，用户的书签会失效，得给提示）。

## 四、边界与风险（必须处理）

| 风险 | 处理 |
|---|---|
| **用户按固定端口配了反代/防火墙** | 自动换端口默认**开**，但设置里给开关；关了只提示不换 |
| 换端口后用户书签失效 | 面板和控制台都要打印「实际在 X」；概览显示实际端口 |
| 扫端口扫到别人的服务 | 只在 `127.0.0.1` 上试，范围限制 `want..want+20`，试到就停 |
| 两个实例同时跑（旧 DSH 没退） | `pid` 字段 + bind 失败自然错开；租约里记 pid 方便排查 |
| 端口换了但 ai-chat 没在跑 | **2026-10-28 修**：以前只在 bind 成功那一刻同步一次，Roost 没起来就永久放弃，面板红字一直支使用户手动去改。现在 `sync-retry.js` 按 5 秒×6 次 → 60 秒退避重试，封顶 30 分钟；面板红字旁另给「现在就改过来」一键按钮 |
| 租约文件损坏 | 解析失败当作没有，退回配置值 |

## 五、涉及改动

| 文件 | 改什么 |
|---|---|
| `dsh-roost/src/server.js` | bind 失败时按候选列表重试，返回实际端口 |
| `dsh-roost/src/host.js` | `startServer()` 用实际端口；启动后同步 ai-chat |
| `dsh-roost/src/sync-retry.js`（新） | 「等一下再试」的退避调度：不叠加、可作废、30 分钟封顶 |
| `dsh-roost/src/setup.js` | `portOf()` 优先读租约的 `roost.actual`；`syncDshUrl()` 返回跳过原因（`roost-down` 才重试） |
| `dsh-roost/src/lease.js`（新） | 读写租约，原子写，坏文件容错 |
| 框架 `src/web/server.js` | listen 失败时 +1 重试，成功写租约 |
| 面板 | 概览显示「意愿 / 实际」，不一致时说明 |

工作量：第一步 ~60 行，第二步 ~150 行（含两份租约实现和测试）。
