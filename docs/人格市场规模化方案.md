## 一、先把问题量化

不是「CPU 撑不住」，是**动线和信息密度撑不住**。但性能上确实有几处会随数量线性恶化，
先把账算清楚，后面每一条改动才有验收口径。

| 位置 | 现在的做法 | 300 份时 | 1000 份时 |
|---|---|---|---|
| `personas.list()`（`personas.js:180`） | 每次 `readdir` + 逐个 `readFileSync` + `parsePersona`（正则切四段） | 每次开面板读 ~300 KB、跑 300 次正则 | ~1 MB、1000 次正则 |
| `seed()`（`personas.js:146`） | 在 `list/read/save/resolve` 里各调一次，每次 `readdir` + 对每个内置文件 `existsSync` | `resolve` 每轮被调 **2 次**（`host.js:1432`、`:1523`）→ 每轮 4 次 readdir + 1200 次 stat | 每轮 4000 次 stat |
| `status()`（`persona-repo.js:365`） | 每个仓库条目：`existsSync` + **2 次** `readFileSync` + sha256 + `bundledSha()` 再读一次内置文件 | 一次 `/personas/repo` ≈ 1200 次同步文件操作 | 4000 次 |
| `sync()`（`persona-repo.js:472`） | 逐条 `await` 下载 | 首次装库 300 个请求，串行 | 1000 个请求 |
| `index.json` | 单文件，每条 ~250 B（id/name/tags/file/chars/sha256） | ~75 KB，安全 | ~250 KB，加 `desc` 后逼近 `MAX_BYTES = 512 KB`（`persona-repo.js:82`） |
| 面板两个列表（`client.js:1379`、`:1454`） | 全量 `.map()` 渲染，无搜索/筛选/分页 | 300 行 × 3 按钮 ≈ 900 个节点 | 3000 个节点 |

**更麻烦的是语义层，不是性能：**

1. **找不到。** 列表按 id 字母序，唯一的检索手段是肉眼扫。名字是中文、id 是英文，
   想找「那个爱吐槽的」只能一个个点开看。
2. **没有一句话简介。** `index.json` 里没有 `desc`（`build-persona-index.mjs:64` 只写 id/name/tags/file/chars/sha256）。
   几十个还能靠名字猜，几百个时**名字+标签不足以做选择**。
3. **换人格只有一条路。** 只有「用这个」写全局 `current`；`byChat`（按群指定）在
   面板上只显示一个数字，没有入口。几百个时「这个群用 A、那个群用 B」才是常态。
4. **撞名只能覆盖。** id 就是文件名，两个人写 `fatfish` 就是互相盖掉。
5. **不知道谁在用谁。** 全局默认、各群覆盖、失效引用（`byChat` 指向已删的 id 会静默回退，
   `personas.js:226`）散在配置里，没有一处能看全。
6. **装不动。** 0.10.7 刻意去掉了单条安装（「一键装全部」）。8 个时是对的，
   300 个时变成「为了 1 个新人设把 300 个下一遍」。

## 二、调研：别人怎么处理几百个

按规矩先看现成方案，只借思路，不搬实现。

| 项目 | 它怎么解决 | 借什么 | 不借什么 |
|---|---|---|---|
| **SillyTavern** | 角色列表 = 搜索框 + 标签过滤（含收藏）+ 文件夹 + 批量打标签（BulkEditOverlay 会算「共同标签」）+ 分页加载；角色本体仍是单文件 | 搜索 + 标签计数 + 批量打标签 + 分页 | 文件夹落在磁盘上（我们是平铺文件） |
| **AstrBot `persona_plus`** | `文件夹/人格ID` 命名空间解决撞名；按人格限工具 | 命名空间的**语义**（`@作者/id`） | 目录分层（会破坏现有 `list/seed/sync`） |
| **chub.ai / characterhub** | 服务端 tag + 排序 + 分页检索，客户端不拿全量 | 「检索在服务端」这条 | 账号/评分/上传（与零依赖单进程冲突） |
| **本项目插件市场**（`qq-bot-roost/src/plugin/market.js`） | index + sha256 + 三层兜底 + 换源 + 并发去重 | 整套分发骨架，直接复用 | — |

四条结论：

1. **列表必须能搜、能筛、能排序**——这是所有同类产品的共同底线，不是加分项。
2. **检索放服务端**（内存里已经有整份目录），客户端只拿一页。几百条全量下发也能用，
   但上千条以后要重写，不如一次做对。
3. **分类用虚拟分组，不用目录**。目录一改，`list()`、`seed()`、`seed` 的「只补缺」、
   `.synced` 的按文件名对齐全部要跟着改，收益不值。
4. **批量操作是刚需**：几百个里想清理 200 个没用的，没有多选就只能一个个删。

## 三、设计主线

```
                    ┌──────────────── 写操作（save/remove/sync）后失效 ───────────────┐
                    ▼                                                              │
 personas/*.md ──增量扫描──▶ .catalog.json ──▶ GET /personas/query ──▶ 市场 / 人格库 / 选择器
      ▲            (mtime+size)   （派生，可删）        │                        │
      │                                                └──▶ 治理视图（体检/正在用）│
      │                                                                          │
      └────────── 按 pack 增量下载 ◀── index.json（远端） ◀───────────────────────┘

 .prefs.json（收藏 / 置顶 / 分组 / 使用统计）── 只读给 query，永不随同步重建
```

四条原则，后面每个设计都服从它们：

1. **`.md` 是唯一真源。** catalog 是派生缓存，删了能一键重建；任何「只能从 catalog 恢复」
   的状态都是设计错误。
2. **一个查询入口。** 市场、人格库、选择器、将来的模型工具，全部走 `/personas/query`。
   不写第二套筛选逻辑（两套逻辑迟早不一致，索引里的名字和面板显示的名字就会对不上——
   `build-persona-index.mjs` 的注释里已经踩过这个坑）。
3. **装是按需 + 批量。** 单装走单文件直链，多装走 pack；都不是「为了一个下一百个」。
4. **偏好只存本地。** 收藏、分组、使用次数不进 `.md`、不跟仓库走。
   否则别人的人格会带上你的偏好，或者一次同步把你的收藏清零。

新增两个点文件，都放在 `personas/` 下，都不会被 `list()` 当成人格（它只扫 `*.md`）：

| 文件 | 内容 | 丢了会怎样 |
|---|---|---|
| `.catalog.json` | 派生：每份的 name/tags/desc/chars/sha256/mtime/size | 自动重建，无损失 |
| `.prefs.json` | 用户态：收藏、置顶、分组、使用统计 | 会丢偏好，所以要备份 |

**为什么拆两个文件**：同步会重写 catalog（内容变了），偏好不能跟着一起重建。
合成一个文件，最容易写出的 bug 就是「点了一次一键更新，收藏全没了」。

## 四、P0：派生目录（catalog）

### 结构

```json
{
  "schema": 1,
  "dirMtime": 1793183054030,
  "files": {
    "fatfish.md": { "mtimeMs": 1793183054030, "size": 731, "sha256": "…" }
  },
  "items": {
    "fatfish": {
      "id": "fatfish", "file": "fatfish.md",
      "name": "大肥鱼", "desc": "短句、爱吐槽、不装真人",
      "tags": ["短句", "吐槽"], "alias": ["大鱼"],
      "author": "tdcq9594", "version": "1.0.0",
      "chars": 731, "sha256": "…",
      "source": "builtin"
    }
  }
}
```

- `chars` 用**整份原文长度**，跟 `index.json` 的口径一致（`build-persona-index.mjs:69` 的注释写了原因：
  body 不含示例和世界书，报出来会明显偏小）。
- `source`：`builtin`（npm 包自带）/ `repo`（从仓库装的）/ `local`（自己建的）。
  判定顺序：不在远端索引里 → `local`；在远端索引里且 `.synced` 有记录 → `repo`；否则 `builtin`。
- **不存 `lastUsedAt` / `useCount` / `fav` / `folders`**——那些在 `.prefs.json`。

### 增量算法

```
scan(force = false):
  st = stat(personas/)                        # 目录 mtime：增删文件会变
  if (!force && catalog.dirMtime === st.mtimeMs) return catalog
  names = readdir(*.md)
  for name in names:
    s = stat(name)
    old = catalog.files[name]
    if (old && old.mtimeMs === s.mtimeMs && old.size === s.size) → 复用 items[old.id]
    else → read + parsePersona + sha256        # 只有变过的文件才读
  删掉 items/files 里已不存在的
  原子写回（先 .tmp 再 rename，沿用 persona-repo.js:232 的做法）
```

两个刻意的取舍：

- **只信 mtime+size 不做全量 hash**：全量 hash 正是要省掉的那笔开销。代价是
  「同一毫秒内改成同样大小」的编辑会漏判——概率极低，且面板上有「重建目录」按钮兜底。
- **不监听 fs.watch**：DSH 里插件生命周期不可控，watcher 泄漏比省下的几毫秒贵得多。
  每次 `list/query` 前 `stat` 一次目录（一次系统调用）就够。

### 顺带修掉的三处

| 改动 | 收益 |
|---|---|
| `seed()` 加模块级 `seeded` 标志，一个进程只跑一次 | 每轮对话从 4 次 readdir + 4N 次 stat 降到 0 |
| `resolve()` 加一层**内存解析缓存**（`Map<id, {sha, parsed}>`，按 sha 失效） | 稳态下每轮 2 次 `resolve` 命中内存，进程内每个文件最多读一次 |
| `status()` 用 catalog 的 sha 代替「每个文件读两次 + 算一次 hash」，`bundledSha()` 改成读**包内 `personas/index.json`** 一次建 map | 一次 `/personas/repo` 从 O(4N) 次文件操作降到 **0 次** |

**catalog 里没有正文，这一点必须说清楚。** 它只存 name/tags/chars/sha 这些元数据，而
`resolve()` 要的是 `body / demos / lore / firstMes`（`personas.js:196-202` 每次都
`readFileSync + parsePersona`）。所以「catalog 建好之后每轮 0 次文件读」只对**元数据**成立，
正文得靠上面那层内存缓存：首轮读一次、之后按 sha 命中。验收口径按这个写（见 §10），
否则 P0 的收益会被高估一倍。

最后一条是本方案性价比最高的改动：`personas/index.json` 本来就随 npm 包发布
（`package.json` 的 `files` 含 `personas`），里面已有每份的 `sha256`，
不需要为了「判断有没有被改过」再把每个文件读一遍。

### `seed()` 只跑一次之后，「删内置人格」要有个说法

现在的行为是：`remove()` 只 `unlink`，而下一次 `list()` 会先 `seed()` 把缺的内置文件再拷回来
（`personas.js:146-171`、`:180`）——**内置人格今天其实删不掉**，删完立刻复活。
改成进程内只 seed 一次，就变成「这次删掉了，重启又回来」，两种都不对。

两个选择，实现时选一个：

- **墓碑（推荐）**：`.prefs.json` 记 `deleted: ["fatfish", …]`，`seed()` 跳过这些 id；
  点「恢复官方版本」时把 id 从墓碑里移除。
- **UI 禁止**：内置人格的「删除」按钮置灰，文案改成「内置人格不能删，可以改成你自己的」。

### 失效与重建

- 写操作（`save` / `remove` / `sync` / `restore`）后**主动** `invalidate()`，不等 mtime 轮询。
- 读 catalog 时 `JSON.parse` 失败 → 静默重建（不抛错，理由同 `seed()`：人格库坏了不该让插件加载失败）。
- 面板加一个「重建目录」，用于排查「列表和磁盘不一致」。

## 五、P1：查询接口与市场列表

### 接口

```
GET /personas/query
  ?q=          名称 / id / 标签 / 简介 / 作者 / 别名，全部 substring
  &tag=a,b     多选 AND
  &source=     builtin|repo|local
  &state=      same|update|missing|modified
  &scope=      local（人格库）| repo（市场）| all（合并，本地优先）
  &sort=       recent|used|name|chars|added|repo（最近更新）
  &page=1&size=50

→ {
    ok, total, page, size,
    tags: [{ name, count }],           // 筛选栏要显示数字
    items: [{ id,name,desc,tags,chars,author,version,
              state,source,pack, fav,pinned,lastUsedAt,useCount }]
  }
```

- **不含正文**。预览仍走 `GET /personas/repo/preview?id=`（已有，不重复实现）。
- `state` 由 catalog + 远端索引在内存里 join 出来，**零文件 I/O**。
- 中文不分词，`toLowerCase().includes()` 就够：几百到几千条 substring 是微秒级，
  上分词器只会引入一个依赖和一堆边界情况。
- 排序必须**稳定**：同分用 id 兜底，否则翻页会看到重复/漏项。
- `sort=recent` 时把 `pinned` 和「当前在用」排最前，其余按 `lastUsedAt` 降序，没用过的按 `added` 降序。

### 为什么检索放服务端

| | 全量下发前端筛 | 服务端 query |
|---|---|---|
| 首次开面板 | 1000 条 × ~500 B ≈ 500 KB | 一页 50 条 ≈ 25 KB |
| 输入即时性 | 无网络往返，最快 | 120 ms debounce 后一次请求 |
| 将来模型工具复用 | 要再写一套 | 直接调同一个函数 |
| 上千条以后 | 要重写 | 不用动 |

选择服务端，前端 `debounce 120ms`。这点延迟在本地回环上基本感知不到。
（300 条时服务端查询只要几毫秒，debounce 其实不必要；留着是给 1000+ 预留，别当成冗余删掉。）

### 市场面板

```
人格市场          [搜索 名称/标签/作者/别名__________]   排序[最近更新▾]   [刷新]
┌ 分类 ──────┐ ┌ 128 / 300 ─────────────────────────────────────────────┐
│ 全部    300│ │ 大肥鱼      @tdcq9594   短句 / 吐槽    v1.0.1   439 字     │
│ 精选     42│ │ 短句、爱吐槽、不装真人                     [预览] [装上]  │
│ 有更新    3│ │ ───────────────────────────────────────────────────────── │
│ 已装     58│ │ 元气少女    @someone    活泼 / 二次元  v1.1.0   512 字     │
│ 未装    242│ │ 高能量、爱用感叹号                     [预览] [装上]      │
└────────────┘ └─────────────────────────────────────────────────────────┘
标签：全部(300) 日常(31) 吐槽(22) 二次元(18) 工具(12) …
                                                       [上一页] 1/6 [下一页]
```

关键点：

- **每行必须有 `desc`**。这是几百个时唯一能扫读的字段，比标签管用。
  front matter 加可选 `desc:`，`build-persona-index.mjs` 写进索引；没写就回退成
  **第一个非空、且不以 `##` 开头的行**截 60 字（生成时截，不是运行时算）——
  直接取「第一行」经常拿到空行或 `## 开场白`，那等于没有简介。
- **每行一个图标位（24px）**：优先 front matter 的 `icon:`（一个 emoji），没写就用名字首字 +
  由 id 哈希出的稳定色相兜底——几百个里 80% 不会填 icon，靠兜底才不至于一片空白。
  **不做图片头像**：几百张 PNG 会让仓库变重，也破坏「人格就是一个可 diff 的 .md」这条底线。
  图标不进检索域（emoji 搜索没有意义）。
- **分类是查询条件的预设**，不是新数据：「精选」= 官方索引里 `featured: true`，
  「有更新/未装/已装」= `state` 过滤。
- **每行一个「装上」**（0.10.7 去掉的那个）。几百个时「只装我想要的」不是优化，是必需。
- 分页 50 条，前端渲染行数 ≤ 50，DOM 不再随人格总数增长。
- 「预览」抽屉里加两个动作：`装上`、`装上并给本群用`（后者 = install + 写 `byChat`，
  一步到位，市场到使用的转化路径最短）。

### `desc` 与 `author` 的兼容

`parsePersona`（`personas.js:41`）现在只认 `name` / `tags`。扩成通用 kv 解析
（`^(\w+):\s*(.*)$` 已经能吃任意 key），新增 `desc` / `author` / `version` / `alias` / `featured`。
老文件没有这些字段 → 取默认值，不报错。索引 `schema` 升到 2，`validateIndex` 对未知字段宽容。

**`chars` 的口径要先统一。** 现在是两套定义、三处使用：`personas.list()` 用 `p.body.length`
（`personas.js:189`），`index.json` 用整份原文长度（`build-persona-index.mjs:71`），
`status.localChars` 也用原文长度（`persona-repo.js:387`）。catalog 统一取**原文长度**
（跟索引一致，也跟面板上「439 字」的观感一致），`list()` 跟着改；否则同一份人格在
her 页和市场页会显示两个数字。

## 六、P2：选择器（换人格的动线）

这是「方便使用」的核心，单独一节。

### 动线

人格页顶部常驻一条**当前人格条**：

```
当前：大肥鱼  @tdcq9594   [换人格]   [本群单独用：开]   本群 3 个群在用 · 全局默认：小栖
```

点「换人格」弹出选择器（不跳页）：

```
┌ 换人格 ─────────────────────────────────────────────┐
│ [搜索____________________________]        Esc 关闭   │
│ ★ 小栖          日常 / 温和        全局默认          │
│ ★ 大肥鱼        短句 / 吐槽        本群在用 · 常用 12│
│   元气少女      活泼 / 二次元      最近 2 小时前     │
│   古风书生      文艺 / 有趣                          │
│   …（最多 8 条，继续输入收窄）                       │
├─────────────────────────────────────────────────────┤
│ ↑↓ 选择   Enter 换   Tab 切「只给本群 / 设为默认」    │
└─────────────────────────────────────────────────────┘
```

- 空搜索时按「置顶 → 最近使用 5 个 → 收藏 5 个」排，而不是从 A 开始列。
- **两个 scope 必须分开**：`只给这个会话`（写 `byChat[chatId]`）和 `设为默认`（写 `current`）。
  现在只有后者，而几百个时前者才是高频动作。
- 键盘：`↑↓` + `Enter`，`Tab` 切 scope，`Esc` 关。不做全局快捷键（DSH 面板里抢按键容易和宿主冲突）。

### 接口

```
POST /personas/use    { id, scope: 'global' | 'chat', chatId? }
POST /personas/unuse  { chatId }        # 清掉本群覆盖，回落到全局
GET  /personas/recent?limit=10          # 置顶 + 最近 + 收藏
```

`use` 内部只写 `cfg.persona.current` 或 `cfg.persona.byChat[chatId]`，**不复制正文**
（正文永远在文件里，这是 0.10.0 定下的）。

### 使用统计

`resolve()` 每次命中时更新内存里的 `{lastUsedAt, useCount}`，**30 秒 debounce 落盘**
到 `.prefs.json`。绝不能每轮都写文件——一次对话两轮就是两次同步写盘。

### 模型侧（后半期）

群里有人说「换成那个爱吐槽的」，模型得能查：

- `persona_search(query, limit=5)` → 只返回 `{id, name, tags, desc, state}`，**不返回正文**。
  返回正文等于让模型自己挑人设，token 和越权都不划算。
- `persona_use(id, scope)` → **仅 owner**（`bucket === 'owner'`），member 一律拒绝。
- 落地注意：`permissions.js` 的工具白名单是 **fail-closed** 的，新工具名必须同时加进
  白名单，否则一加就被整批 deny（0.10.10 踩过：白名单里写了不存在的 `bash/shell/fs`，
  导致权限硬限从没生效过）。

## 七、P3：治理视图（几百个时真正的时间黑洞）

「正在用」一页看全，这是目前完全没有的信息：

```
全局默认：小栖
本群：大肥鱼
其他会话：3 个群单独指定
  · 群「摸鱼部」→ 大肥鱼
  · 群「读书会」→ 古风书生
  · 群「测试群」→ lazycat ⚠ 人格已不存在，正在静默回退到小栖  [清除]
```

每个人格一行附：被几个群用、最后使用时间、使用次数、字数（粗估 token = 字数 × 1.6）、
是否有更新 / 被改过。

### 体检（一次扫描全部已装人格）

| 检查 | 判据 | 为什么值得做 |
|---|---|---|
| 高危命中 | 复用 `scanPersona`（`persona-repo.js:144`） | 0.10.7 只扫「刚更新的」，装进来半年后改过的没人再看 |
| 内容重复 | sha256 相同，或正文相似度 > 0.9 | 几百个里必然有同一份换个名字 |
| 长期未用 | `lastUsedAt` 早于 90 天且 `useCount === 0` | 清理建议，不自动删 |
| 超预算 | `chars > 2000` | 会挤占记忆注入（`MEMORY-memory.md` 的注入预算） |
| 引用失效 | `byChat` 指向不存在的 id | 现在静默回退，用户根本不知道 |

### 批量操作

多选 → 打标签 / 收藏 / 移入分组 / 导出 / 删除。

**删除是本篇唯一的破坏性操作**，规则沿用现有备份机制，但**不能直接复用 `backup()`**：

- 二次确认，且确认文案里写**具体条数**（「确认删除 17 个人格？」）。
- 批量删除要**一个批次一个目录 + 一份 `manifest.json`**。现有的 `backup()`（`persona-repo.js:401`）
  每次调用都自己算时间戳建目录，17 个文件可能散成好几个目录；而 `pruneBackups()`
  只留最近 5 个目录，批量一大就会把这一批的一部分自己删掉。所以批量路径要：
  `mkdir .backup/<ts>/` 一次 → 逐份写入 → 写 `manifest.json`（`[{id, file, deletedAt}]`）。
- 撤销 = 读 `manifest.json`，把列出的文件逐个回拷，然后删掉该批次目录。
  **没有 manifest 就没有撤销**，只能人工去备份目录里翻。
- 不给「全选 + 删除」的一键组合。

## 八、P4：分发规模化（pack + 按需装）

### 索引加两层

```json
{
  "schema": 2,
  "packs": [{ "file": "packs/pack-0.jsonl", "from": 0, "to": 99, "count": 100, "bytes": 180000 }],
  "personas": [{ "id": "fatfish", "pack": 0, "…": "…" }]
}
```

`pack` 格式是 JSONL，一行一份，**每行自带 hash**：

```
{"id":"fatfish","sha256":"…","text":"---\nname: 大肥鱼\n…"}
```

### 三种安装路径

| 场景 | 走法 | 请求数（300 份） |
|---|---|---|
| 首次全装 / 一键更新 | 只下含待装 id 的 pack | 3 |
| 市场里装 1 个 | 单文件直链 `GET /personas/<file>`（已有能力） | 1 |
| 市场里装 6 个 | pack（阈值 ≥ 5 用 pack） | 1 |

规则一句话：**待装 ≥ 5 走 pack，否则逐条**。pack 里逐行验 sha，一行失败只影响那一行，
其余照装——沿用 `sync()` 现在「返回报告而不是抛错」的语义。

**pack 分支必须复用现有的三件事**，不能另写一套：`modified` 一律跳过、
`update` 覆盖前 `backup()`（`persona-repo.js:506`）、逐行验完后**逐文件原子写**。
pack 只是把「一次一个请求」换成「一次一批」，判定和备份语义要和逐条路径**逐字一致**，
否则同一批人格会因为走哪条路而得到不同结果。

### 体积账

- 每条索引 ~250 B（其中 sha256 占 64 B）→ 300 条 75 KB、1000 条 250 KB。
- 加 `desc`（限 60 字）+ `author` + `version` 约 +120 B → 1000 条 ≈ 370 KB。
- 所以：**`MAX_BYTES` 从 512 KB 提到 2 MB**（注释写明这是给索引留的余量，不是给正文）。
  正文上限仍是 `MAX_CHARS = 8000`，不动。
- **pack 要单独的字节上限（8 MB），不能直接抬全局常量。** 现在 `getText()` 只有一个
  `MAX_BYTES`（`persona-repo.js:82`）管所有请求；把全局抬到 8 MB，等于也允许一份 8 MB 的
  `index.json` 通过。正确做法是给 `getText(url, {maxBytes})` 加参数，索引仍 2 MB、pack 8 MB。
- 超过 2000 份再考虑「索引分片 + 服务端分片检索」，现在做是过度设计。

### 兼容

- 老版本读新索引：`packs` 是未知字段，`validateIndex` 不管它，逐条下载照旧能跑。
- 新版本读老索引：没有 `packs` → 回退逐条下载，行为不变。
- `minVersion` 不动（格式没变，只是多了分发路径）。

## 九、命名、撞名、去重、别名

几百个时这些必然发生，且都不该让用户自己处理。

| 问题 | 处理 |
|---|---|
| **id 撞名** | 远端索引里 id 必须全局唯一（生成脚本 `--check` 时报重复并退出 1）。本地装的时候若已有同名但 sha 不同且来源不同 → 装成 `<authorSlug>__<id>.md`，面板显示 `@作者/id`。**`authorSlug` 不能直接用作者名**：`safeFile` 只允许 `[A-Za-z0-9_-]+\.md`（`persona-repo.js:104`），而作者名是中文（阿柚、青柠、小鱼干）。索引里存一个 `authorSlug` 字段，没有就用 `sha256(author).slice(0,6)` |
| **同内容不同名** | 装前用 sha256 查重，命中就提示「和「X」是同一份」，默认跳过（可在预览里强制装） |
| **中文名记不住、英文 id 打不对** | front matter 加 `alias: 大鱼, 肥鱼`，进检索域。比拼音表便宜得多，也更准（作者自己知道别人怎么叫它） |
| **拼音搜索** | 暂不做。要内置一张拼音表（几十 KB）或引依赖，收益不如 `alias` 直接。等有人真的抱怨再说 |
| **删除后 prefs 残留** | 删人格保留 `prefs` 记录 30 天，同名重建能继承收藏；30 天后清理 |
| **删除后 `byChat` 残留** | 删除时**级联清掉** `config.persona.byChat` 里指向它的项（`remove` 与批量删除都要做）。不清就会持续制造「失效引用」，而失效引用现在只会静默回退到 default |

| 风险 | 表现 | 兜底 |

## 十三、明确不做

- **不引 SQLite / 全文检索引擎**。几百到几千条 JSON + substring 足够；引了就要处理迁移、损坏、并发。
  上限写在注释里：超过 5000 份再谈。
- **不把人格存数据库**。真源必须可 diff、可手改、可提 PR——这是 0.10.7 的核心结论。
- **不做磁盘子目录分组**。会同时破坏 `list()`、`seed()` 的「只补缺」和 `.synced` 的按名对齐。
  虚拟分组够用。
- **不做评分/评论/下载数**。要服务端和账号体系，与「零依赖、一个进程」冲突（0.10.7 已定）。
- **不做多人格同时上场**。一个群一个，避免提示词互相打架和 token 爆炸。
- **不做启动时自动同步**。人格突然变味比版本旧难受（0.10.7 已定，仍然成立）。
- **不做拼音搜索**（先靠 `alias`）。
- **不做全局快捷键**（和宿主抢按键）。
- **不在 `resolve()` 里做任何写操作**（统计只进内存）。

## 十四、需要拍板的三件事

1. **市场是单源还是多源？**
   现在 `persona.repo.sources` 支持多个 base，但语义是「换源兜底」（GitHub 挂了换 Gitee），
   不是「多个作者各自一个源」。真叫「市场」且几百个，多半来自多个仓库。
   多源要额外定：源优先级、id 冲突、信任分级（官方 / 社区）。
   **建议**：P1 只做单源（官方仓库），但索引里预留 `origin` 字段；多源留到真有第二个源。

2. **「装上即用」要不要？**
   0.10.7 的结论是「装完只进列表，不自动启用」（防人格突袭）。几百个时，
   市场里点「装上并给本群用」是最顺的动线，但它绕过了那条安全结论。
   **建议**：默认只装；「装上并用」做成显式第二按钮，且只在**当前会话**生效（不写全局默认）。

3. **使用统计要不要落盘？**
   落盘才能做「最近使用 / 常用 / 长期未用」三个排序与清理建议，但会在 `personas/` 下
   多一个用户态文件。不落盘就只能按名字排序，等于放弃治理视图。
   **建议**：落盘到 `.prefs.json`，并明确它不进 git、不随同步走。

## 十五、落地形态（已定 A：市场是 Roost 的一个页签）

### 15.1 为什么不放进侧边栏

DSH 的 `sidebar.panellist` 只接「图标 + label」，是一行**导航**；内容必须挂在根级 `main`
的 keyed slot，用同一个 id 对应过去（`app.asar` 里的插槽说明原文：*The same id addresses
the component registered in the layout's root-scoped `main` keyed slot; selecting a missing
main entry throws without changing the current selection*）。

dsh-roost 现在正是这个模型：`client.js:3456-3458`，`roost` 一个入口 + `RoostPage`。
所以侧边栏那一条**没有内容位**，市场只能作为 `RoostPage` 里的一个页签。

第二个侧边栏入口（`roost-personas`）是可行的退路，约 10 行；但它要占一行稀缺的导航位，
且两个 key 都得维护。**留到「一天要开好几次」再加，现在不加。**

### 15.2 信息架构

```
DSH 侧边栏                Roost 主区
┌──────┐   ┌─────────────────────────────────────────────────────────┐
│ 栖   │──▶│ 概览 · 接入 · 人格与情绪 · [市场] · 记忆 · 主动搭话 · … │
└──────┘   └─────────────────────────────────────────────────────────┘
                                  │
                                  ▼
              ┌───────────────────────────────────────────┐
              │  市场      我的      治理     ← 页内分段  │
              ├───────────────────────────────────────────┤
              │  [搜索 名称/标签/简介/作者/别名]   排序 ▾  │
              │  分类：全部 300 · 精选 45 · 有更新 4 · …  │
              │  标签：日常(31) 吐槽(22) 二次元(18) …     │
              │  ────────── 50 行 / 页 ──────────         │
              └───────────────────────────────────────────┘
```

> 原型（`原型-人格市场.html`）里「市场 / 我的 / 治理」是**顶级页签**，正式形态是**页内分段**。
> 评审原型时看的是内容与交互，别把它当成三个新页签。

### 15.3 页签：位置、命名、key

```js
const TABS = [
  ['overview', '概览'],
  ['setup', '接入'],
  ['her', '人格与情绪'],
  ['market', '市场'],      // ← 新增，紧跟 her
  ['memory', '记忆'],
  …
]
```

- key 用 `market`，不用 `persona`：`her` 已经占着「人格」的语义，两个都叫人格会分不清。
- 页签容器是 `flex-wrap: wrap`（`client.js:3387`），10 个页签在窄窗口会换行，不会破版；
  代价是标签必须短——所以叫「市场」两个字，**不挂角标**。
- 「有更新 N」的角标继续留在 her 页那个按钮上（已有），市场页里用「有更新」分类显示数量，
  不重复造第二个角标。

### 15.4 三个视图为什么合成一个页签

- 三者共享同一套查询参数（`q` / `tags` / `sort`）和同一份 catalog；
- 页签已经 9 个，再拆三个变 12 个，导航会散；
- 分段切换是「换切片」不是「换任务」，各自内存缓存，不重新请求远端。

### 15.5 与「人格与情绪」页的边界（这条最容易做乱）

| 动作 | 放哪 | 为什么 |
|---|---|---|
| 换人格 / 编辑 / 删除 | her 页 | 针对「我正在用的那一个」，就近操作 |
| 从仓库更新 N 个 | her 页保留 **+** 市场页「有更新」分类 | 同一个 `/personas/sync`，两处都是顺手动作，**不写两套实现** |
| 浏览 / 搜索 / 预览 / 装某一个 | 市场页 | 几百个时浏览要整页宽度和独立状态 |
| 按群指定 / 最近使用 | 市场页「我的」+ her 页选择器 | 选择器放 her 是因为「换」这个动作在那儿 |
| 体检 / 批量清理 | 市场页「治理」 | 维护动作，不是日常 |

**her 页要删的东西**：`repoOpen` 那一整块仓库面板（`client.js:1362-1428`，约 66 行），
换成一行「在市场里看全部 →」调 `onGo('market')`（`OverviewTab` 已有这个模式，`RoostPage`
把 `setTab` 传下去即可）。`loadRepo` 保留——它只负责算角标 `pending`；`runSync` 保留。

**her 页的列表本身也要收。** 它现在是全量 `.map()`（`client.js:1454`），300 份就是 300 行 ×
3 个按钮——市场分页了、这一页没分页，等于把问题搬了个地方。两条路选一条：

- 只显示「置顶 + 最近 5 个 + 当前」+ 一行「在市场里看全部」（推荐，her 页回到「改我正在用的」）；
- 或复用 `MarketTab` 的列表组件，`size=20`。

不改这条，P1 的收益会被 her 页吃掉一半。

### 15.6 布局：宽屏 / 窄栏两套

| 宽度 | 变化 |
|---|---|
| ≥ 720px | 单列列表：图标 30 + 名称/简介 `1fr` + 版本/字数 84 + 动作 `auto` |
| < 560px | 隐藏版本/字数列；分类与标签**横滚**不换行；预览从右侧抽屉改成底部 74vh 面板；治理卡片两列；行高与按钮缩小 |

**用容器查询，不用媒体查询**：主区宽度取决于侧边栏是否展开、窗口是否分屏，跟视口不是一回事。
`container-type: inline-size` + `@container (max-width:560px)`。原型已按 420px 验证过
（右上角「窄栏」按钮）。

两条落地注意：

- **原型里的 `.app` 是示意类名。** 真实面板要给市场页加一个自己的包裹元素（如 `.roost-market`）
  做容器，不能指望 `RoostPage` 那层 `roost-scroll-body`——那是整页的滚动容器。
- `container-type: inline-size` 会让内部**绝对定位元素以它为参照**。预览抽屉、选择器浮层
  要挂在包裹层**外面**（或改成 fixed），否则会被裁切。这条必须在真机上试，别只信原型。

### 15.7 状态与数据流

```
进页签        → 立刻画磁盘缓存（query?stale=1）→ 后台 query?force=1 刷新
切「我的」    → scope=local（同一份 catalog，不打远端）
切「治理」    → GET /personas/gov（byChat + 失效引用 + 体检摘要）
装 / 更新 / 恢复 → 失效三个视图的缓存 → 只重拉当前视图
```

**首屏必须两段式。** 现在 `loadIndex()`（`persona-repo.js:267-328`）是「2 个源 × 2 次重试 ×
15 s 超时」全部失败之后才回落磁盘缓存——墙内 GitHub 挂起时，第一次打开市场就是几十秒白屏。
所以 query 要支持 `?stale=1`：命中磁盘缓存直接返回并带 `stale:true`，页面先画，后台再
`?force=1` 刷新。**这条不是优化，是可用性。**

- 搜索：本地输入 → 120 ms debounce → query；**输入法合成期间不请求**（`e.isComposing`）。
- 切视图**保留** `q` 和 `tags`、重置 `page`：搜「猫」→ 市场看有哪些 → 切「我的」看装没装，
  这是真实动线，清空反而要多打一遍。
- **离线时 `state` 要能缺省。** 切「我的」不打远端，但 `update / modified` 依赖远端索引；
  没有索引（或缓存过期）时按「已装」显示，**不显示「有更新」角标**，也不因此让页面空着。
- 远端索引失败：先画本地缓存 + 一行灰字「用的是缓存清单」，**不弹 toast**（0.10.7 的结论）。
- 索引 5 分钟 TTL 内进页不重复请求（`INDEX_TTL`）；用户点「刷新」才 `force=1`。

### 15.10 验收

- 点「市场」页签 → 首屏 ≤ 200 ms（300 份，catalog 已建）

- 420px 窄栏可用，**不出现横向滚动条**
- 列表 DOM ≤ 50 行
- 10 个页签在 900px 宽下换行不破版
- **远端不可达**时市场页仍能列出缓存清单，本地人格照常可编辑；只是没有「有更新」角标

### 15.11 回退

- 页签加一行 + `MarketTab` 是独立组件：出问题删 `TABS` 那一行和组件，her 页恢复仓库面板即可。
- `localStorage['roost.tab']` 存过 `market` 之后插件回退：`TABS.some(...)` 会把它判成无效，
  自动退回概览（`client.js:3185-3191` 已有这个保护），不会白屏。
