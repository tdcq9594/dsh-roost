## 三、扩展本体：标准 MCP server

### 3.1 目录与清单

```
<dataDir>/extensions/
  API.md / extension.d.ts        ← 启动时自动写（内容哈希比对，没变不重写）
  ext-groups.json                ← 影子权限组（仅 capabilities.json 不存在时用，§4.2）
  bili/
    plugin.json                  ← 唯一清单（仓内同名的那份原样复制，零转换）
    .source.json                 ← 来源标记（市场装的 vs 用户手写）
  .<id>.installing/               ← 原子落位暂存（点开头，扫描器不认）
<dataDir>/secrets/
  <id>.json                      ← v3.7 方案 L：一扩展一令牌明文（0600，**不进 E4 包**，§5.4）
```

⚠️ **三点口径（v3.3 统一；v3.2 有三套互斥写法）**：

1. **清单只有 `plugin.json` 一种**：仓内 `qq-bot-roost-plugins/plugins/<id>/plugin.json`，安装后 `<dataDir>/extensions/<id>/plugin.json`，**同一份文件原样复制**（`market.js:545` 的 `fs.cp` 本就整目录拷）。取消 `extension.json` 与任何格式转换层；用 `kind: "dsh-extension"` 区分框架插件与扩展（§8.1）。
2. **`.source.json` 每扩展目录一份**：aurabot 的读法是 `join(dirOf(id), SOURCE_FILE)`（`community.js:119`；其原名 `.aurabot-source.json`，`:19`）——顶层单文件无法区分「市场装的 / 用户手写」，而 foreign 保护全靠它。名字沿用我们的 `.source.json`，只要求本仓一致。
3. **本机安装目录 = `<dataDir>/extensions/`，即 `~/.dsh/dsh-roost/extensions/`**（`config.js:15-16`）；仓内 `plugins/<id>/` 只是发布结构。该目录当前尚不存在，8a 创建。

`extensions/`、`ext-groups.json`、`agent-sessions.json` 都不在 `backup.js:49` 的 `SKIP` 里，`walk()` 全目录递归 → **自动进 E4 备份包**；但 `.installing` / `.old` 点目录同样会被打包（`walk()` 不按点目录通用跳过），必须显式加进 `SKIP`（§11 坑 4）。⚠️ **v3.7：`secrets/` 必须显式加进 `SKIP` 且从 E4 包排除** —— 里面是方案 L 的令牌明文，进包等于把长期凭据复制到备份文件；`cordis.patch.yml` 的写前备份虽已无明文（受管块只放引用名），仍按 §3.2 保持脱敏。备份还原后若 `secrets/` 缺失，宿主在扩展首次调用前**重新生成令牌并写回**，面板提示「扩展令牌已重新生成」（§5.4 / §13）。

清单字段（**只存元数据与挂载参数，不存连接实现**）：

```json
{
  "api": 1,
  "kind": "dsh-extension",
  "id": "bili",
  "name": "刷 B 站",
  "description": "读取 B 站动态与视频信息",
  "version": "1.0.0",
  "transport": "stdio",
  "command": "node",
  "args": ["./server.mjs"],
  "serverName": "bili",
  "mounts": ["*"],
  "buckets": ["owner"],
  "memory": { "writeTarget": "ext:bili", "visibility": "all", "onClear": "keep", "maxRows": 200 },
  "capabilities": ["network"],
  "sha256": "...", "size": 0, "publishedAt": "..."
}
```

- `id` 必须等于目录名，正则收紧为 **`^[a-z][a-z0-9-]{1,31}$`**（总长 2–32）。官方 `serverName` 限 `[A-Za-z0-9_-]{1,32}`；**强制 `serverName === id`** 让 `mcp__<id>__*`（工具名）、`mcp:<id>`（§3.5）、`group:ext_<id>`（§4.2）由 id 推导，零映射表。⚠️ **二轮复核订正**：官方 public-name 的 12-hex 哈希后缀**不是**由 `serverName` 限制触发，而是由 `rawName` 含非法字符或整体超过 64 字符触发（`mcp-client/src/tools.ts`）；短横线与大写本身合法，实测 `matchPattern('mcp__bili__feed_abc123', 'mcp__*') === true`，带哈希后缀仍能被白名单匹配。另：id 里的 `-` **不能直接拼进凭据 REF**，见 §5.4 的规范化规则。
- `name` / `description` 必填（§3.5 生成 usage 用）；`usage?: string` 可选覆盖自动文案。
- 市场元数据（author / license / minRoostVersion / revoked / path）**只在 `index.json` 里**，不重复进清单；清单里的 `sha256` / `size` / `publishedAt` 供本地完整性校验。
- 记忆字段以 §5.7 的 `writeTarget` / `visibility` 与 §5.6 的 `onClear` 为准；v3.2 示例里的 `store: "isolated"` / `inject` 已废弃。
- `url` 形态只认回环；`stdio` 的 command/args 由用户确认后才执行。

### 3.2 挂载：受管块同步

`ext-patch.js` 把清单翻译成一条 `@deepseek-ai/dsh-mcp-client` 配置，写进 `~/.dsh/profiles/<profile>/cordis.patch.yml` 的**受管块**（起止注释标记）。本机实测格式（`cordis.patch.yml:48-62`）是「`- insert:` + 字段全在 `config` 内」：

**v3.7 定稿配置（方案 L，可直接照做）**：

```yaml
- insert:
    - id: mcp-bili
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: bili
        transport: stdio
        command: node
        args: ['<roost>/src/ext-launcher.mjs']
        env:
          ROOST_API_URL: 'http://127.0.0.1:<port>/v1'
          ROOST_EXT_ID: 'bili'
          ROOST_LAUNCHER_DIR: '<dataDir>'
        failOnStartupError: false
```

- `command` 指向**宿主自带 launcher**，不是扩展清单里的 `command`；真 server 的命令/参数由 launcher 从 `<dataDir>/extensions/<id>/plugin.json` 读，扩展仓永远不能直接指定被 spawn 的可执行文件或往受管块塞字段。
- **`env` 里只有引用名与宿主路径，没有任何令牌值，也没有 `!!js` / YAML tag**。`ROOST_LAUNCHER_DIR` 是宿主组件之间的参数，launcher `spawn` 真 server 时**不得透传**它、`ROOST_EXT_ID` 之外的宿主私有路径也不传；断言「扩展进程 env 里读不到 `dataDir` 全路径」进 8c。
- launcher 启动时读 `<dataDir>/secrets/<id>.json` 的 `{token, ref}`，把 `ROOST_API_TOKEN` / `ROOST_API_URL` / `ROOST_EXT_ID` 注入真 server 的子进程 env，`stdio: 'inherit'` 透传 MCP 协议、退出码与信号透传（真机原型见 §10.9）。官方 `buildChildEnv()` = `scrubbedParentEnv() + config.env`，显式 env 能进子进程、父环境里含 `TOKEN` 的变量会被丢弃，已实测（§10.9）。
- ⚠️ **v3.6 历史原稿已作废**：它写的是 `expandTemplates: true` + `env.ROOST_API_TOKEN: '${credential:REF}'`，这套模板解析在本机 `DSH 0.2.2-rc.1` 的配置 schema / 官方源码 / 全 `node_modules` **零命中**（§10.8）。`- insert:` + `config{}` 的**结构**仍成立，字段内容以本节 v3.7 版为准。

- `env` 官方支持；`toolCallTimeoutMs` 默认 60,000，需要时再显式设（本机 graphflow 条目未写）。**`maxInstructionBytes` 不在受管块里自定义**，沿用官方默认 32,768：它是**拒连**而非截断，设低了会拒掉整个连接、该扩展全部工具不可用（多工具 server 的 instructions 含工具清单与示例，10–20 KB 很常见），设高了又防不住小于阈值的恶意说明 —— **阈值既不防恶意、只误伤正常扩展**，宿主不再叠加二次阈值。连接确因超长被拒时，面板提示「该扩展因注入说明超长未连接」（§13）。
- **令牌不落 patch（v3.7 方案 L）**：值由 `ext-registry` 生成后写进 `<dataDir>/secrets/<id>.json`（0600、不进 E4 包），`api.clients` 只存 sha256；受管块只放引用名。**轮换** = 重写 secrets + 更新 hash + 触发该 MCP 连接 reload（launcher 每次启动重读文件，实测可行）；**吊销** = 删 `api.clients` 记录；**卸载** = 删记录 + secrets + 受管块条目。`ctx.credentials` **不用于这条链路**（P3 实测：它是 async 名字引用、provider 不写 `process.env`、launcher 是独立进程调不到 Cordis 服务），**REF 规范化规则保留作 env 变量名 / 审计键 / secrets 文件名的命名规范**（§5.4 / §9-#30 / §10.9）。
- 只增删受管块内的行，**用户手写的条目一律不动**；写前备份、幂等、写完校验 YAML 可解析、失败回滚。**受管块校验必须拒绝任何 `!!js` / YAML tag、拒绝扩展仓自带 `env` 键** —— 方案 L 的受管块零表达式，扩展仓只提供 `plugin.json` 元数据，命令与参数由 launcher 从清单读。v3.2 那次「备份连带 env 明文」在方案 L 下不再可能发生（值根本不在 patch 里），脱敏规矩仍保留作纵深防御。
- **profile 不能硬编码**：仓库根 `cordis.patch.yml` 只有 `roost` + 两个 preset，**没有 MCP 条目、也不会被同步覆盖**；MCP 条目只在 `~/.dsh/profiles/<profile>/cordis.patch.yml`。复用 `src/update.js:191-203` 的 `findProfileDir()`。当前 `~/.dsh/profiles/` 下只有 `desktop` 一个。
- DSH 的 HMR 检测到配置变化后 in-place reload 该 MCP 连接（官方 README：「Editing the configuration entry reloads the server connection in place, and unchanged names stay unchanged」）。⚠️ `architecture.md` 注明 `base enables config-only dsh-hmr; headless, SDK and ACP disable it` —— **v3.6 已实测收口**：官方 `dsh-hmr/README.md` 写明「启动器提供 `profileContext` 时 base 组合启用 HMR；headless / SDK / ACP 在 YAML 里禁用」；隔离 CLI 实例实测 `ctx.get('profileContext')` 存在（10 个字段）、`ctx.get('hmr')` 服务可用，组合树里 `- id: hmr` 的 `disabled: !!js '!ctx.get("profileContext")'` 求值为 false。**真机 desktop 未起进程，按同档机制推断、不外推为「desktop 已实测」**（差异见 §10.8）。⚠️ **v3.7 补充**：这条 in-place reload 只保证「配置条目变了会重建连接」，**不保证 `!!js` 表达式被重新求值**（§10.9 实测 reload 后仍是旧值）。方案 L 不依赖表达式求值——launcher 是每次连接重建时新起的进程，启动时读私有 secrets 的最新值，所以**轮换只需重建 MCP 连接，不需重启 DSH**。

**保守开关**：默认先「生成 YAML 片段 + 一键复制」，用户自己贴一次；实测确认 HMR 可靠后，再把「自动写入受管块」作为开关放开。理由：这是宿主 profile 文件，最坏情况应止于手动。

### 3.3 装一个扩展为什么就多一个功能

```
清单落位 → 受管块加一条 → DSH HMR reload
  → MCP client tools/list → 注册成 mcp__bili__feed → 进 agent.ctx.tools.schemas()
  → 下一轮模型工具表多一项 → 能力页 pool 自动纳入
  → 模型调用 → 全局 ctx.tools.guard() 按 QQ 档位拦 → 执行
```

**这一段我们 0 行代码**（DSH 官方链路）。注意「模型工具表多一项」≠「所有档位能用」——后者的默认开放在 §4.2 单独保证。

| 自造 `/call` / 快照 / `gen` | 全部删除 |

### 3.5 提示词：usage section + 独立会话 instructions 过滤（v3.3 定稿，C+ 方案）

**结论：扩展不写 MCP `instructions`；由 dsh-roost 从清单生成按 QQ 会话注册的 usage section；独立 Agent 会话在自己的 scope 内过滤第三方 instructions —— 8a 在「同名空 section 遮蔽」与「`system-prompt/assemble` waterfall 过滤」间实测择一，优先后者（详见 ③）。**

**官方事实（v3.3 二轮核对直接查到源码，v3.2 的前提因此被推翻）**：

| 事实 | 出处 |
|---|---|
| instructions 注入成**每 server 一个** section：`name: \`mcp:${server}\``、`order: getSectionOrder('MCP_SERVERS')`、`text: () => connection.instructions()`、`interpolate: false` | `packages/mcp/mcp-client/src/server-context.ts` 的 `registerServerContext()` |
| 「A scoped section shadows a global section with the same name」；**同 layer 重复注册抛错**；`section()` 返回 Cordis effect disposer | `docs/subsystems/system-prompt.md` |
| `instructions` 是连接后运行时返回，清单拿不到内容；`maxInstructionBytes`（默认 32,768）超限**拒连**而非截断；无 `includeInstructions` 开关 | `packages/mcp/mcp-client/README.md` |
| 工具表由 tool provider 独立贡献，section 遮蔽**不影响工具可见性** | 同上 + `subsystems/system-prompt.md` |

v3.2 的 C 方案认为「同进程同 patch 无法按会话屏蔽 instructions」——**这条前提不成立**。但修正方向不是回到「给 instructions 设限」，而是把 C 升级成硬隔离：**不阻止第三方写，但让它进不了独立会话**。

**清单**：`name` / `description` 必填；可选 `usage?: string`。**不设 `instructionsBytes`**——扩展不该有 instructions。

#### ① QQ 会话：宿主生成 usage section（`src/ext-usage.js`）

```js
{
  name: `ext:${id}:usage`,
  order: 950,                       // 暂定值，非契约：8a 用 getSectionOrder() 校准、确认不与现有段冲突；同序按 name 的 code-unit 序（官方规则）保证稳定，现有 roost-persona 是 905
  // 动态函数：每次组装重新求值，面板改 usage 后「下一个请求」就生效，无需重载扩展 / 重启 DSH
  text: () => `【扩展：${id}】${liveUsage(id)}（工具：mcp__${id}__*）`,
  interpolate: false,               // 清单文本里可能有 {{...}}，按字面保留
}
```

- **`text` 必须是函数、不是静态字符串**（v3.4，参考 `dsh-persona-dafeiyu`：它的 section `text` 是动态函数，切换后下一个请求即生效、无需重启）。**数据源定死**：`ext-registry.js` 在内存持 `usageCache: Map<id, string>`，`liveUsage(id)` 只读它（零 IO）；**失效钩子** `ext-registry.refreshUsage(id)` 在「面板保存 usage」「安装 / 更新 / 卸载扩展」「启动加载清单」三处调用。**不要在 `text` 里直接读文件** —— 每轮 assembly 都 IO 会拖慢首 token。
- 单条上限 **200 字**、所有 usage 合计 **2 KB**，超出截断并记 warn（内容由我们生成，所以这次真能截）。
- **注册时机**：`mount(agent, chat)` 里按会话注册；关扩展 / 卸载 / 关会话走官方 disposer 整组撤销。
- 面板显示每个扩展的 usage 预览与占用字节数；用户编辑 `usage` 会写回清单，**市场装的扩展须同步使 `sha256` 失效并在面板标注「已本地修改，不再参与更新校验」**（v3.2 漏了这条）。
- ⚠️ **本仓目前只有 11 处 `agent.ctx.systemPrompt.context()`（首处 `host.js:2923`、`order:905`）、零处 `section()`**。`section()` 是本次新引入的 API，8a 必须验证它与现有 11 处 `context()` 的排序 / 遮蔽 / 共存；`order` 应由 `getSectionOrder()` 取官方分配值，不要凭现有 905 猜。

#### ② 独立 Agent 会话：scope 内过滤 instructions（候选 A：同名空 section 遮蔽，**备选**）

> **先读 ③**：8a 要在 A（本节）与 B（`system-prompt/assemble` waterfall）间实测择一，**优先 B**。本节是候选 A 的完整实现说明，**不是已选定的方案**；实现前先看 ③ 的对比表，别直接照本节落地。

若选 A，`/v1/agent.new` 时在**该会话的 `agent.ctx` scoped context**（必须是 `agent.ctx`；用宿主全局 ctx 会连带影响 QQ 会话）按已装扩展列表注册 N 个：

```js
for (const id of installedExtIds) {
  offs.push(agent.ctx.systemPrompt.section({
    name: `mcp:${id}`,                                   // 与 DSH 注入的 section 同名
    order: agent.ctx.systemPrompt.getSectionOrder('MCP_SERVERS'),
    text: '',                                            // 空文本 → 遮蔽
    interpolate: false,
  }));
}
```

- **若选 A**，该机制把**第三方 server 自行返回的 instructions** 从独立会话的 system prompt 里挤掉；**人格、记忆、工具说明等其它 section 一个不少，工具表也全在** → 仅就独立会话提示词层而言零功能折损（整篇的折损边界见 §13）。usage section 独立会话本就默认不注册（§9-#19），**不在「保留清单」里** —— 这是既有决策，不是本机制造成的折损。
- **若选 A**，QQ 会话**不注册**这些空 section，扩展说明照常可见；选 B 时 QQ 会话根本不进该 scope 的 listener，效果相同。
- 这是**提示词层**动作，不改档位 / 次数 / 工具可见性 → 不违反 §9-#4「独立会话不监管」。独立会话默认不注册 usage section（§9-#19）保持不变。
- 关会话时整组 disposer 撤销；卸载扩展时同步撤掉对应那条。
- **QQ 侧边界**：宿主**不设自定义 `maxInstructionBytes`**（§3.2），沿用官方默认 32,768 的拒连线。第三方 instructions 会照常进 QQ 会话，宿主**不做 per-session 抑制、也不做截断**（这两条在 v3.2 就已被官方机制否掉）；唯一例外是连接因超长被拒时面板给出提示。详见 §13。

#### ③ 8a 实测择一、降级链（v3.3 二轮修订）

**8a 在两者间实测择一，优先 B**。**判据写死**：B 的三条断言（独立会话过滤生效 / QQ 会话 instructions 仍在 / 关会话 listener 真撤销）**全绿即选 B**；否则先核 A 的「`agent.ctx` 与 MCP client 不同 layer」条件，满足才选 A；**两者都不满足才**落下面的降级探测，不得默认照 ② 落地。

| | A：同名空 section 遮蔽（上文 ②） | **B：`system-prompt/assemble` waterfall 过滤（推荐）** |
|---|---|---|
| 做法 | 按已装扩展注册 N 个 `mcp:<id>` 空 section | 在独立会话 scope 注册一个 `system-prompt/assemble` listener，过滤 name 以 `mcp:` 开头的 sections |
| 官方依据 | 「A scoped section shadows a global section with the same name」；`PromptLayer` 报错原文甚至推荐「for a per-agent override, register through that agent's `agent.ctx` instead」 | 该事件是 **Scope-filtered dispatch**（"scoped listeners receive only that scope's assemblies"）、返回 text authoritative、`tool declarations remain provider-owned` |
| 风险 | 若 `agent.ctx` 与 MCP client 注册**同 layer**，触发「duplicates within one layer throw」 | 无 duplicate 风险；仅当注册了 `complete` section 时会被绕过（我们不注册） |

**A 的断言（与 B 对称，8a 用同一组）**：① 独立会话的 system prompt 里读不到测试扩展的 instructions；② QQ 会话读得到；③ 工具表在两种会话里都还在；④ 关会话后遮蔽注册被 disposer 撤销。A 的**前置条件**是「`agent.ctx` 与 MCP client 注册不同 layer」——不满足会直接抛错，这不算断言失败。

二轮复核确认 **A 的空 section 遮蔽成立**：官方 `packages/core/system-prompt/src/index.ts` 的 `renderPrompt()` 里唯一丢弃空文本的 `.filter(text => text.length > 0)` 发生在 `layers.merge(scope, ...)`（含 scoped shadow）**之后**，且没有回退 global 的逻辑，所以 `text: ''` 仍占住 name 并遮蔽；`PromptContext` 的 "Empty text contributes nothing" 同理，只影响 context 渲染，不影响 section 遮蔽。

- **B 的落地要求**：listener 必须注册在**独立会话的 `agent.ctx` scoped context**（Scope-filtered dispatch 决定它只收到该 scope 的 assembly，不会影响 QQ 会话），保存返回的 disposer，在 `/v1/agent.close` / teardown 时撤销；listener 内**只过滤 `mcp:` 前缀的 section，不要动 `tools` 字段**（`tool declarations remain provider-owned`）。8a 实测三件事：独立会话过滤生效、QQ 会话 instructions 仍在、关会话后 listener 真撤销。官方 `assemble()` 的 waterfall 在 `renderPrompt()` 的空文本过滤**之前**执行，与 A 的遮蔽逻辑无顺序冲突。

- **降级（A/B 都不可用）**：退到「安装时一次性 MCP 握手读 `InitializeResult.instructions` + 面板黄卡 + 市场标注」。官方 `probeServer()` 的 `McpProbeSuccess` **没有 instructions 字段**（v3.2 的「8a 实测 probeServer」验收项据此作废），要自写约 60 行短连接探测。⚠️ **一旦走这条，独立会话的 instructions 隔离就从硬机制退化为软提示**，§9-#19 的「不是文档自律」不再成立，必须在 G0 结论与 §13 记为已知边界。
- **`complete: true` 明确否决**：官方 `assemble()` 在 `completeSection` 存在时执行 `sections: completeSection === undefined ? transformed.sections : [completeSection]`，人格 / 记忆 / usage **全丢**，与「零功能折损」直接矛盾，不得作为降级。
- **§13 不再写「无法阻止第三方 instructions」**；硬边界是 scope 内的 shadow 或 waterfall，残余风险只剩 8a 的择一实测。
- 无论选 A 还是 B，**工具表、人格、记忆都保留**；独立会话默认不注册 usage section（§9-#19）保持不变。

**能力预算（工具输出）**：除次数外限制单次工具返回长度（默认 4 KB，超出截断并标注）。实现位置是官方 `tools/post-execute` 的 `PostToolDecision { kind:'accept', content:[...] }` 替换（`subsystems/tools.md`）——它是**内容替换而非长度硬闸**，只在结果进模型前替换，不影响扩展实际产生的数据量与网络往返。

## 四、QQ 会话的权限与次数（权限内核一处统一 deny-first 过滤 + 安装时初始化两条路径）

> 标题订正：v3.2 写「内核 0 行」不准确。§4.1 的「独立会话不监管」确实不动现有 guard，但 §4.2 要**改 `resolvePolicy()` 一处统一 deny-first 过滤**（v3.5 定稿，见下）、给 **`host.js:4331` 的启用 handler** 加影子组合并钩子、新增 `ext-groups.js`，并给 `capabilities.json` 加 `forceDeny` 持久化字段。**改动集中在 capabilities 与其启用调用点，不是零行**；`accumulateAllow()` 不动。

### 4.1 边界：鉴权 ≠ 监管

| | QQ 会话 | 独立 Agent 会话 |
|---|---|---|
| 档位 allow/deny | ✅ 六档 | **不做** |
| 次数 / 输出预算 | ✅ quota + byBucket | **不做** |
| `mounts` 按会话收工具 | ✅ `restrictTurnTools()` | **不做**（看全部已挂扩展） |
| `/v1` Bearer + scope + 限频 + 幂等 + 审计 | — | ✅ **保留** |

**主人决策：独立 Agent 会话不纳入监管**。它服务于游戏裁判这类场景，没有「这一句是谁说的」，档位与次数无从判定；由 `/v1` 客户端自行负责。dsh-roost 对这条通道只做**接入鉴权**（谁能调），不做**行为监管**（能调几次、哪档能用）。

因此 `mountToolGuard` 的「只对 QQ 会话生效」判据（`sessions.list()` 里有没有这个 sessionId，`host.js:763` 的 `if(!mine) return undefined`）**保持不动**——`/v1/agent.*` 不写 `sessions.json`，天然落在监管之外。

**「监管」在本文的明确定义**：仅指**档位 allow/deny、quota 次数、按 `mounts` 收工具可见性**这三类（§4.1 表）。§3.5 在独立会话做 instructions 过滤属**提示词层**，不在此定义内，因此不违反 §9-#4。v3.2 的「内核 0 行」结论**只对独立会话成立**；QQ 会话恰恰是 §4.2 改 `resolvePolicy()` 统一 deny-first、加启用 handler 钩子、新增 `ext-groups.js` 与 `forceDeny` 配置字段的那一侧（§四 标题已订正；v3.5 起 `accumulateAllow()` 不动）。

⚠️ 措辞订正：v3.2 写「本来就**刻意**不写 `sessions.json`」，但 `/v1` 当前尚未实现，这不是既有设计而是本方案的约定。8d 验收里的「若以后补了 sessions 映射，监管会意外生效」因此是**真实接线风险**，不是回归项。

### 4.2 默认全局可调取：用 groups 机制保住（P0-1 修复）

问题：`capabilities.js:116` 白名单语义是「没写 = 不给」，`defaultStore()`（`:118`）只给 `owner: ['*']`，`admin/member` 是固定白名单。新装的 `mcp__*` 和 `ext_memory_search` 对非 owner 档**默认全 deny**，与「默认全局可调取」相反。

解法（**改 `resolvePolicy()` 一处统一 deny-first 过滤、`accumulateAllow()` 不动**，复用现成的 `groups` 与 `matchPattern`；v3.5 修订，详见本节 P0-1）：`capabilities.js:143-148` 的 `store.groups` 已有 4 组；`matchPattern():171` 只做通配，**`group:` 分支实际在 `expandAllow():203-213`** 遍历 `pool` 展开（v3.2 把两者张冠李戴）。

**关键语义**：`accumulateAllow()`（函数体 `capabilities.js:273`，`:282` 的 `BUCKET_ORDER.slice(idx)`）是「这一档 + 所有更低的档」对 allow / deny **都增量累加**；`BUCKET_ORDER`（`:34`）从高到低 `owner→admin→manager→helper→member→unknown`。所以**只要在 `member.allow` 追加一次组，五档就全部自动继承**，不用逐档写四遍。`unknown` 最末、累加只含自己，不给扩展组。

⚠️ `accumulateAllow` 的真实语义是「**无 `allow` 字段 = 继承低档、`allow: []` = 断链**」（`:292-295`），与 `:116` 注释字面有张力；写配置时别把 `{}` 和 `{allow: []}` 混用。

安装扩展时，`ext-registry` 在 `capabilities.json` 里自动写入：

```js
groups: {
  ext_bili:       { match: ['mcp__bili__*'], label: '刷 B 站' },
  ext_memory_read:{ match: ['ext_memory_search'], label: '扩展记忆检索' },
}
defaults: {
  owner:   { allow: ['*'] },                                  // 不动
  admin:   { allow: [/* 原样保留 */, 'ext_memory_note'] },    // 只追加写工具
  manager: { /* 原样保留 */ },
  helper:  { /* 原样保留 */ },
  member:  { allow: [/* 原样保留 */, 'group:ext_bili', 'group:ext_memory_read'] },
  unknown: { /* 原样保留，绝不重写 */ },
}
```

**v3.3 关键：安装时的两条路径（v3.2 完全没考虑）**

`capability-store.js:52-60` 的启用判据是「**文件存在**」；`host.js:321` 未启用时 `planByCapabilities()` 直接返回 `null` → 完全走旧逻辑（全放开）。所以**安装扩展绝不能盲目创建 `capabilities.json`**，那等于替用户启用能力页，从全放开切成白名单，与「默认全局可调取」正好相反。

| 场景 | 做法 |
|---|---|
| `capabilities.json` **已存在** | `get()` → 只**追加** `group:ext_<id>` / `ext_memory_note` / groups 定义 → `write()` 传完整子对象。**不能用 `patch()`**：它是顶层浅合并，注释明确要求调用方给完整子对象。保留用户手改内容（本机 `unknown.allow` 实际是四项，不是 `defaultStore():140` 的 `['qq_send']`） |
| **不存在** | **不创建文件**，保持旧逻辑全放开；把同一份 groups 定义与应追加项写进 `ext-groups.json`（纯声明，**不参与运行期判定**）。用户日后点「启用能力页」时，**在 `host.js:4331-4350` 的启用 handler 里**把影子组的 `groups` 定义 + `member.allow` 引用合进传给 `init(seed)` 的 seed。⚠️ **主路径的合并点在调用点**（`init()` 未启用分支只是 G0 实测失败时的备选落点，见 §10.1，**二者择一、不得双改**）：`host.js:4332` 先构造 `seed = { defaults: {} }`，`4336-4349` 再由 `cfg.permissions` 循环给 owner / admin / member / unknown 四档填 `allow`（`GUEST_KEEP_TOOLS`），`4350` 才 `init(seed)`；`capability-store.js:81` 是 `{...defaultStore(), ...seed}` 的**顶层浅合并**。全程**不读 `ext-groups.json`**，且 `init()` 在文件已存在时直接 `return get()`。不改 handler 的后果：`member.allow` 里根本没有 `group:ext_bili` 引用（所以**不会**报「分组不存在」，那只在「有引用、缺定义」时才出现），而是回落 `defaultStore():139` 的固定白名单 → `mcp__bili__feed` 对非 owner 档 **deny，启用后扩展静默断档**。补上后 `normalizeStore():496` 的 `{...D.groups, ...raw.groups}` 与 `expandAllow():203` 的 `group:` 分支现成可用。⚠️ seed 合并必须是**追加**、**不是整档替换 `defaults`**，否则会冲掉用户/默认档位白名单：主路径追加到 `seed.defaults.member.allow`（沿用 `host.js:4332-4347` 的 `GUEST_KEEP_TOOLS` 那套），备选落点追加到 `base.defaults.member.allow`（`base = {...defaultStore(), ...seed}` 顶层浅合并后两者同引用），**两者都必须追加** |

⚠️ **`groups` 也要合并、不能整块替换**（v3.4 补充）：`init()` 是 `{...defaultStore(), ...seed}` 的**顶层浅合并**，直接 `seed.groups = extGroups` 会把默认的 `mcp / files / ops / github` 组整块冲掉，G1 会表现成「默认组全没了」。正确写法 `seed.groups = { ...defaultStore().groups, ...extGroups }`；`host.js:28` 当前**没有 import `defaultStore`**，8b 要补这一行 import。

### 5.1 数据结构：独立目录分文件（v3.4 修订，替代 memory.json 的 ext 桶）

**为什么改**（2026-11-10 市场调研，§10.7）：`dsh-soul-md`（51.6k 下载）把长期记忆存成 `$DSH_HOME/soul-md/memory/` 下的 `global.md` + 每卡一个文件，而不是塞进一个总文件；`hindsight`（113.5k）同样按仓库分记忆库。我们的原设计把 ext 桶塞进 `memory.json`，§12 风险表里正有「ext 桶膨胀撑爆 memory.json」——**改为每个扩展一个文件，这条风险直接消失，同时省掉对 `memory.js` 的 9 处改动**。

**新结构**

```
<dataDir>/ext-memory/
  <extId>.json        { version:1, rows:[{ text, w, at, until, src, expiredBy }], meta:{ archivedAt?, onClear?, maxRows? } }

}
```

**`private` 判定（P1-6 修复）**：只用 `bucket === 'owner'` 会误伤——主人在**群里**说话时回话是公开的，不能把私密条目念给群友听；只用 `kind === 'group'` 又会让主人在群里读不到。正确判据：

```
private 行命中条件 = (kind === 'c2c') && (bucket === 'owner' || bucket === 'admin')
```

依据 `tools.js:138-140` 的注释：注释原文讲的是「`bucket === 'owner'` 在主人所在的群里同样成立（`permissions.js` 的 `bucketOf()` 根本不看 chat kind），**只判 bucket 会让『主人在群里随口一句』变成『群友能查别群』**」。即 **kind 必须参与隐私判定**，与此处「身份档位 + 会话场景双条件」的结论一致；v3.2 那句「身份档位决定能不能查、会话场景决定能不能当众说出来」是方案自撰的概括，不是注释原文，已订正。

### 5.4 两个写入入口、两个读取工具（P1-5 修复）

v3 把「扩展后台写」和「模型在 QQ 会话里写」混进同一个 `ext_memory_note`，导致「宿主按调用来源定 extId」在后者根本不成立（调用来源是模型，不是某个扩展）。拆开：

| 入口 | 形态 | `extId` 怎么来 | 判定 |
|---|---|---|---|
| **扩展后台写** | `POST /v1/memory/ext.add` | **由客户端令牌绑定**，不接受 body 里的 `extId` | `/v1` scope `memory:write`；不看 QQ 档位、不计 quota |
| **模型在 QQ 会话写** | 工具 `ext_memory_note({ extId, fact })` | 由工具参数指定**目标命名空间** | 宿主按 `caller().bucket` 查 `byBucket[bucket].write` 白名单，再走 §4.2 的档位 allow/deny 与 quota |

**扩展后台写的令牌链路（v3.7 定稿：方案 L「宿主 launcher 注入」，§9-#30 / §10.9）**：

> ✅ **本版是可施工的定稿**。v3.3 的「官方凭据存储 + 模板解析」整条已被 v3.6 真机实测证伪（`expandTemplates` / `${credential:REF}` / `templates.ts` / `MissingTemplateValue` / `is not a template token` / `credentials/reference-updated` 在 5382 个官方 DSH 文件、全 `node_modules`、888 KB 配置 schema 里**全部零命中**，§10.8）；v3.7 又用三轮隔离 DSH 对照实验把候选跑了一遍（§10.9），选定 **方案 L**。历史原文与候选取舍留在 §10.8 / §10.9，**实现一律按本节**。

**方案 L 的完整链路**（扩展是独立 MCP server 进程，要调 `/v1` 必须有自己的客户端令牌）：

1. **生成**：安装扩展时 `ext-registry` 生成随机令牌 → `api.clients` 写一条 `{ id:'ext:'+extId, hash(sha256), scopes:['memory:write'], extId, enabled:true }`（**只存 hash，不存明文**）→ 明文写进 `<dataDir>/secrets/<extId>.json` 的 `{token, ref}`（0600、`backup.js` 的 `SKIP` 补 `secrets/`、不进 E4 包）。
2. **注入**：受管块的 `command` 指向宿主自带 `src/ext-launcher.mjs`（§3.2）。DSH 拉起 MCP server 时实际 spawn 的是 launcher；它按 `ROOST_EXT_ID` 从 `<dataDir>/extensions/<id>/plugin.json` 读真 `command` / `args` / `cwd`，从 `secrets/<id>.json` 读令牌，再 `spawn(真 server, { env: { ROOST_API_TOKEN, ROOST_API_URL, ROOST_EXT_ID }, stdio:'inherit' })`，退出码与信号透传。**只传这三个业务变量**：宿主 `dataDir` 全路径、`ROOST_LAUNCHER_DIR`、私有文件路径一律不传给扩展进程。
3. **轮换**：重写 `secrets/<id>.json` + 更新 `api.clients` 的 hash + 触发该 MCP 连接 **reload**（launcher 每次启动重读文件 → 真 server 拿新值；旧令牌立刻 401）。**不需重启 DSH** —— 这正是选 L 而非 `!!js` 方案的关键：§10.9 实测 HMR reload **不会重新求值 `!!js`**，而 launcher 是每次重建连接新起的进程。
4. **吊销 / 卸载**：删 `api.clients` 记录即吊销（可选删 secrets 文件）；卸载 = 删记录 + secrets + 受管块条目。
5. **缺值 / 失效**：launcher 读不到 secrets 时注入空串，扩展调 `/v1` 得 401 → 宿主记审计事件 `ext.auth_failed` → **面板显示「扩展鉴权失败」而不是静默失联**（G3 提供后端可观测、G5 呈现）。备份还原后 `secrets/` 缺失时宿主自动重新生成令牌并写回，面板提示「扩展令牌已重新生成」。
6. **`streamable-http` 形态**：不由宿主注入（没有可接管的子进程）。宿主只生成配置片段 + 一次性显示令牌，由用户自行配到扩展的启动环境，属 §13 已知边界。

**为什么不用 `ctx.credentials` / `!!js`**：P3 实测 `ctx.credentials` 运行期确实可用（8/8：`set`/`unset`/`resolve`/`describe`），但它是 **async 名字引用**、官方 provider **不把值写进 `process.env`**、launcher 是独立进程调不到 Cordis 服务；`!!js` 虽真机插值成功（含 `config.env` 嵌套层），却是 `with(ctx) eval(expr)` 的任意代码执行、运行期 config 对象含明文（探针 dump 会打印）、且 reload 不重新求值。方案 L 让**值完全不经过 DSH 配置层**：受管块零明文、零表达式，日志 0 明文命中（§10.9）。REF 规范化规则继续用作 env 变量名 / 审计键 / secrets 文件名的命名规范，合官方 `credentialRef()` 的 `REF_PATTERN`（`dsh-credentials/lib/index.js:13`）。

- **一扩展一令牌**：安装时 `ext-registry` 自动建 `api.clients` 记录 `{ id:'ext:'+extId, name, hash(sha256), scopes:['memory:write'], extId, enabled:true }`，scope 只给 `memory:write`。宿主侧只存 hash，**明文只在 `secrets/<id>.json`**。
- **令牌不写进 `cordis.patch.yml`**：受管块只有 `command` / `args` / 三个引用名 env（§3.2）。官方 `buildChildEnv()`（`dsh-mcp-client/lib/index.js:26-31`）是 `scrubbedParentEnv() + 显式 config.env`：父环境里含 `TOKEN` 的变量会被丢弃，**显式 env 能进子进程** —— 这条实测事实是方案 L 能工作的基础，但值不来自 `config.env`，而来自 launcher 在 spawn 真 server 时注入。
- **REF 规范化（v3.6 真机坐实，v3.7 保留为命名规范）**：`REF = 'ROOST_EXT_' + id.toUpperCase().replace(/-/g, '_') + '_TOKEN'`（如 `bili-helper` → `ROOST_EXT_BILI_HELPER_TOKEN`）。出处是官方 `dsh-credentials/lib/index.js:13` 的 `REF_PATTERN = /^[A-Za-z_][A-Za-z0-9_]*$/`（`credentialRef('ROOST_EXT_bili-helper_TOKEN')` 真机抛 `must match ...`），**不是** `mcp-client/src/templates.ts`（本机不存在）。v3.7 里它不再是模板 token，而是 **env 变量名 / 审计键 / secrets 文件名**的命名规范；前缀 + 规范化用来避免两个只有短横线差异的 id 撞名，8c 仍要断言不冲突。
- **不需要自研 `/v1/auth/exchange` 自举端点**（约 100 行，撤销）：launcher 直接读私有文件，扩展拿到令牌后照常走 `/v1` 的 Bearer 鉴权。
- **轮换 / 吊销 / 卸载**：见本节开头链路第 3–4 步。**没有「官方事件自动重建连接」这回事**（`credentials/reference-updated` 零命中）：重建由宿主显式触发 MCP 连接 reload，launcher 重启时读新值。`describe(ref)` 不返回值这条不再适用（不用 `ctx.credentials`），改为「`api.clients` 只存 hash、任何接口都不回显明文」。
- 令牌生成时只在宿主面板显示一次（若用户选择手工配置 streamable-http）；**stdio 主路径下用户完全看不到令牌值**。`dataDir` 全路径只给 launcher（宿主组件），**不进扩展进程 env**。
- `/v1/memory/ext.add` 的 `extId` **一律从令牌记录读**，body 里传了也忽略并记 warn（F9 红线：来源不可自报）。
- 该客户端令牌**不能**调 `/v1/agent.*`、`/v1/say` 等其它端点——scope 硬隔离。
- **8c 硬前置实测（v3.7 已全部结案，见 §10.8 / §10.9）**：① `@deepseek-ai/dsh-credentials-local` 属 base 组合（`--dump-config` 第 74–75 行），**不需要注入 provider 第二受管块**；② `ctx.credentials` 运行期 8/8 可用，但**方案 L 不用它**；③ `!!js` 插值、launcher 注入、显式 env 进子进程、HMR 不重新求值，三轮真机实验均有可复跑输出；④ 8b 主/备落点合并 21/21。8c 的验收断言已按方案 L 重列（§10.3）。
- **降级链（v3.7 重定）**：方案 L 的主路径是 `launcher + secrets`。若将来某版 DSH 不允许自定义 `command`，或 launcher 的 stdio 透传与官方 transport 不兼容，**备选是方案 E′（进程内 `process.env` + `!!js process.env.<REF>`）**：§10.9 实测该写法在 `config.env` 嵌套层可插值、宿主排前的插件 apply 同步写 `process.env` 能被后续条目读到、显式 env 真进 stdio 子进程。采用 E′ 必须同时接受三条代价并写进验收：① 受管块永久禁止任何扩展自带表达式（只允许安装器生成固定 `process.env.<REF>`）；② 运行期 config 对象含明文，宿主自己的面板/日志不得 dump config；③ **轮换必须重启 DSH**（实测 HMR reload 不重新求值）。**env 明文直写受管块**仍是最末兜底，须用户显式确认 + 单独断言 + 记审计，不进主验收。
- **缺值 / 失效行为（v3.7 定稿）**：官方 `waiting-credentials` / `MissingTemplateValue` 零命中，不存在等待态。launcher 读不到 secrets 或令牌被吊销时注入空串 → 扩展调 `/v1` 得 **401** → 宿主记审计 `ext.auth_failed` → 面板显示「**扩展鉴权失败**」（G3 后端可观测、G5 呈现），**不静默失联**。`failOnStartupError: false` 仍是官方字段（schema 有效），保证缺令牌时连接本身不把宿主拖崩。8c 要断言「删掉 secrets 文件后扩展工具报鉴权失败且面板有状态、不静默」，以及「备份还原后 secrets 缺失会自动重新生成令牌」。

「来源不可自报」的红线仍然成立：**调用者身份**永远由宿主按 owner/session/caller 判定；这里的 `extId` 是**写入目标**，两者不是一回事，文档要写死这个区分。

读取：

- `ext_memory_search({ query, extId?, all?: boolean })` — **默认只搜当前会话可见的扩展命名空间**（§9-#23），显式 `all: true` 才全搜；传 `extId` 则限定单个命名空间。返回带 `[extId]` 前缀。这里的「全局可调取」指 `visibility: all`（谁能读），**不等于「默认全搜」**（默认范围），两者别混。单独成工具而非扩 `memory_search` 的 enum——那边 `canCrossGroup()` 管跨群，这边是命名空间可见性，硬塞进同一个 enum 迟早算错。

### 5.5 来源标签、预算与降权（优化采纳）

写 ext 桶时 `src: 'ext:<id>'`（现有字段，零结构改动）。检索结果按来源可过滤/可降权，面板显示每扩展占用条数，防止某个扩展刷屏把整体检索质量拖垮。每扩展 `maxRows`（默认 200）、单次最多 5 条 / 每条 120 字，与人格 facts **分开排名**。

### 5.6 清空归属契约（P1-4 修复）

报告 §17 对 D3/D7/D8 提过同构缺口：**「清了记忆但扩展记忆还在」是隐私缺口**。v3 只写了「按扩展单独清空」，没定义现有三个动作。补齐：

| 动作 | 对 ext 桶 | 面板行为 |
|---|---|---|
| `memory.clear`（清本会话） | **默认不动**（ext 是跨会话的，按会话清没有意义） | 确认框列出「另有 N 条扩展记忆，是否一并清除」勾选 |
| `memory.purge`（彻底删） | 同上，默认不动 | 同上 |
| `memory.clearGlobal`（全局清空） | **默认清空 `ext-memory/*.json`**，但尊重每个扩展的 `onClear: keep` | 确认框明确写「含 N 个扩展的 M 条记忆」 |
| 面板「扩展记忆」分组 | 删对应 `<extId>.json` 单文件 | 显示条数 / 字节 / `archivedAt` |

每个扩展可设 `onClear: 'keep' | 'clear'`（默认 `keep`），`clearGlobal` 尊重该设置。备份：**`ext-memory/` 目录整体进 E4 包**（不在 `backup.js:49` 的 `SKIP` 里，`walk()` 递归打包），还原即整目录恢复；**不再涉及 `insertRaw` / `restoreRetentionRows` 的 `scope` 归一**（v3.4 分文件后作废）。`memory.json` 仍整文件进包，但里面不再有 ext 数据。

### 5.7 生命周期与两个维度

卸载扩展默认保留并标 `archivedAt`（卸载 ≠ 清记忆）；`archived` 行不参与检索，面板可手动恢复或清除。

上一轮的「独立 Agent 会话不写共享记忆」和这一轮的「按插件隔离」是**另外两个维度（写哪层 / 谁能读）**，与 §5.4 说的「`visibility: all` 全局可调取 vs 默认检索范围收窄」**不是同一组维度**，别混。配置拆成：

- `writeTarget`：`shared` / `ext:<id>` / `off` —— 写哪层
- `visibility`：`all` / `owner` / `self` —— 谁能读（**默认 `all`**）

游戏裁判会话 = `writeTarget: off`；刷 B 站扩展 = `writeTarget: ext:bili, visibility: all`。

**生效范围的解析顺序（v3.4，参考 `dsh-persona-dafeiyu` / `dsh-soul-md` 的 `session > workspace > global`）**：三个字段都按「越细越优先」解析，且**显式关闭不回退**：

| 字段 | 解析顺序（从细到粗） | 显式关闭语义 |
|---|---|---|
| `mounts`（**仅 QQ 会话**） | 会话覆盖 > 扩展清单 `mounts` > `['*']` | `[]` = 该 QQ 会话不给任何扩展工具，**不回退**；**独立 Agent 会话恒为全见，不受此表约束**（§9-#3 / #4） |
| `writeTarget` | 会话覆盖 > 扩展清单 > `shared` | `off` = 不写任何层，**不回退** |
| `visibility` | 会话覆盖 > 档位 `byBucket` > `all` | 空可见集 = 谁都读不到，**不回退** |

依据：`dsh-soul-md` 是 `session choice > workspace mapping > active default card > none`，`dsh-persona-dafeiyu` 是 `Session > Workspace > Global`，两者都明确「No persona」= 该会话完全关掉、不回落。面板要显示**这一项最终来自哪一层**，否则用户改了半天不知道被谁覆盖。

**会话覆盖存哪**：`sessions.json` 增加 `overrides[chatId] = { mounts?, writeTarget?, visibility? }`（与现有 `chatId → sessionId` 映射同文件，随 E4 包备份）；独立 Agent 会话的覆盖放 `agent-sessions.json`（仅 `persist` 打开时存在），**不写 `sessions.json`**。

## 六、通用 Agent 通道（方案 B，已确认）

**场景**：开一个与 QQ 无关的独立 AI 会话，处理连续对话问题，例如游戏里 AI 参与裁判、多轮规则解释。

### 6.1 为什么不改 `sessions.json`

`sessions.js:67` 是 `chatId → 一个 sessionId`，整条链路（`speaker`/`bucket`、`sendOut`、投递账本、被动回复窗口、备份、账号迁移）都假设有 QQ。游戏裁判恰好相反：无 QQ 身份、不要人格记忆心情、要并发多个独立对局、要能续上之前的局。硬塞要给每个虚拟 chatId 造假字段，再在出站层到处加「别发 QQ」判断——**漏一路就是「裁判结果发到群里」**。

### 6.2 为什么选 B 而不是直连 DSH ACP

`@deepseek-ai/dsh-acp` 官方已提供 `session/new / list / resume / close / prompt / cancel / set_config_option`、一连接多会话独立上下文、按会话挂 MCP server。但它是**标准 v1 表面，没有自定义 system prompt 参数**；裁判规则只能靠 MCP `instructions`（全局静态）或第一条 prompt（用户消息，不是 system）。

| | A：插件直连 ACP | **B：dsh-roost `/v1` 代理（已选）** |
|---|---|---|
| 自定义 system prompt | ❌ | ✅ 同进程 `agent.ctx.systemPrompt.section()` |
| 复用人格/记忆/扩展/选模型 | ❌ 另一个 profile 进程 | ✅ |
| 插件侧协议 | stdio JSON-RPC，要 spawn DSH 进程 | HTTP，插件本来就熟 |

### 6.3 端点与实现

```
POST /v1/agent.new       {clientId, persist?, preset?, sections:[{name,order,text}]}
POST /v1/agent.prompt    {sessionId, text}   → SSE 流式返回
POST /v1/agent.close     {sessionId}
GET  /v1/agent.list
```

- 用 `ctx.agents` 开会话，**不写 `sessions.json`**
- `sections` 按数组里**每项自带的 `name`** 调 `agent.ctx.systemPrompt.section()` 注册（官方 `name` 唯一、同 layer 重复注册抛错，别像 v3.2 那样写死 `ext:<client>:<session>` 一个名字）；返回值是 disposer，关会话整组撤掉
- **instructions 过滤由宿主另行注册**，不接受客户端传入：`/v1/agent.new` 一律按已装扩展做 instructions 过滤（8a 择一：shadow / waterfall，优先 waterfall，§3.5 ③），`agent.new` 的响应里返回「已注册 section 清单 + 过滤清单」便于排障
- **v3.3 删除 `mounts?` 入参**：`mounts` 只管 QQ 会话的工具可见性（§4.4），独立会话工具全见，传了会与「不监管」混淆；清单里 `mounts` 是否含 `agent` 仅作响应元数据
- **`persist` 可选、默认关**：打开时存「会话 id + 客户端 id + 规则快照」到 `agent-sessions.json`，**该文件要进 E4 备份包**（P2 修复），恢复后按 id 拉回并重新注册 section
- 独立会话默认 `writeTarget: off`，不写共享记忆
- **SSE 流式（保留，v3.3 重写理由）**：v3.2 说「ACP prompt 返回 enqueue receipt、同步聚合必超 HTTP 超时」——核实不成立：官方 ACP README 的 prompt 是 **completion-settled**（"settlement follows root and descendant completion plus ordered update delivery"），且 8d 走 `ctx.agents` 同进程、**根本不经 ACP**。SSE 的真实理由是独立会话多轮 / 长任务需要流式输出与中途 `cancel`，同步等待会占住连接且难以取消；非流式客户端用 `?wait=1` 兼容
- **不纳入监管**（主人决策）：见 §4.1

**怎么起一个隔离 DSH 实例（v3.4 补充，已实测）**

DSH 自带 CLI，**不在 PATH**：`C:\Users\<user>\AppData\Local\Programs\DeepSeek Harness\resources\runtime\cli\bin\dsh.cmd`（内部 `ELECTRON_RUN_AS_NODE=1` 跑 `app.asar` 里的 `cli.js`，无 GUI）。已实测：

- `dsh --version` → **`0.2.2-rc.1`**
- `DSH_HOME=<临时目录>` **完全隔离**（临时 HOME 会被创建，不碰 `~/.dsh`）
- **必须带 `--profile <name>`**（不带会报 `--profile <name> is required`）；临时 HOME 首次 `--profile web` 会从 shipped 模板生成 `profiles/web/`（`cordis.yml` / `cordis.patch.yml` / `package.json` / `pnpm-workspace.yaml`）

- 每道门不通过 → **停在本阶段**，先修或改设计，不往下铺代码。**门验收项只引用本阶段及之前已实现的组件**；需要后阶段组件才能测的项，下沉到对应门，不许在当前门硬凑。

- 并行会话仍在提交：**P0 记下三仓（`dsh-roost` / `bot` / `qq-bot-roost-plugins`）各自的 `git rev-parse HEAD` 作为基线**；每阶段开工前对该阶段要改的文件跑 `git diff <base>..HEAD -- <文件>` + 符号存在性 grep，确认没被别人改过。**version 号不作判据**（可能没 bump）；行号以 §11-bis 为参考、**以符号名为准**。
- 改插件子模块（非 index.js）**必须重启 Roost 进程**，否则「重载」= 新入口 + 旧子模块，静默失效。
- 推前必跑 `node scripts/build-index.mjs --check`（插件目录任何改动）、CI 绿。
- 同步运行副本只同步本次新功能改动的那几个文件，不做全仓比对 / 版本核对 / 进程排查；备份照旧、覆盖后不重启。
- **提交前起干净子智能体**（只读、临时目录、真跑）独立复核，按 P0 / P1 / P2 出结论；**查 → 修 → 再查一遍，直到 0 条 P0**。

## 十三、已知边界（v3.3 重写）

- **`maxInstructionBytes` 不自定义**：受管块不写该字段，沿用官方默认 32,768 的**拒连线**（超限整个连接被拒、该扩展全部工具不可用）。宿主不叠加二次阈值，也不截断 / 按会话抑制 instructions；第三方非空说明一律进 QQ 会话 —— **独立会话侧有 scope 内过滤（§3.5），QQ 会话侧没有防线**。设低阈值既不防恶意、只误伤 instructions 较长的正常扩展（含工具清单与示例时 10–20 KB 很常见）。连接确因超长被拒时面板给出提示。
  - ⚠️ **主路径下宿主零观测、不声称预算受控**（shadow / waterfall 成立、不走降级时）：长度接近但未超 32,768 的正常说明会连接成功、每轮无声占用 QQ prompt。宿主拿不到 `instructions()` 文本（`ServerContext.instructions()` 只在 mcp-client 内部 connection 里，官方 `probeServer()` 返回也没有该字段），所以**主路径下既不能统计字节数、也不能做面板 warn**；宿主能控的只有自己生成的 usage（单条 200 字 / 合计 2 KB）与工具输出 4 KB 截断。**这与 §3.5 ③ 的 8a 降级探测是两回事**：降级时自写握手读 `InitializeResult.instructions`，能拿到静态文本长度并做面板黄卡，但那时硬隔离已退化为软提示（见 §3.5 ③）。另可在 `system-prompt/assemble` 加只读 listener 做统计，属后续候选、不进 8a–8h。见 §3.2 / §3.5 ②。
- **preset 是 DSH 侧的**：`agentPreset` 只能传 DSH 已注册的 preset 名（`inbound.js:119` 的三元写死 `roost-private`/`roost-social`）。「自定义预设」= 选已有 preset + 按会话覆盖 prompt section；要新建 preset 得改 DSH 的 agent preset registry。
- **ACP 能力未直接使用**：本方案用 `ctx.agents`（`docs/subsystems/core.md` 的 `AgentRegistry`：`create/resume/get/list/setFactory`，真实存在）自行实现等价独立会话；若后续 DSH 给 ACP 加上自定义 system prompt 参数，8d 可以简化。ACP 的 prompt 是 **completion-settled**，不是 enqueue receipt（§6.3 已订正）。
- **市场验签**：`EMBEDDED_ENFORCE` 实测为 `false`（验而不拦）；8g 全量 `--verify` 补签后打开，才成为真边界。
- **在线下载 SSRF**：一期不做逐 IP 校验的下载链（`market.js` 的 `assertSafeIndexUrl` 已有，接入时复用即可）。
- **`newTools: 'owner-only'` 保持不动**：默认放开靠 §4.2 的 groups 初始化实现。**按方案 C′ 只改 `resolvePolicy()` 一处**（deny 在 `expandAllow` 之后按最终工具名统一过滤、只取当前档、`forceDeny` 支持通配并持久化；`accumulateAllow()` 不动，§9-#18 / §10.7-bis），存量 `capabilities.json` 里 `helper.deny` 等配置从「连坐高档」变成「只约束本档」，8b 必须给升级说明 —— v3.2 那句「不改核心语义、避免影响现有能力页行为」是错的，已删除。
- **独立会话的扩展可见范围**：默认看全部已挂扩展（不监管），`mounts` **不参与**独立会话的工具过滤（§4.4）。提示词层另算：独立会话默认不注册 usage section，但**一律做 instructions 过滤（8a 择一：shadow / waterfall）**（§3.5）。
- **⚠️ instructions 过滤的两个已知边界**：① shadow 方案下若 `agent.ctx` 与 MCP client 的 `registerServerContext()` 注册在**同一 layer**，`mcp:<id>` 会「duplicates within one layer throw」——8a 择一实测，优先改用 scope-filtered 的 `system-prompt/assemble` waterfall（§3.5 ③）；② 过滤**只作用于独立会话 system prompt 的 section 文本**：第三方 instructions 仍会进 QQ 会话（宿主不设自定义阈值，唯一上限是官方 32,768 拒连线；任何非空 instructions 都会进 QQ 会话），也不影响扩展产生的数据量或网络行为。「独立会话不受污染」只对**提示词**成立，不是对该扩展整体行为成立。另：`complete: true` 作为降级**已明确否决**（官方 `assemble()` 会把 sections 整体替换成它一个，人格 / 记忆 / usage 全丢，见 §3.5 ③），8a 不得回退到它。③ **若 G0 的 shadow / waterfall 实测都不成立而退到「探测 + 面板标注」，硬隔离即降级为软提示**，此时「独立会话不受污染」不再成立，须把这一条作为已知边界写进验收结论，不得在验收里声称「已隔离」。
- **凭据链路边界（v3.7 方案 L 定稿）**：v3.6 证伪的 `expandTemplates` / `${credential:REF}` / provider 缺时 load 抛错 / `waiting-credentials` 在本机 `0.2.2-rc.1` **全部零命中**，不再是本方案前提。**实测成立**：`@deepseek-ai/dsh-credentials-local` 属 base 组合、`ctx.credentials` 运行期 8/8 可用（但**方案 L 不用它**）；`credentialRef()` 的 `REF_PATTERN=/^[A-Za-z_][A-Za-z0-9_]*$/`（`dsh-credentials/lib/index.js:13`）要求短横线 id **必须规范化**，v3.7 里 REF 只作 env 变量名 / 审计键 / secrets 文件名的命名规范。**已知边界**：① **令牌明文落在 `<dataDir>/secrets/<id>.json`**（0600、不进 E4 包）——这是宿主自有私有文件，不同于「patch / 备份 / E4 包无长期明文」的承诺；备份还原后该文件缺失时宿主**自动重新生成令牌**并提示，扩展无需重装。② **`streamable-http` 形态不归宿主注入**（没有可接管的子进程），宿主只给配置片段 + 一次性显示令牌，由用户自行配到扩展启动环境。③ **多开 / 多 profile**：每个 profile 的 MCP 连接各自 spawn launcher，`secrets/` 按 `extId` 共享，轮换时须把所有相关连接都 reload 一遍，否则旧连接会短暂 401。④ **HMR reload 不会重新求值 `!!js`**（§10.9 实测），所以方案 L 的轮换靠 launcher 重启读文件，**不靠配置表达式**；`--patch` 覆盖层改动也不触发配置重解析，轮换要显式触发连接 reload。⑤ 用户自己的 `~/.dsh/.credentials.yaml` 仍不进 E4 包（与本方案扩展令牌无关）。
- **`bucket` fallback 会让按档位限次退化**：`host.js:778` 是 `sp?.bucket || mine.preset || ''`，`roost-private` / `roost-social` 不在 `BUCKETS` 里，传给 `quota.charge` 的 `byBucket` 查不到 → 退回默认 `max`（`host.js:1091` 注释也承认 callerOf 会归一成 unknown）。这是既有行为，但方案里「按档位次数」在 speaker 缺失的路径上会静默退化，面板应显示实际生效的档位。
- **`tools/post-execute` 截断是内容替换而非长度硬闸**：只在工具结果进入模型前替换 `content`，不影响扩展实际产生的数据量；大结果仍占一次网络往返与内存。
- **`section()` 是本仓新 API**：现有只有 11 处 `context()`（首处 `host.js:2923`、`order:905`），`section()` 零处。**v3.6 共存已实测**：G0a 补验按 11 个真实 name/order 注册 `context()` + 1 个 `section()`，scoped assembly 里两者同时命中、工具表不变、global 不受污染、disposer 撤销恢复（11/11，§10.8）；官方 `section()`/`context()` 分写 `layer.sections`/`layer.contexts`（`dsh-system-prompt/lib/index.js:255/281`），机制上不存在 duplicate 冲突。**排序仍别把 `order:950` 当已验证值** —— 复用 `getSectionOrder('MCP_SERVERS')` 的那套是实测过的。
- **HMR 档位（v3.6 实测收口）**：`architecture.md` 的 `base enables config-only dsh-hmr; headless, SDK and ACP disable it` 已由官方 `dsh-hmr/README.md` 补全判据 —— **启动器提供 `profileContext` 时 base 组合启用 HMR**（组合树 `- id: hmr` 的 `disabled: !!js '!ctx.get("profileContext")'`）。隔离 CLI 实例实测 `profileContext` 存在（10 个字段）、`ctx.get('hmr')` 服务可用，与 desktop 同属 `dsh-app-boot` 启动路径、按官方规则**同档**；**但真机 desktop 未起进程，不得写成「desktop 已实测」**，这项差异随 G0a 结论一起交接（§10.8）。§3.2 的「默认生成片段 + 一键复制」保守开关**继续保留**（保守的是写宿主 profile 的动作，不是 HMR 能力本身）。
- **⚠️ G0a 的 desktop 两项只在隔离实例验证**：HMR 档位与 11 处 `context()` 共存按 §10.1 选项①在 `dsh web` CLI + web profile 里跑通（bundles 仅 `dsh-base` + `dsh-web-app`），真机 desktop 由 Electron app 启动、多 8 个 bundle 且带两个 roost preset；11 处 `context()` 是探针按真实 name/order 复刻，未触发真实 QQ 会话。**若要求「desktop 真机已验证」，需在 G0 结论里另安排一次复验**，本版不声称已覆盖。**v3.7 补充**：凭据设计已冻结、阶段 1 可开工，这项 desktop 复验不再是开工前置条件，但仍是交付前要补的验证（§9-#32）。
