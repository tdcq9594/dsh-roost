# 同会话排队方案（用户反馈：先回「上一条还在想」再回答案）

> **⚠️ 历史文档（2026-11-12）**：本文写于 ai-chat 中间层时代，文中的
> `POST /inbound` / `/r/reply` / 插件适配器 / 端口同步等描述**已全部废弃**。
> 现行链路是 Roost 框架外接协议 `roost-host/1` 直连，见
> [接入说明](接入说明.md) 与 [使用手册](USER-MANUAL.md)。
> 本文保留作为当时的设计记录，不要照着它配置。

> 起因：2026-11-05 用户 mist 反馈「我发一条后它会先发这个在回我」，截图里连着三条
> 「上一条还在想，稍等一下。」。
>
> 这一页记录：为什么会这样、改成什么、为什么这么改、哪些地方故意没做。
>
> **2026-11-05 已实现**（未发版）：`src/turnqueue.js`（含钉住表）、`src/inbound-shell.js`、
> `host.js` 拆壳 + 接线、`turn.js` 加 `isWaiting` / `run({timeoutMs})`、
> `config.chat.queueMax` / `queueMinBudgetSec`。测试 1243 全过（新增 19 条）。
>
> 实现时踩到两个坑，记在这里免得下次重犯：
> 1. **看门狗定时器不能无条件 `unref`**：生产必须（不能拖住进程退出），
>    但测试里没有别的活任务时它永远不触发，`node:test` 会报
>    「event loop has already resolved」。所以 `createTurnQueue` 收了 `unref` 开关，测试传 `false`。
> 2. **卸载要先 `turnQueue.dispose()` 再 `turns.dispose()`**：反过来的话，
>    排队的任务会被唤醒去调已经卸载的 `turns.run`。
>
> **2026-11-05 二次修订**（独立审校后）：初稿的「常见 30–120 秒」不成立（实测中位 2–3 秒），
> 容量默认值 1 → 2；**队列 key 改成「按 chatId 钉住、只算一次」**——初稿「每次现算
> `sessions.get()`」会让新会话的第一波消息仍然丢，正是用户反馈的场景；
> 主动轮次的 `isBusy` 要同时问 `turns`，否则两个定时器互撞仍抛 busy。

## 一、问题定位（代码证据，不是猜）

### 1.1 三个环节

| 环节 | 位置 | 行为 |
|---|---|---|
| 锁 | `src/turn.js:222` | `waiters.has(sid)` 为真就抛 `kind: 'busy'` |
| 人话 | `src/host.js:3308` | `busy` → 「上一条还在想，稍等一下。」 |
| 后果 | `src/host.js:3316` | 回完这句就结束，**这条消息再没有第二次机会** |

`waiters` 的 key 是 `sid = agent?.session?.id ?? agent?.sessionId`，所以这把锁是**会话级**的。

所以用户看到的两件事其实是一件事：

1. 上一轮还在跑；
2. 新消息进来撞锁 → 立刻回那句；
3. 上一轮跑完 → 正常回复这才发出来。

用户看到的「先发这句、再回我」，其中**「回我」答的是上一条**；他刚发的那条被丢了。
群里更糟：一个群共用一个 DSH 会话，任何人上一轮没跑完，别人说话也会被踢。

`onInbound` 在 `server.js:247` 是**不 await** 直接调用的（「收到就立刻回 200」），
所以多条消息天然并发进来——这就是锁会被撞到的原因。

ai-chat 侧有个合并窗口（`merge.js:16` 的 `createMerger({waitSec:1.5, maxSec:6})`，
配置名 `mergeWaitSec` / `mergeMaxSec`），只兜得住「1.5 秒内连发三句」。
等一会儿再说、或者第二个人开口，都不在窗口里。`merge.js:6` 的注释已经预告了这个失败方式：
「或者更糟：第一条还在想，后两条被 busy 锁直接丢掉。」

### 1.2 单轮到底多慢（实测，2026-11-05）

初稿写「模型 + 工具链，常见 30–120 秒」，这个数字没有出处。用日记里的
user→bot 时间差实测（`journal-bridge.js:32` 两边都写 `Date.now()`，所以差值就是这一轮的真实耗时；
严格说还含 `agentFor` + 检索，不含真正的网络发送）：

| 会话 | 样本 | 中位 | p90 | 最大 |
|---|---|---|---|---|
| `55597677`（机器人测试） | 146 | **3.1s** | 5.3s | 10.2s |
| `F1F759AD`（roost交流群） | 59 | **1.8s** | 3.1s | 9.7s |
| `CBF1E6B3`（私聊） | 21 | 2.5s | 4.4s | 6.0s |

两点限制要认：

- **长尾被截断**。超时 / 报错的那轮不会写 bot 记录，所以「最大」只会偏小。
  用户能撞到 busy 锁，说明长尾确实存在（工具链、大上下文）。
- 样本只覆盖「触发过回复」的轮次，被动放弃的不在内。

结论不变（仍然要排队），但**容量不必保守到 1 条**：第二条最多等几秒，
排 2 条的成本远小于「丢消息」。见 §3.3。

## 二、目标 / 非目标

**目标**

- 同一会话里，别人的消息不再「丢了还回一句」。先后关系保留，逐条都回。
- 不引入新的刷屏话术：正常情况下，用户只会看到真正的回答。
- 出问题能退回：一条配置（`chat.queueMax=0`）即回到现在的行为，不用回滚版本。

**非目标（这一版不做）**

- 不打断正在跑的那一轮（DSH 没有对外 `interrupt`，硬做要改宿主协议）。
- 不做跨会话全局限流（那是配额层的事，`quota.js` 已经有一份）。
- 不改 ai-chat 的协议、不改 `/inbound` 报文结构。
- 不在预算不足时自动改发主动消息（见 §3.4 的取舍）。

## 三、方案：per-chat 串行队列

一句话：**把「一条消息的完整处理」当成一个任务，同一个会话一次只跑一个，后来的排队。**

```
        ┌──────────── onInbound(payload) ────────────┐
        │  chatOf(payload) 拿 chatId（同步）          │
        │  chatId 为空 → 忽略（现有行为）             │
        │  deadline = payload.reply.expiresAt ?? now+180s │
        └───────────────────┬────────────────────────┘
                            │  q.push(chatId, task, {deadline})
                            │  （队列内部：首次 push 时钉住 key，之后复用）
                ┌───────────┴────────────┐
        空闲    │                        │ 忙
                ▼                        ▼
        立即执行 handleTurn      队列没满且预算够 → 入队（不回话）
                                        否则 → 回一句（旧文案/新文案）
                │
                ▼ 任务结束（含失败）
        取下一条 → 预算还够？ ──否──→ 丢弃 + 说一句「没赶上」
                │是
                ▼
            执行 handleTurn
```

### 3.1 队列包在哪一层：`onInbound` 整段，不是只包 `turns.run`

`onInbound` 里有一批**按 chat 变化的状态**，至少这四个：

| 名字 | key 维度 | 串起来会怎样 |
|---|---|---|
| `memState` | chatId | 这轮命中了哪几条记忆被下一轮顶掉 |
| `rounds` | chatId | 轮次计数错乱（压缩阈值靠它） |
| `qqTurn` | sid | 工具拿到的「谁在说话」错位 |
| `speaker` | sid | **权限档位**（bucket）可能串到别人身上 |

除此之外还有 `pendingOpening` / `keywordNote` / `keywordPick`（按 chatId），
以及 `lastScene` / `lastMsgText` / `lastTurn`（**进程级单例，谁最后写谁赢**）。
后一组更隐蔽：`lastScene` 是「/mind」和场景块的数据源，两轮并发时会显示成另一个群。

只在 `turns.run` 外面加锁的话，这些状态会先互相覆盖，再排队跑——回答质量下降且难查。

所以：原 `onInbound` 整体改名为 `handleTurn(payload)`（**函数体一个字都不动**），
新的 `onInbound` 只做三件事：算 deadline、入队、按结果决定要不要回话。
这样 diff 极小，`handleTurn` 里的 try/catch/finally 全部保留。

`chatOf(payload)`（`host.js:2752` 调用，定义在 `inbound.js:93`）是纯同步函数，
不碰 `agentFor`，所以可以在壳里安全地先算 `chatId`。

### 3.2 key：**按 chatId 钉住，只算一次**

初稿写「每次 push 现算 `sessions.get(chatId) || chatId`」，**这是错的**，而且错在最该救的场景上：

```
msg1 进来 → sessions.get(chatId) 为空 → key = chatId，任务开始
             agentFor 里 sessions.set(chatId, sid1)（host.js:1993，在 resolveAgent 之前）
msg2 进来 → sessions.get(chatId) 已经是 sid1 → key = sid1 → 另一条空队列 → 立刻执行
             → turns.run(sid1) 撞 turn.js:222 → busy → 回「上一条还在想」
```

新群 / 新私聊的**第一波消息**恰恰是用户最可能连发的时刻，现算 key 等于没修。
而 `sessions.set` 发生在 `resolveAgent` 之前，这个窗口每次新建会话都会出现一次，
不是初稿以为的「归档重建」那种罕见边界。

所以队列内部维护一张 `chatId → key` 的**钉住表**。注意接口要拆成两层，
否则调用方会把「原始解析」和「钉住后的 key」混成一个参数：

```js
// 调用方只提供「怎么从 chatId 解析出 key」，其余都在队列内部
const q = createTurnQueue({
  resolveKey: (chatId) => sessions.get(chatId) || chatId,   // 只解析，不记忆
  ...
});

// 队列内部
const pinned = new Map();
function keyOf(chatId) {
  let k = pinned.get(chatId);
  if (!k) { k = resolveKey(chatId); pinned.set(chatId, k); }
  return k;
}
```

**`pinned.delete(chatId)` 的时机必须钉死**：只在同一个 `finally` 里、与 `running = null` 一起执行。
「pending 为空就删」是错的——`turns.run` 返回后还有 `postReply` / `journalAdd` / `lastTurn` 的尾段没跑完，
这时删表 + 重新钉，新任务会拿到 sid 这条**新 key** 立刻起跑，两条任务的尾段就重叠了，
等于把 §3.1 辛苦论证的「整段排队」又拆掉。

钉住之后：

1. 首轮 key = chatId，第二、三条也走同一把 key，正常排队；
2. 已有会话的 key 就是 DSH 的 sessionId，与 `turn.js:222` 的锁**同一把**，语义对齐；
3. `memory.consolidateChat` 若被配成私聊 openid，巩固和真人消息的 key 相同——
   但**巩固绕过队列**（见 §3.8），这条只是让 key 不冲突，不等于它会排队。

为什么仍然想要 sessionId 而不是一律用 chatId：一个 chatId 对应一个 DSH 会话是**约定**，
不是硬约束（`consolidateChat`、`selftest` 这类共享会话就打破了它）。用 sessionId 才能保证
「同一把锁上只有一个任务」。钉住表是在「拿不到 sessionId」时的正确折中。

### 3.3 容量：默认 2 条

- 队列长度上限 `chat.queueMax`（**默认 2**，初稿写 1，按 §1.2 的实测放宽）。
- 为什么不是 1：`queueMax=1` 只兜住「两条」的场景，用户连发三条时第三条照样被丢，
  而丢消息正是这次要修的东西。实测单轮中位 2–3 秒，第二条等 3 秒、第三条等 6 秒，
  远没到 ai-chat 的 180 秒上限。
- 为什么不是更大：排到第 4 条起，等待时间开始接近「用户以为没收到」的阈值，
  而且真排到那么长，说明这一轮已经异常（交给看门狗）。
- 满了才走老路：回「上一条还在想，稍等一下。」——这时**确实是**堆着了，这句话才诚实。
- 为什么不做「把多余消息合并进排队那条」：合并后只能用其中一条 `reply.url` 回话，
  另一条 payload 的用户**永远收不到回复**——比现在的表现更怪。

### 3.4 入队不回话；出队前必须查预算

入队一律**不吭声**（不发「排队中」）。理由：这句话在群里是纯噪音，
而且大部分排队在几秒内就轮到，用户体感只是「这次回得慢一点」。

出队前查一次：`deadline - now < chat.queueMinBudgetSec`（默认 30 秒）就**别再跑了**——
跑了也赶不上 ai-chat 的 180 秒，回话会 404，白烧一次模型。
这时回一句「这条等太久了没赶上，再说一次？」（比沉默强，用户知道不是没听见）。

**只查一次不够，还得给这一轮一个短超时。** `turns.run` 的超时是**实例化时写死**的
（`host.js:453` 的 `timeoutSec: cfg.chat.turnTimeoutSec`，150 秒），`run()` 签名里没有 per-call 选项。
所以「剩余 31 秒」放进去照样可能跑满 150 秒，最终 404 —— 正是这条预算检查想避免的事。

两个改法，必须选一个：

1. **给 `run()` 加 `timeoutMs`**（推荐）：出队时传 `Math.min(150_000, remaining - 5_000)`，
   让它自己提前收尾。改动是 `turn.js` 里把 `timeoutSec * 1000` 换成 `opts.timeoutMs ?? timeoutSec * 1000`；
2. 把 `queueMinBudgetSec` 提到 150：等价于「排队超过 30 秒的全丢」，长尾任务全废，不推荐。

`deadline` 取 `payload.reply.expiresAt`（形状是 `reply: {url, token, expiresAt}`，
见 `ai-chat/inbound.js:274`）。它在 `adapter/host.js:80` 生成，值是 `Date.now() + 180_000`，
**那一刻已经过了合并窗口**（1.5–6 秒），所以真实预算比「入站起算 180 秒」还少 1.5–6 秒——
方向是保守的，不会多跑。缺省（老版本 ai-chat、或 webhook 适配器不传）时按 `now + 180s` 兜底。

**为什么不在预算不足时改发主动消息**：dsh-roost 有 `sendOut`（`host.js:1356`）和默认不限的配额，
技术上做得到。但主动消息要过审核、延迟不确定，用户会从「没赶上」变成「几分钟后突然冒出来」，
比明说没赶上更困惑。留作以后的可选项，本版不做。

### 3.5 看门狗：防止一个卡死拖死整个群

串行化把「一条卡住」的代价从「影响这一条」变成「影响该群后面所有消息」，
所以必须有兜底：单个任务超过 `chat.turnTimeoutSec * 1000 + 60000` 仍未结束，
`log.warn` 一条并**强行释放槽位**，继续跑下一条。

`turnTimeoutSec` 默认 150（`config.js:122`），所以阈值是 210 秒。
`turns.run` 自己有这个超时，正常不会触发；这条防的是它之前的前段
（`agentFor`、记忆检索、`followup` 卡在 DSH 里不返回）。

代价：强放之后可能出现两轮并发（老的那轮其实还活着）。**这是两害相权**——
并发的结果是「乱一点」，不释放的结果是「这个群再也不回话，只能重启插件」。
所以留 warn，方便事后定位。

### 3.6 队列满时**不要**伪造 `kind: 'busy'` 异常

初稿写「满了回旧文案」，实现上有个岔路：是抛一个 `kind:'busy'` 让 `handleTurn` 的 catch 去回，
还是在新 `onInbound` 里直接 `postReply`？

**必须选后者。** 抛异常会走 `handleTurn` 的 catch（`host.js:3257`），那里会写
`lastTurn = { ok: false, error }`，面板的「最近一轮」和失败统计会把「排队满」
记成一轮**失败**。事后看数据分不清「模型挂了」还是「只是排满了」。

所以：队列满 → 新 `onInbound` 直接回那句旧文案，`handleTurn` 根本不被调用，也不产生 `lastTurn`。
这是唯一需要新增文案回话的地方，其它情况（入队、正常执行）一律不回话。

### 3.7 主动搭话 / 觉醒：让路，不排队——但 `isBusy` 必须问两处

它们用的是 `chatId = ownerId()` 的同一个私聊会话：

| 入口 | 位置 | 什么时候走 |
|---|---|---|
| 主动搭话（旧） | `host.js:852` | **只在 `awake.enabled === false` 时** |
| 主动搭话 / 觉醒 / 群主动 | `host.js:1472` | awake 打开时的 `awake.compose()`、群主动（`awake.js` 的 `wakeGroups`）都汇到这里 |

排进去会出现「用户问一句 → 先答一句主动搭话 → 再答用户」，顺序全乱。
所以它们**进门前查忙，忙就放弃这次机会**：

- 主动搭话（私聊）→ 返回 `<<skip>>`，`speakup` 当作「她不想说」，正常重新排期、不占今日额度；
- 群主动 → 返回 `<<skip>>`，`awake` 侧 `skipStreak++` 并按 `nextAskAt` 退避（`awake.js:612`）。

**一个要认的副作用**：被「忙」挡下和「她不想说」在现有代码里是同一个信号，
所以每次让路都会让该群的下次搭话间隔翻倍。低频场景（凌晨、主人正在对话）可接受，
但要写进「已知限制」，否则以后看数据会以为「她越来越不爱说话」。

**关键：只查队列的 `isBusy` 不够。** `turn.js` 的 `waiters` 是私有 Map，对外只有
`get waiting()`（返回数量，`turn.js:365`），队列看不到它。而这两条主动轮次**不入队**，
所以两个定时器同时触发时，后者仍会撞 `turn.js:222` 抛 `busy`——不是 `<<skip>>`，会被记成失败。

所以要给 `createTurnRunner` 加一个只读方法：

```js
isWaiting(sid)            // turn.js 新增，waiters.has(sid)
```

判断要两把锁都问，但**两个参数不是同一个东西**：

```js
// generate 里此时已有 agent；owner 就是主人私聊的 chatId（host.js:825/1451 的 const owner = ownerId()）
const sid = agent?.session?.id ?? agent?.sessionId ?? '';
if (q.isBusy(owner) || turns.isWaiting(sid)) return '<<skip>>';
```

- `q.isBusy(...)` 收 **chatId**（队列内部换算成钉住的 key，见 §4）；
- `turns.isWaiting(...)` 收 **sid**（`waiters` 的键就是 sid，`turn.js:217`）。

传错了不报错、只是恒为 false——而「新会话第一波」时队列的 key 恰好就是 chatId，
两者长得一样，最容易写错。`isWaiting(sid)` 没有「已结束仍报忙」的窗口：
`turn.js:118-120` 的 `finish` 是**先 `waiters.delete` 再 resolve**。

主动开口本来就是「看情况」的事，错过一次无所谓；用户正在跟它说话时插一句才是错的。

### 3.8 凌晨巩固：**不进队列**，接受偶发失败

它用的是独立会话（`cfg.memory.consolidateChat || 'consolidate'`），默认与任何真实聊天都不同。

但要说清一件事：**巩固的 `generate`（`host.js:1185`）直接调 `turns.run`，不经过新队列。**
所以如果把 `consolidateChat` 配成主人私聊 openid，它撞上正在跑的一轮照样抛 `busy`，
那一轮巩固失败（`consolidate.js` 里 catch 掉，次日再来）。§3.2 的钉住表只保证 key 不冲突，
**不保证它会排队**。

本版的选择：**不接**。凌晨 3 点撞上的概率极低，失败一次次日补跑；
接进去要改 `consolidate.js` 的调用链，超出这个版本的范围。写进「已知限制」。

队列模块对外形态：

```js
const q = createTurnQueue({
  maxPending, minBudgetMs, capMs, log, now,
  resolveKey: (chatId) => sessions.get(chatId) || chatId,   // 只解析，钉住由队列内部负责
});
q.push(chatId, task, { deadline, label })
// → { accepted:true, queued:false, promise }
// → { accepted:true, queued:true,  promise }
// → { accepted:false, reason:'full' | 'expired' }
// queueMax=0（关闭排队）时恒为 { accepted:true, queued:false, promise } —— 直接跑，与现状一致
q.isBusy(chatId)   // 主动搭话用；收 chatId，内部换算 key
q.stats()          // { busy, pending }，留给面板以后展示
q.dispose()        // 插件卸载时清定时器
```

`task` 是 `() => Promise<void>`，**约定它自己吞掉异常**（`handleTurn` 本来就是）。
队列永远不 reject，出错只记日志——排队层不该成为新的错误来源。

## 五、配置

```jsonc
"chat": {
  "queueMax": 2,             // 每个会话最多排几条；0 = 关闭排队（回到旧行为）
  "queueMinBudgetSec": 30    // 轮到它时剩余时间不足这么多秒就不跑了
}
```

两个都能在 `config.json` 里改，不重启：实例化时**传取值函数**（`() => cfg.chat.queueMax`），
不用值。这不是风格问题——`cfg` 是 `let`、多处被重新赋值（`host.js:383/424/710/880`，另有 3837/3961/4007 等），
传值等于把旧对象焊死在闭包里。项目里 `ai-chat` 的 `url` 参数就是这么传的。

**已在「能力」页暴露**（2026-11-05 补）：新增分组「消息来不及回的时候」，
两项都是 `kind:'number'`——`queueMax`（可填 0–10，`0` = 关掉排队）和
`queueMinBudgetSec`（5–180）。`features.js` 支持 `select` / `number`，
前端按 `kind` 画开关、下拉或数字框；改完即时生效，不用重启。

注意 `0` 是合法值，别用 `|| 默认值` 兜——`turnqueue.js` 的 `val()` 和
`features.js` 的 `normalizeSetting()` 都为此单独处理过（空串也会变成 0，
必须显式挡，否则清空输入框就会静默关掉排队）。

## 六、测试计划

### 6.1 为什么要抽壳——难点不是「没有 harness」

`test/host.test.js` **已经有**驱动 `apply(ctx)` 的 harness：里面 5 处 `host.apply(ctx)`，
并且会截获 `webServer.register` 注册的路由、直接调 handler（例如 `routes.get('/roost/api/quick')(req, res)`）。
所以「写不出来」这个理由是错的。

真正的难点是两件：

1. `onInbound` 是 `createInboundServer({ onInbound })` 传进去的（`host.js:3347`），
   要测它得**真 bind 一个端口**再打 HTTP，或者把 `onInbound` 从 `apply()` 闭包里掏出来；
2. 每一轮都要一个**活的 DSH agent**（`agent.followup` + 事件流），在单测里造不出来。

抽壳解决的是第 1 条（队列逻辑与 HTTP 解耦），第 2 条用假 `handleTurn` 绕开：

```js
createInboundShell({ q, handleTurn, postReply, chatOf, now })
// 返回 { onInbound }；handleTurn 在测试里换成假函数
```

这样「排队不丢消息」「队列满不写 lastTurn」这些断言可以纯函数级验证，
不必起宿主、不必真发消息。

### 6.2 `test/turnqueue.test.js`（纯逻辑，假时钟）

1. 空闲时立刻执行，`queued:false`；
2. 忙时入队，前一个结束后按 FIFO 依次执行（并发度恒为 1）；
3. 队列满返回 `full`，且不执行；
4. `deadline` 余量不足返回 `expired`；入队后到点出队时余量不足 → 跳过并 resolve；
5. 任务抛错不会卡死队列（后续任务照跑）；
6. 看门狗到点释放槽位，且原任务晚到不重复释放；
7. `dispose()` 清掉定时器、放弃排队项；
8. **钉住表**：同一个 chatId 的 `resolveKey` 先后返回不同值时，仍进同一条队列（首轮分叉的回归用例）；
9. **尾段不得重叠**：任务 A 的 `handleTurn` 已返回但 `postReply` 仍 pending 时 push 任务 B，B 不得开始；
   且此时 `pinned` 里该 chatId 的 key 仍在。

### 6.3 `test/inbound-shell.test.js`

1. 同一 chat 连续两条 → `handleTurn` 被调用两次，且**没有**「上一条还在想」；
2. `queueMax=0` → 行为和现在完全一致（回归保护）；
3. 队列满 → 第二条收到「上一条还在想」，且**不产生** `lastTurn.ok=false`（壳里不该碰 `lastTurn`）；
4. 预算不足 → 收到「没赶上」，`handleTurn` 不被调用。

## 七、风险与回滚

| 风险 | 处理 |
|---|---|
| 串行后多条消息叠加变慢 | 实测单轮 2–3 秒，叠 2 条约 6 秒；`expiresAt` 兜底：来不及就不跑，明说没赶上 |
| 一个卡死拖死整群 | 看门狗 210 秒强放 + warn |
| 强放后两轮并发 | 接受；有 warn，可定位 |
| 排队体验「怎么不回我」 | 可后续加「入队超过 20 秒补一句」，本版不做 |
| 整体判断错误 | `queueMax=0` 一行配置回退，不用回滚版本 |

## 九、已知限制（写进 README「已知限制」）

- 排队只存内存：进程重启时，正在排的那条会丢（inbound 本来就是一次性的）。
- 排队的消息最多等 `queueMax` 条；再多仍会收到「上一条还在想」。
- 面板看不到队列长度（`stats()` 已经备好，等「运行数据」页一起做）。
- 会话归档重建 sessionId 后，钉住表要等该 chat 排空才更新；那一瞬间可能出现一轮并行。
- **凌晨巩固不进队列**：把 `memory.consolidateChat` 配成私聊 openid 时，
  它撞上正在跑的一轮仍会失败（次日补跑）。
- **让路会让主动搭话退避**：`<<skip>>` 与「她不想说」是同一个信号，
  所以每次因为忙而让路，该群的下次搭话间隔都会翻倍。
- **剩余预算不足 30 秒直接丢**：不会改发主动消息（理由见 §3.4）。
