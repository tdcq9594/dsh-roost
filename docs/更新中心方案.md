# 更新中心方案（设置页顶部）

> 目标：**一个地方**能更新两样东西——dsh-roost 本体（插件自己）、人格库。
>
> 本体更新走 DSH 自己的 `pluginManager` 服务，**不自己调 pnpm、不自己改 node_modules**。
>
> **已定（2026-10-28 主人拍板）**：不新开侧边栏入口，两块都放**设置页最上面**。
> 更新是低频动作，为它多占一行侧边栏不划算；而设置页本来就是"改这台机器"的地方。


## 一、可行性：已经查过 DSH 的实现

翻 `DeepSeek Harness/resources/app.asar` 确认了三件事，不是猜的：

**1. DSH 有一个 `pluginManager` 服务**，方法共 12 个：

```
pluginManager/inspect              listPlugins        listBundles
installBundle    cancelInstall     waitForInstall
removeBundle     setBundleEnabled   setPluginEnabled
registries       setVersionExemption   listVersionExemptions
```

**2. `installBundle(spec, options)` 就是现成的安全自更新原语。** 原文描述：

> Install a package using the same pnpm implementation as dsh plugin. …
> A run that fails, is cancelled, or adds a package without a bundle patch
> **restores `package.json` and `pnpm-lock.yaml` as they were**; downloaded files can stay.

参数：`spec`（一个包 spec，如 `dsh-roost@0.10.7`）、`options = { enabled, saveExact,
requestId, approvedBuilds, registry }`。结果 `ChangeResult` 里有
`application: success | failed | cancelled`、`packageResult`（pnpm 诊断）、`registries`、`bundle`。

**我们自己写这套东西的风险全在"改到一半坏了怎么回滚"**——DSH 已经做完了，包括
`requestId` 可取消、`waitForInstall` 可恢复。所以自更新不该自己实现。

**3. 调用方式**：插件里 `ctx.get('pluginManager')` 拿服务。
**不写进 `inject`** —— 老版本 DSH 没有这个服务，写进 inject 会让插件直接激活失败；
用 `ctx.get()` 拿到拿不到都只是"这个 DSH 版本不支持自更新"。

## 二、一个必须先挡住的坑：本机是符号链接

开发时 `~/.dsh/profiles/desktop/node_modules/dsh-roost` 是**指向源码目录的符号链接**
（本机现在就是这样）。这时候跑 `installBundle` 的后果是：

- pnpm 会把符号链接换成真实目录 → 开发链路断掉，改源码不再生效
- 而且 DSH 在 HMR 模式下对"已存在的依赖"会直接抛 `already-installed`

所以面板第一件事是**判断自己是怎么装的**：

```
lstatSync(<profile>/node_modules/dsh-roost).isSymbolicLink()
```

是链接 → 本体那行显示「开发模式（符号链接），自更新已禁用」，只留人格更新。
不是链接 → 正常显示版本和更新按钮。

这条不是"防用户"，是**防我自己**：下次改完代码在这台机器上点一下更新，源码仓库就被 pnpm 覆盖了。

## 四、本体更新的流程

```
1. 取 registry：pluginManager.registries() → 用配置的那个
   （拿不到就用 https://registry.npmjs.org）
2. 查最新版：GET <registry>/dsh-roost/latest → 取 .version，8 秒超时
   失败不重试第二次（更新是低频操作，报错让人重试比闷头重试好）
3. 比版本：自己的 package.json version vs latest（semver 比较）
4. 用户点「更新」→ POST /roost/api/self-update
5. 服务端：pluginManager.installBundle('dsh-roost@' + latest, { saveExact: true, requestId })
6. 按 application 三态收尾：
     success   → 显示「已装 v0.10.7，重启 DSH 生效」
     failed    → 显示人话（见下），本地什么都没动
     cancelled → 显示「已取消」
```

**失败要说人话。** `ManagementFailure` 的 code 直接抛给用户没人看得懂，映射一下：

| code | 面板显示 |
|---|---|
| `invalid-spec` | 版本号不合法，可能是 registry 返回了脏数据 |
| `already-installed` | 已经是这个版本了（HMR 模式下重装同一个包会被拒） |
| `registry-unreachable` | 连不上 registry，检查网络或换源 |
| 其它 | 「更新失败：」+ 原始 code，提示去 DSH 插件管理里手动更新 |

**为什么只更新 `dsh-roost` 这一个包名**：面板不接受任意包名。`installBundle` 的 `spec`
是字符串，虽然 DSH 自己挡了 `spec.startsWith('-')`（防 pnpm 参数注入），但我们这层也不该把
用户输入透传进去——否则这个面板就成了"任意装包"的洞。包名写死。

**重启**：DSH 里有 `restartApp` / `relaunch` 的痕迹（asar 里各出现 15 / 7 次），但没确认
是否暴露给插件。**这一版不提供重启按钮**，只提示"重启 DSH 生效"。P2 再查。

## 六、边界与风险

| 风险 | 处理 |
|---|---|
| 更新替换正在运行的代码 | Node 已加载的模块在内存里，改文件不影响当前进程；**必须重启才生效**，面板明说 |
| 更新期间动态 import 失败 | 查过：运行期只有一处动态 import——`src/tools.js` 里的 `await import('@deepseek-ai/dsh-tools')`，那是 DSH 自己的包（不在 `node_modules/dsh-roost` 里），首次加载后就进了模块缓存，不受影响。**但更新过程中不要点「重载插件」**——那会重新加载刚被 pnpm 改过的目录 |
| 更新把开发环境搞坏 | 符号链接检测，直接禁用（第二节） |
| 失败留半个包 | DSH 会回滚 `package.json` + `pnpm-lock.yaml`；我们不做二次回滚，避免两套逻辑打架 |
| 重复点击 | 前端 busy 锁 + 固定 `requestId`，服务端在飞的时候拒绝第二次 |
| 误以为"更新完就好了" | 成功文案必须带「重启 DSH 生效」，不能只说"更新成功" |

**不做自动更新。** 本体更新 = 改用户的安装，必须手动点。人格更新同理（人格突然变味比版本旧难受）。

## 七、24 小时发布冷却（pnpm `minimumReleaseAge`）

这一节是"为什么刚发的版本装不上"的答案。

**机制**：pnpm 10.16+ 的供应链保护，`minimumReleaseAge` **默认 1440 分钟（24 小时）**——
**发布不满 24 小时的包不装**。pnpm 11 默认开启。DSH 自己的 schema 里写得很明白：

> `version` … pnpm's `minimumReleaseAge` **can make it older than the newest release**.

也就是说 DSH 不绕过它，只是如实报告"装到的可能不是最新版"。而且注意：是**降级**不是失败——
pnpm 会挑一个满 24 小时的版本装上，用户看到的是"更新成功了"，版本号却停在旧的。

**本机实测**（2026-10-28 19:00）：

```
~/.dsh/profiles/desktop/pnpm-workspace.yaml
minimumReleaseAgeExclude:
  - dsh-roost@0.3.2 || 0.3.3 || … || 0.5.13      ← 17 个历史版本
```

这个列表就是这个冷却期一次次手动豁免攒下来的。而 0.10.4 / 0.10.5 / 0.10.6 都不在里面，
发布时间分别是 **7.6 小时 / 46 分钟 / 30 分钟**前——**全在冷却期内**。

**三条路**

| 做法 | 评价 |
|---|---|
| 把 `dsh-roost@<新版本>` 加进 `minimumReleaseAgeExclude` | **推荐**。pnpm 提供的正规豁免口，可审计、只对本包生效 |
| `minimumReleaseAge: 0` 全局关掉 | 不要。等于对所有包关掉防投毒保护 |
| 用 tarball 直链当 spec 绕 | 不写进产品。`installBundle` 的 spec 本来就允许 tarball / git，**能绕**，但绕掉的是安全机制，不该当功能做 |

**这不是 bug，是防线**：24 小时窗口是给"npm 账号被盗后发毒包"和"抢注同名包"留的发现时间。
对我们自己的包（作者=维护者）风险可控；对第三方包不要绕。

**面板要处理三件事**

1. **显示发布时长**：查最新版时顺手读 npm 的 `time` 字段，算出"发布 30 分钟前"。
   不满 24 小时就在按钮旁标出来，别让用户点了才发现没动。
2. **核对装到的版本**：请求 `0.10.6` 却返回 `0.10.5`，要明说
   「因为发布不满 24 小时，pnpm 装到了 0.10.5」，**不能假装成功**。
   （`ChangeResult` 里有 `version` 字段，就是给这个用的。）
3. **给一个「立即安装（不等 24 小时）」按钮**：
   ```
   备份 pnpm-workspace.yaml → 按行改（不解析重排，里面有注释和其他键）
   → 清掉旧的 dsh-roost@… 条目，只写最新一条 → 原子写（.tmp + rename）
   → 再调 installBundle
   ```
   **只对本包生效**，不接受任意包名；否则这个面板就成了"给任何包跳过安全期"的洞。

**本机特例**：这台机器 `package.json` 里是

```json
"dsh-roost": "link:C:/Users/q9079/WorkBuddy AI/workbody.work/douluo/dsh-roost"
```

`node_modules/dsh-roost` 是符号链接 → **本机根本不走 npm 更新**，改完源码重启就是最新。
24 小时机制对我们自己的开发机没有影响，它影响的是真实用户。

## 九、落地顺序

1. **只读面板**：侧边栏条目 + 查最新版 + 显示状态（不改任何东西）——先让"有没有新版"可见
2. **本体自更新**：接 `installBundle` + 失败映射 + 符号链接禁用
3. **人格更新**：接 `/personas/sync`（依赖人格仓库方案的 P0）

前两步拆开提交，自更新出问题能单独回退，不用连带面板一起撤。

## 十、三个问题的结论（2026-10-28 已定）

1. **放哪儿**：不做独立侧边栏条目，两块都放**设置页最上面**（第三节）。
2. **要不要自动检查**：进设置页（或「人格与情绪」页）时查一次，**不后台轮询、不自动装**。
3. **「立即安装（不等 24 小时）」做不做**：**做**（只对本包、写之前备份）；
   但**不预先往 `minimumReleaseAgeExclude` 里塞条目**——那条豁免由用户点按钮时才写，
   平时那个列表不该因为"我们发了个版"而自己变长。
